# 多卡执行与通信：张量拆分、分阶段执行最小原型

后续追加：[P800执行状态定位、单卡恢复与分桶验收修复](P800_EXECUTION_STATE_ROOTCAUSE_20261111.md)已完成，P800三路径9/9严格通过，主机回归增至115。下文保留首批实验及当时未完成边界，不回写旧失败记录；最新状态以上述追加报告及STATUS为准。

## 📋 本周交付与计划对应

本周由已验证的数据并行训练，推进到计划中的张量并行（TP）和流水线并行（PP）执行关系：新增双卡张量分片计算、两阶段前向/反向传递、重复启动和严格汇总入口。**这是两层合成网络的正确性原型，不是 DeepFM 或 OneRec-8B 的 TP/PP 改造，更不是完整流水调度器。** PP 当前串行推进微批，尚无计算通信重叠或吞吐收益结论。

| 计划功能 | 本周新增 | 实际验证范围 | 尚未交付 |
| --- | --- | --- | --- |
| 张量并行执行 | 按给定计划切分第一层输出通道、第二层输入通道，规约局部输出 | 两种分片宽度；逐步核对完整输出、分片梯度和更新后参数 | 真实模型切分、混合并行、多节点 |
| 流水线并行执行 | 两层分别放在两端，传递激活并反向返回梯度；按完整 batch 累加微批梯度 | 两阶段、2/4 个微批、固定 shape，串行正确性基线 | 1F1B/重叠调度、动态 shape、背压、真实模型流水 |
| 复现与验收 | 保存每次启动退出码、逐端逐步检查、调用数、载荷及源码摘要；失败不重试覆盖 | CPU/Gloo 与 910C/HCCL 分别严格汇总 | 不把 CPU 通过替代设备验收，不把 HCCL 通过替代 FlagCX 修复 |
| 训练前设备检查 | 在原有空闲、镜像和 UUID 校验后增加逐卡基础计算检查及排除列表 | P800 本轮成功拦截基础计算超时，未进入训练 | 不重置共享设备，不认定物理损坏 |

## 📊 TP/PP 实测

固定 FP32、batch=16、输入维度16、输出维度8、50步 SGD。TP 隐藏宽度32/64，PP 隐藏宽度32且微批数2/4。每种配置独立启动三次，第二轮反转运行顺序；每次两端。CPU autograd 完整网络为参考，每一步均核对，不只比较最后 loss。

| 环境 | 配置 / 启动 / 端记录 | 训练步数（不重复计算两端） | 输出及梯度检查最大绝对误差 | 更新参数最大绝对误差 | 退出与汇总 |
| --- | --- | --- | --- | --- | --- |
| CPU/Gloo | 4 / 12 / 24 | 600 | 2.384185791015625e-7 | 1.4901161193847656e-8 | 12次退出0，24端 CLOSED，PASS |
| 910C/HCCL | 4 / 12 / 24 | 600 | 3.5762786865234375e-7 | 1.4901161193847656e-8 | 12次退出0，24端 CLOSED，PASS |

原始证据：[CPU 汇总](../results/20261111-parallel-and-preflight/cpu-gloo/summary.json)、[910C 汇总](../results/20261111-parallel-and-preflight/ascend-hccl/summary.json)。对应目录包含每次启动记录、日志和全部逐端 JSON。判据为完整50步、所有启动退出0、通信组 CLOSED、数值有限且误差满足固定阈值（逐张量 `atol=1e-5, rtol=1e-4`，汇总另限制最大绝对误差不超过1e-5）。

TP 每端每轮51次 AllReduce：1次建组后预热，50次输出聚合，输入载荷25,604字节。PP 每端先做1次预热 AllReduce；微批2/4时每端每轮各100/200次 Send 和 Recv，两个方向各102,400字节。载荷是传入张量字节数，**不是链路流量**；微批增多没有增加总激活体积，但调用数增加。

TP 两端持有不同参数分片，PP 两端持有不同层，不能套用数据并行的“两端参数完全相等”判据；本实现逐端比对各自应持有的参考分片/层。TP 输出执行 SUM，不再除以 world_size；PP 按完整 batch 归一化，避免微批数改变导致梯度倍增。

## 📊 DeepFM 分桶验收对照

在同一910C/HCCL基座上，用逐张量同步、合并同步和受控自动同步三种路径各独立运行三次，每次预热5步、训练50步，**9/9启动退出0，18份端记录通过且通信组CLOSED，严格汇总PASS**。每端每轮17/17项梯度参考通过，最大梯度误差4.190951585769653e-9，更新参考最大误差3.725290298461914e-9，最终跨端参数差0；三路径loss最大差5.960464477539062e-7。见[严格汇总及逐端记录](../results/20261111-parallel-and-preflight/deepfm-hccl/summary.json)。

受控自动同步由DDP组织反向和分桶，通信钩子明确执行SUM后除以world_size一次；不等同默认原生DDP。本次重建后两个桶为1,291,204与394,604字节，合计1,685,808字节，50步每端100次梯度通信、输入载荷84,290,400字节。新版汇总消费实际桶大小，检查字节覆盖和调用次数，不再假设固定单桶。此对照确认该验收入口在HCCL上能完整通过，**不关闭P800/FlagCX受控验收或默认DDP问题**。

逐张量/合并/受控自动同步的非首步平均step分别为9.58±0.21 / 6.58±0.62 / 5.40±0.09 ms（各三次独立均值的样本标准差）。只是同机合成输入功能对照，包含框架与打包等成本，不是纯通信时延、真实业务吞吐或跨周性能收益；周报不据此宣传加速。

## 🖥️ 实测基座与复现

910C 使用经用户批准共用的 `npu-eval`，实际镜像为公共 **ascend-operator-runtime v3**，image ID 为 `sha256:62bcaae3f8399b9444628aa24085e0da6871871eb5299ca29e3b2712dc91e106`。Python3.11、torch2.10.0+cpu、torch_npu，通信后端 HCCL；这**不是 train-comm v3/FlagCX 镜像验收**。只在独立临时目录解包自己的测试副本，按进程设置 `ASCEND_RT_VISIBLE_DEVICES=10,11`，可见设备数实测为2；未改现有挂载、安装依赖、重启或停止共享容器。

在已经完成环境、设备空闲与使用权核对的容器中执行（`RUNTIME_ROOT` 指向选定且记录版本的原型目录）：

```bash
python3 dev/communication/training/run_parallel_matrix.py \
  --backend ascend --collective hccl \
  --runtime-root "$RUNTIME_ROOT" \
  --prototype-revision 3f95b09411cb6b305151444d05d9f865b163b229 \
  --output /tmp/communication-parallel-NEW --launch-timeout 120
```

CPU 使用 `--backend cpu`；macOS 的 Gloo 网卡按实际环境指定，本轮为 `GLOO_SOCKET_IFNAME=lo0`。输出目录必须全新，不覆盖原始证据。P800 使用启动器 `--mode pair --parallel-minimal`，必须先满足其设备检查与公共镜像 strict 基线；当前没有通过的 P800 TP/PP 批次。

## ⚠️ P800 问题：基础计算超时，不冒称通信修复

本周两组候选卡对4/5、6/7的 DeepFM 前置显式同步均未完成，启动器超时后非零结束，**没有进入受控 DDP 验收**。随后剥离训练、设备原型和 FlagCX 调用，仅保留厂商 torch 原生单卡探针：物理6通过填充回读、32² matmul和事件查询；物理7在 `fill_and_synchronize` 超时（退出137）。同窗口 PCI `bb:00` 内核日志出现常量填充内核超时、`XPUERR_KEXCEPTION` 和 `KL_XID_KERNEL_EXCEPTION`。这把本次失败前置到基础执行/同步阶段，不能直接判定为 FlagCX 逻辑错误，也不足以确认物理卡损坏。

补入启动前逐卡检查后，再查4/5卡对；物理4同样在填充同步阶段超时，启动器记录 `ERROR`，模型运行列表为空。物理5本轮未单独验证，不外推其状态。证据见 [原生隔离探针](../results/20261111-parallel-and-preflight/p800/native-isolation/)、[内核窗口](../results/20261111-parallel-and-preflight/p800/kernel-window.log)及[新前置检查拦截记录](../results/20261111-parallel-and-preflight/p800/controlled-strict-r4/selection-execution.json)。

`XPU_EVENT_KL3_ENABLE` 继续遵守公共 K-3 基线、保持未设置。曾试设为1以核对厂商告警，但被镜像身份探针直接拒绝，未运行训练，随后撤回；该记录单列为前置拒绝，不是修复。自有测试容器已停止；未改驱动、reset卡或停止他人任务。默认原生 DDP 的既有梯度问题和 P800 受控路径严格验收仍开放，本周未提交缺乏证据的 FlagCX C++ 补丁。
