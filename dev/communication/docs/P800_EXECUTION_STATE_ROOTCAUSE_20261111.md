# P800 计算超时：隔离定位、单卡恢复与训练验收

_范围：第二台新 P800 的物理卡4/6/7；区分当前阻塞的直接原因与尚未确定的原始触发缺陷。_

---

## 📋 结论

当前阻塞双卡测试的直接原因已定位到**设备侧计算执行状态异常**：卡7没有显存占用、没有进程或设备句柄，但计算内核不能完成；该状态跨新进程、新容器和两个独立框架版本持续存在。用户批准后，仅复位卡7，驱动记录其 `cu0_noc_main_pending(0x37)`，随后原样测试恢复。卡6保持通过，未复位的卡4保持失败，形成卡级前后对照。

这不是“设备忙”或“没有sudo权限”，也不需要调用我们的训练脚本、设备原型或FlagCX才能复现。**不等于已经确认永久物理损坏，也不等于已经定位最初触发异常的具体算子/固件缺陷。** 单卡复位会同时清理多项设备状态，不能仅凭日志把根因进一步断言为某个NoC硬件模块损坏。

恢复后，P800物理6/7上的DeepFM三种同步路径各三轮、每轮50步，9/9通过严格验收，最终跨端参数差0。期间还定位并修复了本方向验收工具读取旧分桶日志的问题；没有把旧失败批次改写成PASS。

## 🔍 故障为何不是简单的占用或框架配置

sudo检查了宿主内核、完整设备信息、设备文件持有者和PCI信息。目标卡复位前 `Memory_used=0`、利用率0、`Processes: None`，root下 `fuser` 无持有者。三张卡同为驱动5.0.21.47、同固件，PCIe均为Gen5×16；查询中的ECC计数为0、无pending remap。上述查询只证明控制面可访问，不能替代实际计算检查。

隔离过程只映射当次目标设备节点及控制节点，按PCI/UUID核对身份。普通CUDA兼容驱动/运行时的分配、填充和回读在三卡都通过；真正计算算子在卡4/7失败。再用不导入PyTorch、FlagCX或设备原型的独立C++程序调用厂商XDNN `constant<float>`，未复位卡4仍停在内核等待，而卡6及已复位卡7通过。因此不能把问题只归到本方向Python代码或某一训练镜像。

| 对照项目 | 卡6：未操作的对照 | 卡7：唯一复位目标 | 卡4：未复位的负对照 |
| --- | --- | --- | --- |
| 复位前，裸驱动内存操作 | PASS | PASS | PASS |
| 复位前，厂商运行时内存操作 | PASS | PASS | PASS |
| 复位前，独立PyTorch2.5计算 | PASS | 超时 | 超时 |
| 复位后，公共PyTorch2.9计算 | PASS | PASS | 超时 |
| 复位后，独立PyTorch2.5计算 | PASS | PASS | 超时 |
| 复位后，独立XDNN计算内核 | PASS | PASS | 超时 |

这里的普通内存填充不能冒称计算内核成功：它和XDNN/PyTorch算子走的路径不同。独立镜像仅作诊断，不是新公共基座，也未安装或修改公共镜像。证据：[复位前隔离](../results/20261111-p800-rootcause/isolation-before/)、[复位后隔离](../results/20261111-p800-rootcause/isolation-after/)、[独立XDNN对照](../results/20261111-p800-rootcause/native-xdnn/)。当日较早的公共PyTorch2.9失败记录继续保留于[原前置检查](../results/20261111-parallel-and-preflight/p800/controlled-strict-r4/selection-execution.json)。

## 🔄 授权与恢复对照

本次仅对第二台机器的物理卡7执行一次单卡复位：PCI `0000:bb:00.0`、UUID `GPU-66371c5f-2ce9-5990-9dfa-be6236b4f74e`、节点`/dev/xpu6`。**SMI物理卡号不等于节点后缀**，执行前逐项核对，root检查无进程/句柄后才操作。没有重置卡4或其他卡，没有重载驱动、重启服务器、修改基座或停止他人容器。

驱动复位记录节选：

```text
(PCI:0000:bb:00): reset begin ...
(PCI:0000:bb:00): cu0_noc_main_pending(0x37), but reset anyway ...
(PCI:0000:bb:00): m3 mode1 reset...(at most 10s)
(PCI:0000:bb:00): reset done ...
```

复位命令退出0，复位前后其他运行容器ID列表一致。相同探针在原PyTorch2.9镜像和独立PyTorch2.5镜像均恢复填充、矩阵计算和事件检查；未复位卡4仍超时。整个复验观察窗口内，卡7没有新 `KL_XID_KERNEL_EXCEPTION`。见[一次性操作与身份守卫记录](../results/20261111-p800-rootcause/reset-card7.json)和[最终服务器状态](../results/20261111-p800-rootcause/final-server-state.json)。

普通退出进程/重建容器未消除这次状态，而单卡复位消除了它，这就是本次当前阻塞的直接恢复路径。**复位不是共享服务器上的自动重试策略**；后续如再发生，仍须先隔离、留证、排除资源，再经授权操作。

## 🔧 同时修复的验收工具问题

设备恢复后的r5批次，九次启动退出0、各端功能检查通过，但严格汇总仍为ERROR：`Unexpected gradient call count`。原因不是新的梯度错误，而是代码把 `_get_ddp_logging_data()` 中的桶大小当作重建后的实际值。P800的PyTorch2.9只给出初始化总桶1,685,808字节；实际梯度回调为每端每轮100次，旧工具按单桶预期50次，因而拒绝验收。r5保持原记录，不事后补造桶元数据。

这是消费者采集假设错误，不据此认定厂商日志接口本身有缺陷。现在在每个实测反向中直接采集 `GradBucket.index()` 与输入张量字节数，完整记录50步，要求桶索引连续且唯一、两端计划一致、每步覆盖全部FP32参数梯度、调用次数及输入总字节相符。原DDP日志只作旁证，不据次数猜桶、不硬套910C的桶大小。回调采集位于原通信/平均/同步完成后，不改变梯度数学或通信完成语义。

r6实际记录两个桶为 **1,289,604 / 396,204字节**，合计1,685,808；每端每轮100次梯度通信、输入载荷84,290,400字节。这与日志的旧单桶确有差异。汇总对缺步、重复桶、错误索引/字节及旧记录仍严格拒绝。新增13项主机回归，总计115/115通过，CPU/Gloo三路径九轮严格通过；这些不计入NPU验收。修复入口：[通信钩子与真实桶记录](../training/distributed.py)、[训练采集](../training/deepfm_train.py)、[严格汇总](../training/summarize_repeated.py)。

## ⚠️ 已解决范围与仍开放的问题

当前卡7的训练阻塞已恢复，P800受控DDP严格验收已闭环；这不代表所有P800问题关闭。卡4仍计算超时、未获复位授权，继续排除；卡0/5没有本轮完整健康判定。默认原生DDP不同于本轮受控通信钩子，其既有梯度问题仍开放，没有提交未经验证的FlagCX C++修复。

保留日志中可见更早的`get_cluster_clock`超时，且健康对照卡6也有历史异常计数，说明不能用一条XID或累计次数判定永久卡损坏。原始触发负载、具体驱动/固件缺陷及复发条件尚未通过因果实验锁定，须在隔离维护窗口与厂商进一步分析；不把旧PID映射到当前同号进程来猜测责任人，也不在公共机器上重放已知会挂死的负载以追求复现。

完整宿主日志仅留本地，仓库保留相关时间窗口、身份、执行记录与源码。后续继续使用逐卡实际计算检查；设备状态恢复与默认DDP修复分开跟踪。
