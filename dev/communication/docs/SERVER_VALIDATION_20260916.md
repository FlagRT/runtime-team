# 服务器验证结论（发布摘要）

使用当前 stack.lock v2 的 lock.train 镜像，未切换候选镜像。
原始服务器日志及内部配置仅在本地证据分支保存，不随此次代码提交发布。

## 已完成

- 基于 FlagCX `4e0e0cb` 整理的两项修复，在锁定环境中通过核心库编译，生成 libflagcx.so。
- Torch 插件完整编译通过，生成扩展动态库；未覆盖原安装库。
- 修改后的 Event 头文件通过真实 CANN 头文件编译检查。
- 14 项主机进程/结果验收测试通过；Event 主机模拟测试完成 1000 次创建/释放配对。
- 新增命名空间快照关联工具，7 项解析测试通过；实机快照中 16 个逻辑设备全部关联到同一个存活容器。此项是环境诊断，不是通信数值验证。

## 未完成与实测阻塞

双卡运行在 ACL 初始化阶段失败，未进入数值校验。独立 ACL 检查不加载 Torch/FlagCX，
仍返回 500000；驱动返回 87 RESOURCE_OCCUPIED，内核记录跨容器设备命名空间冲突。
仅挂载空闲设备的隔离对照仍复现。

本轮进一步读取驱动随附源码 `kernel/dbl/uda/uda_access.c`，确认该检查使用的是
`mnt_ns`（挂载命名空间），不是设备计算利用率，也不是 PID 命名空间。
`uda_occupy_dev_by_ns()` 对非共享设备拒绝另一个仍存活命名空间的访问；
`uda_dev_is_occupied()` 检查已登记根进程是否退出。因此空闲但仍运行的容器也可能保留归属。
实机 `/proc/uda/udevice`、`namespace_node` 和 Docker 主进程快照对应一致：
16 个逻辑设备登记在同一现存容器名下，正是错误日志中的被占用命名空间。
具体容器名、PID、命名空间标识只保留在本地证据，不发布到仓库。

已确认冲突归属及源码机制；尚未做停止该容器后的 A/B，故不承诺释放后所有问题都会消失。
没有证据将根因归为算力繁忙、主机监控进程或驱动版本升级；仅改可见卡列表不能改变已有归属。

临时诊断实例已删除，原训练容器恢复原名称及停止状态；没有停止其他成员服务或修改驱动。
已请求用户批准临时停止归属容器、测试后恢复；未获得批准前不执行。
释放并复查 ACL 后才能继续双卡、跨流、故障退出和训练回归。编译通过不等于修复已验收，
也不证明已解决候选镜像退出 SIGABRT。

## 复用检查

将同一时段的 `udevice`、`namespace_node`、Docker inspect JSON 快照留在本地，再执行：

```bash
python3 dev/communication/probes/namespace_ownership.py \
  --udevice /path/to/local/udevice.txt \
  --namespace-node /path/to/local/namespace.txt \
  --containers /path/to/local/containers.json
```

该工具不连接服务器、不停止容器、不改驱动；快照缺失或无法关联不能被解释成设备空闲。
进程退出、PID 复用及快照间状态变化需要人工复核，工具输出不能替代释放授权。
