## 4) 两种形态在编译流水线上的位置（同一条路径的两个不同失败阶段）
triton/backends/xpu/compiler.py:581-585 的 stage 注册顺序：
   stages["ttir"] -> stages["ttxir"] -> stages["llir"] -> stages["elf"] -> stages["xpubin"]

·「OutOfResources: uni_sram」= 第 2 阶段 ttxir 失败，被 compiler.py:362-367 包装：
       try:
           pm.run(mod, 'make_ttxir')
       except Exception as e:
           from triton import OutOfResources
           raise OutOfResources(0, 0, f"uni_sram {e}")
   注意这是**误标**：它把 pm.run 抛出的任何异常一律包成 OutOfResources，消息里的
   "Required: 0, Hardware limit: 0" 是硬编码的零，并非真的显存/uni_sram 不足。
   e 的原文是 "PassManager::run failed"。
·「原生 abort」= 第 3 阶段 llir 失败，compiler.py:486 的 `pm.run(mod, 'make_llir')`
   **没有 try/except**，而 LLVM 的 assert 是不可捕获的原生断言 -> abort()。
=> 早一步（ttxir）就失败的形状/dtype 永远走不到 llir，于是拿到「礼貌的」包装异常；
   能过 ttxir 的那些接着在 llir 撞上 LLVM 断言，于是原生死掉。
   **两种形态是同一个缺陷在不同阶段暴露，差别只在该阶段有没有错误处理。**

## 6) 口径更正（仓内两处现有记述不准确）
① v2/lock.yaml known_issues: gemm-failure-signature-differs-from-v1 的 description 写
   v2 形态是「退出码 1（进程正常抛异常，未 SIGABRT）」，并以此与 v1 的 SIGABRT 对比。
   实测：**v1 那次的退出码也是 1**（见 v1 证据文件底部 EXIT=1），且 v2 上的 abort 形态
   同样是 rc=1、未被信号杀死。rc 在两种形态下都是 1，**不能用来区分形态**。
   真正的区分点是「有没有 Fatal Python error: Aborted / LLVM 原生断言」。
② 本轮一次性观测到过 rc=134（首次整文件 -x -s 跑，当时 triton 编译缓存为冷）。
   随后以相同命令形态复测 5 次（含 os.waitpid 直读 WTERMSIG）均为 rc=1 / 未被信号杀死，
   该 134 未能复现。**本文件以可复现的 rc=1 为结论**，134 仅作为一次性观测记录在此。

## 7) 一个取数陷阱（复跑时务必注意）
pytest 不加 -s（即启用 capture）时，abort 形态的**输出会整段丢失**：进程在 pytest 写出
报告之前就死了，被捕获的 stdout/stderr 随之丢弃，落到文件里是 **0 字节、rc=1**。
实测同一用例：
   -s  三次：rc=1，880 字节，均含 LLVM 断言
   -q  三次：rc=1，**0 字节**，无任何标记
另：设 PYTHONFAULTHANDLER=1 反而会压掉 faulthandler 的 Python 栈 dump（只剩 LLVM 断言行）；
要拿到 Python 栈，用 TODO #18 里那条原始命令形态（pytest -x -s，不额外设该变量）。
