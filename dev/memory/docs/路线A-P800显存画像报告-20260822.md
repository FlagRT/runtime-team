## 5. 结论：KV 预分配策略与利用率分析

1. **预分配结构（gpu_mem_util=0.9，eager）**：权重 7.56 GiB + **KV 76.40 GiB（~89%）** + 工作区 ~1.7 GiB = 85.69 GiB（占卡 89.3%）。KV 预分配激进但**无碎片**（vLLM 块表整块管理），代价是其余用途（graph 工作区、更大激活余量）被挤出。
2. **利用率口径**：556,352 tokens 对应 40,960 长请求 × 13.58 并发容量；对 4B 模型的常规负载（短上下文、低并发）实际 KV 占用远低于预分配上限——预分配换容量、不换即时占用，这是 vLLM 块表设计使然，**分层缓存/可控溢出的主对象确认为 KV 不变**（910c 76% → P800 89%，占比更高）。
3. **eager vs graph 的显存权衡（新数据点）**：P800 上 `enforce_eager=True` 比 graph 模式**多出 7.2 GiB KV 容量**（76.40 vs 69.22 GiB，无 graph 工作区）且 init 快 ~7 倍（10.26s vs 71.5s），代价是 decode 吞吐下降（~17-20 vs 96.5 tok/s）。**若 KV 容量是瓶颈，eager 是"零成本扩容"选项**；若吞吐优先则用 graph 模式。
4. **对 V2-A（显存池 A/B 定义）建议**：P800 无 torch_fl 池（torch_plugin 0.1.0），A/B 开关应定义为 **vLLM 层参数组合**（gpu_memory_utilization / enforce_eager / max_num_seqs / KV 块大小）vs 厂商 torch allocator 行为，基线用本报告数值（eager：KV 76.40 GiB；graph：69.22 GiB）。建议首轮做 `gpu_memory_utilization ∈ {0.7, 0.8, 0.9}` 梯度测试，量化 KV 容量 vs 峰值余量的互换曲线（预期 0.9 档 KV ~76 GiB、0.7 档 ~60 GiB 级）。
5. **对 V3-A（分层缓存原型）建议**：KV 块级管理无碎片 + 89% 占比 → Host 溢出对象与粒度明确（以 vLLM 块为单位，evict_blocks + flagcx_connector 模式沿用 vllm-offload 调研）；8k/32k 长上下文在 P800 可实际跑通（本画像 8192 档 1.88s），V3 的容量收益与吞吐代价可在真实长序列负载上验证，**不受 910c 式 P0 阻塞**。
6. **口径备忘**：① 探针 hbm_gib 为 GB（1e9）口径，与 xpu-smi MiB / vLLM GiB 换算时注意；② 日志中 `No module named 'triton.language.target_info'` 为非致命已知告警（官方镜像 gpt_oss_triton_kernels_moe import fallback，见 flagos 技能坑位记录），不影响结果；③ 全阶段 180s 超时未触发，实际最长阶段 3.39s。
