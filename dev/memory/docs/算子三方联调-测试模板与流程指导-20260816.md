## 1. 模板长什么样（先看整体）

新增两个文件 + 一份说明，都在 `tests/integration/ops/`：

| 文件 | 作用 | 谁用 |
|---|---|---|
| `template_op_test.py` | **空白模板**（带 mm 默认配置，可直接跑） | 算子组复制改名 |
| `test_mm_triparty_template_demo.py` | **mm 完整样例**（模板怎么填的参考答案） | 三组对照学习 |
| `README.md` | 英文使用说明（仓库内给所有人看） | 全组 |

模板内部按会议的"三方分工"切成三块，每块顶部有醒目标记：

```
[Op Team]       TestOpNumericalCorrectness   数值正确性（形状×dtype 全组合）
[Compiler Team] TestOpCompileAndLaunch       编译启动（写一次管所有算子）
[Runtime Team]  TestOpRuntimeDispatch        设备调度（写一次管所有算子）
```

三块共享同一个配置表 `OP_CONFIG`——新增算子时**只填这一张表**，三块测试自动生效。

## 2. 三方各自要做什么（按会议决策 B）

### 算子组（工作量最大：每算子一条）

新增算子时：

1. 复制 `template_op_test.py` → 改名 `test_<算子名>_dispatch.py`
2. 填 `OP_CONFIG` 表：算子名、torch 接口、要测的形状、dtype、**精度阈值**
3. 输入生成函数 `_make_inputs` 若与"两输入一输出"不同则改写
4. 在 [Op Team] 区块补算子特有的边界用例（非连续、零尺寸、极端值、out= 别名等）
5. 跑 `pytest tests/integration/ops/test_<算子名>_dispatch.py -v`
6. 想让 CI 冒烟覆盖，给代表用例加 `@pytest.mark.main_ops`

### 编译组（写一次管所有算子）

不需要为每个算子写新代码——[Compiler Team] 区块已经是通用实现：
- 首次调用触发 kernel 编译不报错
- 同形状重复调用复用已编译 kernel
- 每种配置形状都能编译并启动（覆盖 JIT 形状变化重编译路径）

编译组要做的是：**在真实硬件上把这块跑一遍确认机制可用**（已实测通过），
以后新增算子由模板自动覆盖。如果某算子编译路径特殊，在 [Compiler Team] 区块
追加该算子的编译用例。

### Runtime 组（写一次管所有算子）

[Runtime Team] 区块同样通用：
- flagos 设备已注册、设备数 ≥1
- dispatch 日志能显示该算子实际走的后端（`[flagos dispatch] mm -> ascend`）
- `FLAGOS_OP_<算子名>` 环境变量覆盖生效（调试逃生门）

Runtime 组的持续责任：模板机制维护（新增平台改 `native_backend` 字段）、
conftest 平台标记维护。

## 3. 精度标准怎么定（按会议决策 C）

- **算子组定阈值**，写在 `OP_CONFIG["tolerances"]`，按 dtype 分列
  `(rtol, atol)`，定完三方在契约评审时确认。
- **参照用 fp64 计算**，且与设备输入是**同一份数据**（CPU 生成后拷贝到设备，
  同 seed 可复现）——这样阈值只吸收设备 kernel 自身的累加误差，
  不会把"两个不同 fp32 实现的重排误差"也算进去（后者即使实现全对也有 1e-3 级差异）。
- 实测参考（Ascend 910C，mm 算子）：fp32 `(1e-2, 2e-2)`、fp16 `(5e-2, 5e-2)`
  在模板全部形状下通过。想收紧欢迎，以目标硬件实测通过为准。

**坑（模板已踩平，写死进注释）**：
- 不要用 CPU fp32 当参照——累加顺序不同，正确实现也会差到 1e-3 级误报。
- `assert_close` 默认查 dtype——设备输出转 fp64 再比（`out.cpu().double()`）。
- 不要在设备上生成随机输入——NPU 与 CPU 的 RNG 序列不同，参照必须同源。

## 4. 完整联调流程实录（2026-08-16，Ascend 910C 实机）

**环境**：容器 `flagos-fl-dev-910c`（host 网络 · CANN 9.0.0 · torch_fl 主线），
venv `/root/tf-venv-integration`（阶段 3 编译产物，pytest 已装），16 卡空闲。

**步骤与结果**：

```bash
# 进容器，仓库已 bind-mount（宿主 /home/xliu969/workspace/PyTorch-Plugin-FL ↔ 容器 /workspace/PyTorch-Plugin-FL）
cd /workspace/PyTorch-Plugin-FL

# 1) 跑 mm 完整样例（三方联调验证）
/root/tf-venv-integration/bin/python -m pytest \
  tests/integration/ops/test_mm_triparty_template_demo.py -v
# → 19 passed（数值 11 + 编译启动 5 + 设备调度 3）

# 2) 跑空白模板自检（验证模板本身可复用）
/root/tf-venv-integration/bin/python -m pytest \
  tests/integration/ops/template_op_test.py -v
# → 18 passed

# 3) （CI 冒烟子集验证，可选）
/root/tf-venv-integration/bin/python -m pytest \
  tests/integration/ops/ -m main_ops -q
```

**联调中真实抓到并修掉的两个模板缺陷**（这也是模板价值证明）：
1. 参照用 CPU fp32 → 误报（正确实现也有 1e-3 级重排误差）→ 改 fp64 同源参照。
2. dispatch 覆盖测试硬编码 flaggems_python → 环境没装 FlagGems 就挂
   → 改为 `OP_CONFIG["native_backend"]` 可配置（ascend）。

**三块各自验证了什么**（对应三方交付物）：
- 数值块：mm 在 flagos 设备上 4 形状 × 2 dtype 与 fp64 参照一致、out= 别名、
  非连续输入——**算子组的算法与实现正确**。
- 编译块：首次编译、复用、多形状 JIT 重编译全部启动成功——**编译组的
  编译/启动链路可用**。
- 调度块：设备注册、dispatch 日志、env 覆盖——**Runtime 的设备接入与调度正确**。
