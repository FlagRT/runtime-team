## 1. 结论（一屏）

> **v5.0.0（新线镜像目标版）未补 `renormalize`——kunlunxin 后端 `topk_softmax` 仍为 4 参。**
> 进一步检查当前最新 release **v5.3.4** 与最新 dev tag **v5.4.0.dev0**：**仍未补**（4 参）。
> → 指南待办 #1 状态更新：**静态检查确认修复未落地**。
> → 新线镜像（gems 5.0.0）复测纯 MoE，预计仍会在 profile_run dummy run 处触发
> `TypeError: topk_softmax() takes 4 positional arguments but 5 were given`（与 4.2.1rc0 完全同源）。
> → 复测仍值得执行（实证 + 触发厂商修复 + 为 issue 附最新 file:line），但**若目标为打通到
> fused_experts 取得 MoE 内核数据，必须先做临时包装探针**（按指南 §三.7，标注探针、不进交付路径）。

  > 与 gems 4.2.1rc0 的过期配对；**可先静态检查 5.x 的 `_kunlunxin/fused/topk_softmax.py` 是否已补 `renormalize`**。

## 5. dispatch 机制核实（v5.0.0，防误判）

kunlunxin vendor 下 `flag_gems.topk_softmax` 必然解析到 4 参实现，链路：

1. `src/flag_gems/__init__.py:10` → `from flag_gems.fused import *`
2. `src/flag_gems/fused/__init__.py:64` → `from flag_gems.fused.topk_softmax import topk_softmax`（通用 5 参，进 flag_gems 命名空间）
3. `src/flag_gems/__init__.py:25` → `runtime.replace_customized_ops(globals())`
   - `src/flag_gems/runtime/__init__.py:28-45`：`device.vendor != NVIDIA` 时，遍历
     `backend.get_current_device_extend_op(vendor_name)` 返回的算子，**覆盖 flag_gems 命名空间同名符号**
   - `src/flag_gems/runtime/backend/__init__.py:272-274`：收集 `_{vendor_name}.fused` 模块内全部函数
     （含 `_kunlunxin/fused/topk_softmax.py` 的 4 参版）
4. 容器实证：4.2.1rc0 安装版 `inspect.getsource(flag_gems.topk_softmax)` = 4 参（与 GitHub tag 一致）→ 探测方法正确性闭环。

插件调用点（容器内复核）：`/env/xvllm-plugin-FL/vllm_fl/ops/_fl_ops.py:22`
`topk_softmax(topk_weights, topk_indices, token_expert_indices, gating_output, renormalize=False)` → 5 参位置调用 `flag_gems.topk_softmax(...)`。

→ 结论：`GEMS_VENDOR=kunlunxin` 时插件 5 参调用 4 参实现，任何 5.x 版本（含 v5.3.4/v5.4.0.dev0）均必然 TypeError。

### 6.2 复测建议（按优先级）

1. **直接复测（必做，成本低）**：新线镜像（gems 5.0.0 / vllm 0.20.2）跑纯 MoE 四组配置。
   预期同一 TypeError；跑通则本预检有误（概率极低），跑崩则提供最新实证。
2. **临时包装探针（若需打通到 fused_experts）**：仅在测试环境，对 `flag_gems.topk_softmax`
   做 5 参→4 参适配包装（丢弃 renormalize，默认 False），取得 MoE 内核（fused_experts）首份数据。
   **标注为探针，不进交付路径**（指南 §三.7 原文）。
   - 风险低：kunlunxin kernel 恒「归一化后取 topk」（v5.0.0 L32-35 `probs = exp_vals / (sum+1e-8)`），
     即等价 renormalize=False 语义；补参后插件默认调用行为与现状一致。
3. **issue 提交（附最新 file:line）**：向智源/厂商提交时引用本预检证据——
   `_kunlunxin/fused/topk_softmax.py` v5.0.0 L56 / v5.3.4 L70 / v5.4.0.dev0 L70 均 4 参；
   建议补 `renormalize: bool = False` 参数并与通用版（fused/topk_softmax.py L84）对齐
   （通用版 kernel 已支持 `renormalize` 语义，kunlunxin kernel 可先透传/忽略）。
4. **昇腾对照**：通用实现恒为 5 参（v4.2.1rc0 L67 / v5.0.0 L70 / v5.3.4 L84），
   昇腾不受此阻塞（与[昆仑芯问题反馈清单-20260822.md](昆仑芯问题反馈清单-20260822.md)昇腾对照表一致）。
