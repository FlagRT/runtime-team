## #1【厂商 SDK · 高优】xpudnn::causal_conv1d_update ret=1 —— 混合注意力 MoE 模型默认模式必崩

- **现象**：Qwen3.6-35B-A3B（Qwen3_5MoeForConditionalGeneration，含 GDN 线性注意力层，omni 混合架构）
  默认模式（enforce_eager=False）引擎初始化 CUDA graph capture dummy run 阶段崩溃：
  `ValueError: Check 0 == ret failed, left operand=0, xpudnn::causal_conv1d_update failed, ret=1`
- **栈**：qwen3_5.py → qwen3_next.py layer.linear_attn → gdn_attention_core → qwen3_next.py:616
  → vllm_fl vendor/kunlunxin impl/causal_conv1d.py:136 → xtorch_ops.causal_conv1d_update（_fusion.py:879）→ xpudnn ret=1
- **enforce_eager 变通**：可跑完但输出乱码，伴随
  `Input tensor shape suggests potential format mismatch: seq_len (5) < num_heads (16)`（vendor attention 输入格式问题）
- **复现范围**：官方发布镜像（该镜像命名即此模型的 nomtp-kunlunxin 变体）与 dev 容器均复现；
  镜像同名模型 Qwen3.6-35B-A3B-nomtp-kunlunxin-FlagOS 默认模式同样崩溃。
- **归属判断**：xtorch_ops 0.1.2640 内 xpudnn 算子（C++ 库，与 triton 版本无关），两容器同版本同失败。
- **影响**：官方发布镜像与其模型命名不符——Qwen3.6-35B-A3B（含 nomtp 变体）在官方镜像内默认模式不可用，
  eager 输出不可用。建议：修复 xpudnn causal_conv1d_update（GDN/linear attention 路径）或补充 reference 回退。

## #2【FlagOS 组件 · 高优】flag_gems kunlunxin 后端 topk_softmax 缺 renormalize 参数 —— 纯 MoE 模型必崩

- **现象**：纯 MoE 模型 Qwen3-30B-A3B（Qwen3MoeForCausalLM，128 experts，标准 attention，无混合架构）
  默认模式与 enforce_eager 均在 profile_run（内存摸底 dummy run）阶段崩溃：
  `TypeError: topk_softmax() takes 4 positional arguments but 5 were given`
- **根因**（API 签名不匹配，官方镜像自带组合即存在）：
  - 插件 vllm-plugin-fl 0.1.0 `vllm_fl/ops/_fl_ops.py:22` 调用 `flag_gems.topk_softmax(topk_weights, topk_indices, token_expert_indices, gating_output, renormalize)` —— 5 参
  - flag_gems 4.2.1rc0 通用实现 `fused/topk_softmax.py:66` 含 renormalize —— 5 参 ✓
  - flag_gems 4.2.1rc0 **kunlunxin 后端** `runtime/backend/_kunlunxin/fused/topk_softmax.py:56` **缺 renormalize** —— 4 参 ✗
  - GEMS_VENDOR=kunlunxin 时解析到 4 参实现 → TypeError
- **无法绕过**：enforce_eager / USE_FLAGGEMS=0 / VLLM_FL_PREFER=vendor（官方脚本默认参数）均无效——
  插件 `FusedMoEFL.select_experts` 是 import 时对 vllm FusedMoE 的猴子补丁（layer.py:254），
  `_fl_ops.topk_softmax` 无条件调用 flag_gems。
- **复现范围**：官方发布镜像与 dev 容器（flag_gems 同 commit 73c5aff1）均复现，同一 TypeError 同一栈
  （dev 复验：pure_moe_dev_container.log，权重加载 13.37s 后 profile_run 崩溃）。
- **影响**：昆仑芯上所有标准 MoE 架构模型（Qwen3Moe/Qwen2Moe/Mixtral 等，走 vllm 原生实现 + 插件 fused_moe OOT）
  在引擎初始化即崩，MoE 路由 softmax 之后的 expert GEMM 内核从未被触达。
- **建议**：为 _kunlunxin 后端 topk_softmax 补齐 renormalize 参数（对齐通用版签名），或插件按 flag_gems 版本自适应。

## #3【FlagOS 组件 · 中优】vllm 0.13 与 triton 3.0.0 的小型不匹配

- `gpt_oss_triton_kernels_moe.py` 导入 `triton.language.target_info` 失败：
  `No module named 'triton.language.target_info'`（官方镜像 triton 3.0.0+03c4c9be；dev triton 3.6.0 无此报错）。
  当前为优雅降级（非致命），但说明 vllm 0.13 与官方镜像 triton 版本存在预期差。
- 官方镜像 triton `3.0.0+03c4c9be` ≠ backends.yaml 声明的 `triton==3.0.0+a48aedef`（同为 3.0.0，commit 不同）。
- 昆仑芯 vllm 0.13 构建必须依赖 vllm-plugin-FL 做平台引导：不带插件直接报
  `RuntimeError: Device string must not be empty`。建议文档明示「该构建为插件强依赖」。

## #4【FlagOS 组件 · 高优·新线镜像】flag_gems 5.0.0 `_moe_C::moe_align_block_size` 6 参 schema vs vllm 0.20.2 7 参调用

- **现象**（2026-08-22 新线镜像复测新增）：新线镜像（gems 5.0.0 + plugin 0.2.0 + vllm 0.20.2）下，
  使用旧线 env 口径 `VLLM_FL_PREFER=flagos|vendor` 时 `use_flaggems()`=False → fused_moe 落回 vllm 原生路径 →
  flag_gems 5.0.0 wheel 注册的 `_moe_C::moe_align_block_size` 为 **6 参 schema**（旧 vllm 签名），
  vllm 0.20.2 以 **7 参调用**（新增 `expert_map`）→ `RuntimeError`。
- **规避**：新线镜像必须用新口径 `VLLM_FL_PREFER=flagos`（单独值），`flagos|vendor` 组合在新线不可用。
- **影响**：新线镜像（0.20.2 线）与旧线（0.13 线）的 env 口径不兼容，文档未提示。
- **建议**：gems 5.0.0 补 7 参 schema，或 vllm 0.20.2 对旧 schema 做兼容。

## #5【厂商 SDK · 待查】纯 MoE eager 生成质量退化（expert GEMM 厂商内核正确性）

- **现象**（2026-08-22 新线镜像复测）：Qwen3-30B-A3B eager 模式 EXIT=0 完整跑通（3.2 tok/s），
  但首 token 正确（"Paris"/"John"）后退化为重复/乱码；expert GEMM 走厂商内核
  `_klx_fused_experts`（xtorch_ops 0.1.2935：gen_block_statistic→moe_pre_sorted→moe_fc×2→post）。
- **归属判断**：正确性未过关，候选原因（厂商内核精度/格式、reference.torch 回退路径、输入格式）未隔离，
  需进一步定位；MoE 路由（topk_softmax）经 dispatch 降级到 reference.torch 已确认不崩。
- **影响**：昆仑芯纯 MoE 从「初始化必崩」推进到「能生成但质量不可用」；默认模式另有 graph capture 35min 不可用问题。
