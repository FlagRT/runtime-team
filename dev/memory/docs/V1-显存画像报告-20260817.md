# 验证报告：V1 显存画像（2.4 任务 #1）

> 日期：2026-08-17 ｜ 环境：flagos-fl-dev-910c / venv311 / Qwen3-4B bf16 单卡（flagos:0）
> 脚本：benchmarks/v1_memory_profile.py ｜ 状态：🟡 **部分完成**（加载画像完整；长序列推理因性能问题未完成，本身即重大发现）

## 1. 结论摘要

1. **加载后显存结构清晰**：模型加载 + KV 预分配共 **31.89GiB**（24.6s），其中 KV cache 预分配 **170,224 tokens**（约 24.3GiB，占 76%）——**KV cache 是显存大头，分层缓存/可控溢出的主对象明确**。
2. **首次 attention 初始化 437s（7.3 分钟）**：每进程一次，短请求也躲不掉；之后短请求正常（kernel 热）。
3. **🔴 长序列 prefill 极慢（重大新发现）**：2048-token 输入 × 4 并发，22 分钟未完成首个请求 prefill（AICore 满载 91-100%，无死锁但每 token 秒级）。**阶段 4 只验证过 <64 token 短序列，长序列性能是未探索区**——这是运行时层当前最大的性能问题，也是 V2 显存池 A/B 对比的前置阻塞。
4. **画像方法限制**：vLLM EngineCore 是 spawn 子进程，主进程读不到 worker 的 allocator 统计（allocated/reserved 恒 0）→ 碎片/分配次数数据本次未取得，需 worker 内嵌采样或 npu-smi 连续采样（后续补）。

## 3. 重大发现与影响

### 3.1 🔴 长序列 prefill 极慢（P0 上报项）
- 现象：2048-token 输入 prefill 22 分钟未完成，AICore 满载但吞吐 ~0 token/s 级别
- 影响：
  - 阻塞 V2（开关 A/B 需要可测的吞吐对比）
  - 阻塞长序列场景（8k/32k 上下文）的任何评测
  - 与 2.4 直接相关：KV cache 是显存大头，但长序列跑不动 → 分层缓存收益无法在真实负载上验证
- 可能原因（待查）：flag_gems attention 长序列 kernel 未优化 / tiling 选择极差 / vLLM chunked prefill 与 FL 调度交互问题
- 建议：上报运行时组例会 + 与编译组/算子组联合定位（这是运行时问题反哺 8.5 的典型场景）

### 3.2 每次进程 7 分钟 attention 初始化
- 现象：任何新 vLLM 进程首次调用 attention 需 ~437s（短请求也要）
- 影响：调试/迭代成本高；**基准测试必须先预热**（已记入看板）
- 待查：是否可将初始化产物缓存（kernel/tune cache 落盘）

### 3.3 显存画像方法学
- 主进程拿不到 worker 统计 → V1 之后的画像建议：① worker 内嵌采样（在 vllm worker 里调 torch_fl.flagos.memory_stats 回传）；② 或 npu-smi 连续采样脚本（外挂）
- KV 预分配是整块一次性（vLLM 块表管理），激活走 torch_fl 缓存池（探针已证明复用良好）→ **碎片风险主要在激活区，KV 区无碎片问题**
