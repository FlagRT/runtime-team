> 容器：flagos-official-moe-recheck（官方发布镜像 qwen3.6-35b-a3b-nomtp-kunlunxin-gems_4.2.1rc0-vllm_0.13-plugin_0.1-cx_0.10.0-python_3.10.18-x86_64-driver_515.58:2604161518）

> 为昇腾侧同一套 vllm-plugin-FL 代码的 MoE 可达性提供参照。只测不修。

## D. 一句话判定（先给结论）

> **纯 MoE 也不可用，但失败点不在 MoE 路由/GEMM 内核，而在 FlagOS 组件层 API 不匹配：**
> Qwen3-30B-A3B（Qwen3MoeForCausalLM，128 experts 标准 attention）在官方发布镜像上，
> 默认模式与 enforce_eager 均在引擎初始化（profile_run 内存摸底 dummy run）阶段崩溃于
> `flag_gems.topk_softmax` —— 插件 vllm-plugin-fl 0.1.0 按 **5 参数**调用，
> 而 flag_gems 4.2.1rc0 的 **kunlunxin 后端实现只有 4 参数**（缺 `renormalize`），
> `TypeError: topk_softmax() takes 4 positional arguments but 5 were given`。
> **enforce_eager / USE_FLAGGEMS=0 / 官方脚本默认参数均无法绕过**（插件 `FusedMoEFL.select_experts`
> 是 import 时对 vllm FusedMoE 的猴子补丁，`_fl_ops.topk_softmax` 无条件调用 flag_gems）；
> 不带插件则 vllm 0.13 昆仑芯构建平台引导直接失败（`Device string must not be empty`）。
> 即：**昆仑芯 MoE 支持存在更广缺口** —— 混合架构 MoE 被厂商 xpudnn causal_conv1d_update 阻塞（前次结论），
> 纯 MoE 被 flag_gems kunlunxin 后端 topk_softmax 签名缺失阻塞（本次新发现，组件层，官方镜像自带组合即不匹配）。
> MoE 路由 softmax 之后的 expert GEMM（fused_experts）因 topk 先行崩溃**从未被触达**，昆仑芯 MoE 内核本身仍无数据。

## B. 四组运行结果（卡 2，模型 /workspace/models/Qwen3-30B-A3B，同 3 prompts / max_tokens=64 / temp=0）

| # | 配置 | 结果 |
|---|---|---|
| 1 | 默认模式，VLLM_FL_PREFER=flagos\|vendor，USE_FLAGGEMS=1（与前次测试完全一致） | ❌ EXIT=1：权重加载 14.02s → profile_run dummy run → layer0 MLP → experts → select_experts → `flag_gems.topk_softmax` TypeError（4 参 vs 5 参） |
| 2 | enforce_eager=True，其余同 #1（任务步骤 5 对照） | ❌ EXIT=1：**同一 TypeError 同一位置**（证明与 CUDA graph 无关，前向路径组件 bug） |
| 3 | 不带插件（VLLM_PLUGINS 置空，纯 vllm 原生） | ❌ EXIT=1：`RuntimeError: Device string must not be empty` —— 该 vllm 0.13 昆仑芯构建必须靠插件做 platform 引导 |
| 4 | 官方脚本默认参数（zhenghaojia Try1 脚本口径：USE_FLAGGEMS=0 + enforce_eager=True + prefer=vendor） | ❌ EXIT=1：**同一 TypeError**（fused_moe OOT 注册不随 USE_FLAGGEMS 关闭；仅 unquantized_fused_moe_method 被跳过，但 select_experts 猴子补丁仍在 → 同一 flag_gems 调用） |

### 失败栈（#1/#2/#4 完全一致）
```
vllm core._initialize_kv_caches → determine_available_memory → profile_run → _dummy_run
  → vllm/model_executor/models/qwen3_moe.py:199 self.experts(...)   ← FusedMoE (custom op)
  → fused_moe/layer.py moe_forward → forward_impl → quant_method.apply
  → UnquantizedFusedMoEMethod.forward_cuda → layer.select_experts
  → /env/xvllm-plugin-FL/vllm_fl/ops/fused_moe/fused_moe.py:35 vllm_topk_softmax
  → /env/xvllm-plugin-FL/vllm_fl/ops/_fl_ops.py:24  fl_ops.topk_softmax
  → flag_gems.topk_softmax(...)   ← 5 参
TypeError: topk_softmax() takes 4 positional arguments but 5 were given
```

### 根因（组件层 API 不匹配，官方镜像自带组合）
```
插件 vllm_fl/ops/_fl_ops.py:22  topk_softmax(topk_weights, topk_indices, token_expert_indices, gating_output, renormalize=False)  → 5 参
flag_gems 4.2.1rc0 通用实现  flag_gems/fused/topk_softmax.py:66   (topk_weights, topk_indices, token_expert_indices, gating_output, renormalize=False)  → 5 参 ✓
flag_gems 4.2.1rc0 kunlunxin 后端 flag_gems/runtime/backend/_kunlunxin/fused/topk_softmax.py:56  (topk_weights, topk_indices, token_expert_indices, gating_output)  → 4 参 ✗ 缺 renormalize
```
GEMS_VENDOR=kunlunxin 时 `flag_gems.topk_softmax` 解析到 _kunlunxin 4 参实现 → TypeError。
插件 0.1.0 按新版（≥5.x）签名编写，官方镜像却配 4.2.1rc0 → 该组合下纯 MoE 必崩。

## C. MoE 算子 dispatch 归属表（日志提取，任务步骤 4）

| 算子 | dispatch 归属 | 实测状态 |
|---|---|---|
| attention_backend | **vendor.kunlunxin**（KunlunxinAttentionBackend） | 初始化 OK（dummy run 前段 attention 层实际执行通过） |
| rms_norm / silu_and_mul / rotary_embedding | OOT 注册 flagos（flag_gems），vendor 备选 | dummy run 前段实际执行 OK |
| **fused_moe → router (topk_softmax)** | 插件 FusedMoEFL（OOT）→ **flag_gems kunlunxin** | ❌ TypeError（4 参 vs 5 参），profile_run 即崩 |
| fused_moe → expert GEMM (fused_experts) | 插件 fused_experts（未及确认内核来源） | ⚠️ 未触达（topk 先行崩溃） |

结论：昆仑芯纯 MoE 的**路由 softmax 步骤**被组件 API 不匹配阻塞，expert GEMM 内核路径无实测数据；
失败发生在引擎初始化阶段（未进入生成），不适用「乱码输出」类别（与混合模型 eager 乱码问题不同源）。
