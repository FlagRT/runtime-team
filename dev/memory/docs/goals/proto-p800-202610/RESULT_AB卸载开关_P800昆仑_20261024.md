> 状态：🟢 双腿全通（cost 无池压 6 跑 + expand 超池 2 跑），160/160 零失败。

> TP=1，gmu 0.8，`--kv-cache-memory-bytes 64GiB`（GPU 池 **466,032 tok** 两腿逐字一致），eager，max-model-len 4096，port 18307。
> A 腿 = `--kv-transfer-config` XpuSimpleCPUOffloadConnector，**kv_connector_module_path=`offload.xpu_offload`（memory-manager 新仓路径首次真机验证）**，Host 池 16 GiB，pinned。
> 卡：xpu5 独占（容器内 mem_get_info 真值 95.97/96 GiB free；xpu-smi 同期报 65GB/98%——再次实锤其双向不可信）。
> 原始数据：本地 `p800_results_1024/ab/`（43 文件：8 driver 日志 + 18 metrics 快照 + 8 summary + 4 serve 日志 + marker 5 件）。

## 0. 一句话结论

**真模型上，卸载不只是"能扩展容量"——在超池负载下把总完工时间缩短 38%，且无池压时零开销；冷跑对比被共享机噪声淹没（±70%），暖跑配对才是可信口径。**

## 1. cost 腿：无池压（16 并发 × 37,157 tok = 池 8%，预期"卸载有代价"）

| 引擎状态 | B（关） | A（开） | 判定 |
|---|---|---|---|
| 冷跑 | B1 **214.3s**（离群）/ B2 **111.4s** | A1 126.5s / A3 **179.6s** | 冷跑方差 111-214s（±70%），**不可用作对比**（共享机 CPU 噪声 + 首跑暖机混杂） |
| 暖跑 | B2w **40.4s**（TTFT p50 2.37s） | A2 55.3s（离群）/ A3w **39.4s**（TTFT p50 1.04s） | **40.4 vs 39.4s——零开销差**（A2 55.3 为噪声窗口离群） |

- token 真值六跑全等：prompt 33,061（均值 2066/req）+ 生成 4,096（16×256 整）——设计值与实测严丝合缝。
- 机制自洽：无池压 → 无驱逐 → 无 DMA → connector 只剩每步轻量检查 → 开/关无差是**应然**。
- **方法论沉淀：这台机器上 A/B 数字必须暖跑配对**（prompt 确定性 + prefix caching 使同引擎重放全命中，天然构成暖跑；跨引擎冷跑只配做 sanity 不配做结论）。

## 2. expand 腿：超池（160 并发 × 496,401 tok = 池的 106.4%）——主菜

| 项 | B（关） | A（开） | 差 |
|---|---|---|---|
| wall 总完工 | **2009.8s（33.5 min）** | **1246.2s（20.8 min）** | **A 快 38%** |
| e2e p50 | 1747.1s | 1215.1s | -30% |
| TTFT p50 / max | 568.9 / **1540.0s** | 453.3 / **1175.6s** | 长尾 -24% |
| decode 聚合峰值 | ~13 tok/s（84 running 时 8-13） | **124.3 tok/s**（155 running） | ~9× |
| 运行形态 | 容量排队：Running 封顶 ~84，Waiting>0（`waiting_by_reason=capacity`），0 驱逐 | **155-160 全量在跑**，Waiting=0 | Host 池吸收超池部分 |

两腿引擎史完全同位（都是 cost 冷跑→expand 冷跑），token 真值全等（464,401+32,000），池数字逐字一致——**38% 的差只能是"16 GiB Host 池把 30k 超池 token 吃进去了"这一件事**。

**DMA 实锤（真模型首次）**：`/tmp/w2x_marker_transfers.txt` 共 **656 store 事件**（单批最多 1,107 块）+ **2 次 load 事件**（189 块 + 1,107 块 Host→GPU 召回），pin 模式=pinned；跑毕 Host RSS 1.47 GB（完成即释放，无泄漏迹象）。marker 五件已备份 `ab/`。

## 3. 附带发现（独立于卸载，报 vendor/插件线）

1. **批量 decode 病态**：单流 13.8 tok/s（10-23 实测），但批量（16-160 并发）聚合吞吐反而低至个位数 tok/s——批量解码在该栈上是负扩展。B 腿尤其极端：池 100% 满时 decode 崩到 ~8 tok/s。这是插件/vendor 域问题（与 10-23 "72ms 固定开销主导"同族但更重）。
2. **prefix caching 重放效应**：确定性 prompt + 默认开 prefix caching → 同引擎第二跑 TTFT 从 70s 掉到 1-2s。做基准的人不知道这个会得出荒谬数字（10-23 的"4B 0.8 tok/s"共卡污染就是近亲）。
3. xpu-smi 第三次实锤双向不可信（报 65GB/98% vs 真值空卡）。

## 4. 结构性验证（搭车完成）

- `kv_connector_module_path=offload.xpu_offload`（memory-manager 仓新路径）在昆仑栈真模型上加载、注册（4 元组→8 条目，dedup 后 bpb=32768，cpu_blocks=4096）、swap 全通——**w2_xpu_offload → offload.xpu_offload 迁移零断链**。
- OneRec-8B 的 connector 注册面：n_entries=4（kv 元组数）→ 8 unique 条目；与 tiny 模型路径一致。

## 5. 局限

- expand 每腿 n=1（但单跑 21-33 分钟、差 763s，远超机器噪声量级）；cost 暖跑 n=2 per 侧。
- Host 池 16 GiB 是单点配置（≈+110k tok ≈ +25% 容量），未扫其他档位。
- "池满 decode 病态"的机制未拆（block manager 满载开销 / 内核路径切换），只报现象。
- 傍晚邻居上线潮未遇（xpu5 全程独占，16:55 收卡）。

## 6. 汇报口径（11 月计划"昆仑 P800 卸载开/关对照（真模型+A/B 数字）"就此收口）

真模型 OneRec-8B 上：无池压暖跑开/关无差（39.4 vs 40.4s）；负载超池 6.4% 时，16 GiB Host 池使总完工时间 **-38%**（33.5→20.8 min）、TTFT 长尾 -24%、656 次卸载 + 2 次召回 DMA 实锤、零失败零泄漏。代价面（带宽优化未做，逐块 copy_）在超池场景被排队收益覆盖，净收益为正。
