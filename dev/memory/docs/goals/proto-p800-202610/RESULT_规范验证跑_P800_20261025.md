## 3. B 档位（c=池 25/50/90/110%，prompt≈3968 tok，输出 128；第二轮为报告口径）

- **饱和悬崖确认**：c102（87%）聚合 90 tok/s 生龙活虎，c125（100%）崩到 11-13——
  "批量 decode 病态"精确定位为**池 100% 满载态**，与昨天 expand-B（160req/496k）
  同一机制。capW=121/125：满池时 121 个请求滞留 capacity 队列。
- 饱和档 OFF→ON 快 17%（昨日 38%）：差异来源=昨日 expand 为全新 prompt 冷缓存，
  今日 c125-r2 的池被自己第一轮的 prefix 缓存占满——cache 状态不同，驱逐形态不同。
  两轮都报，不挑数。
- **DMA（ON 窗口）**：846 store（中位 3 块/次、峰值单次 7040 块、合计 140,548 块）
  + 3 load（1,168 块）。注意：store 在 24% util 档也有发生——**该 connector 的 store
  策略是积极的（非满载也存）**，但代价面测不出来（c28/57/102 差值≈0）。
  规范"无驱逐则无 DMA"的假设需按此修正。
- 正确性：S2 ON r3/r4 输出 sha1 与 OFF 逐字一致（3618977dee）✓（ON r1/r2 不一致
  系 JIT 首跑数值漂移，warm 后收敛——记录为现象）；B 各档 sha 比对同轮 OFF=ON 一致。

## 4. 规范验收：本次跑抓出了什么（规范的价值证明）

| # | 事件 | 被什么抓住 | 规范修订 |

| 1 | S1 v1 三档 TTFT 全 0.1s——同 prompt 重放是 cache 命中不是 prefill | 实跑数字违背常识 → 溯因 | S1 判据补"每轮冷 prompt（轮次×档位唯一 i）" |
