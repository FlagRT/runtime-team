## 死点清单（按触发顺序）

**P-0 内存画像一致性断言（上游核心，环境级）**
`vllm/v1/worker/gpu_worker.py:412 assert init_snapshot.free_memory >= free_gpu_memory`
昆仑平台 profile 期间空闲显存上报**增加**（90.97→95.48 GiB，+4.5 GiB），核心防干扰检查炸。
修法（已验证可行）：`--kv-cache-memory-bytes <bytes>` 走 early-return，做完 profile（编译需要）但跳过断言。
注：此 knob 在 FL/910C 上曾挂死（profile_run 不返回），昆仑 profile 3.5 min 能跑完——同一开关两栈命运相反。

**P-1 流优先级不支持（connector 内部，代码雷）**
`vllm/v1/simple_kv_offload/worker.py:171 torch.cuda.Stream.priority_range()`
→ `RuntimeError: greatest_priority <= -1 INTERNAL ASSERT FAILED (C10 CUDAStream.h:188)`
昆仑 XMLIR 兼容层实现了 Stream 但无优先级语义。修法：外挂 connector（kv_connector_module_path）自定义 worker_handler，用普通 Stream（实测普通 `torch.cuda.Stream()` 创建成功）。

**P-2 copy backend 依赖 cuda-python（connector 内部，预测雷，未走到）**
`vllm/v1/simple_kv_offload/cuda_mem_ops.py` 需要 `from cuda import cuda`（cuda-python 包），镜像内未装（cupy-cuda12x 在但不含 cuda.bindings）。
修法：XpuCopyBackend 用 `copy_(non_blocking=True)` 替代 cuMemcpyBatchAsync——即 NpuDmaCopyBackend 模板原样移植。

## 通过项（正面证据，对照 910C）

1. **形状注册无死点**：910C 死点#1（vllm-ascend reshape 元组格式断言）在 vllm_fl/昆仑上不存在——kv_caches 直接过校验，走到 P-1 才死。
2. **host 池钉页已走通**：崩溃点在分配循环之后——`pin_tensor`（cudaHostRegister 路径）在昆仑上对 ~1 GiB host 池执行成功未炸。
3. **torch.cuda 兼容面实测**：`torch.cuda.is_available()=True`、设备计数正确、`pin_memory()`→is_pinned True、D2H `copy_(non_blocking)`+synchronize 全通、普通 Stream 全通。
4. **vllm_fl 0.2.0 完整支持 KV connector 注册框架**（traceback 经过其 worker initialize_from_config→register_kv_caches 链路，即昆仑走的是与 910C 同一套 vLLM 0.20.2 connector 机制）。

## 修法面（W2 移植工作量评估）

我们的 w2_npu_offload 模板（NpuDmaCopyBackend：普通流 + torch pin_memory + 逐块 copy_ non_blocking + Event 上报）
在 P800 上几乎原样适用，差异仅两处：**不用 priority_range**（P-1）、**不用 cuda-python**（P-2）——这两点恰是 910C 版已经绕开的东西。

先决：`--kv-cache-memory-bytes` 必带（P-0），否则启动期必炸。

## 补测（同夜 phase 2）：基线实测 + P-1 绕过验证 + P-2 实锤

**基线（无卸载，--kv-cache-memory-bytes 40G，xpu0）**：启动 ~1 min（编译缓存热时；冷 ~3.5 min）；冒烟 8 请求×32tok：
稳态 **0.37 s/请求 ≈ 86 tok/s**（首请求 6.9 s = 懒初始化），延迟稳定、无 NaN（昆仑 decode-NaN patch 在位）；
KV 池 40 GiB = **20,971,520 tokens（2 KiB/token）**，等效并发 40960×。栈本身健康可跑。

**P-1 绕过验证 ✅**：monkeypatch `torch.cuda.Stream.priority_range = lambda: (0,0)` 有效。机制要点：
vLLM V1 引擎核心是 **spawn 子进程，会以 `__mp_main__` 重 import 父入口脚本**——补丁必须放顶层（才能带进子进程），
入口必须加 `if __name__ == '__main__'` 保护（否则子进程递归 main()，双双互踩崩溃，首翻车点）。

**P-2 实锤 ✅（stock 路线终点）**：补丁后引擎越过 priority_range，走到
`worker.py:176 → copy_backend.py:46 init → build_params → cuda_mem_ops.py:60 _resolve_batch_memcpy → from cuda.bindings import driver` →
`ModuleNotFoundError: No module named 'cuda'`。注意昆仑的 `xpytorch_import_hook` 会拦截 import 也变不出 cuda 模块。
**至此死点地图全部实弹闭环：P-0/P-1 有旁路，P-2 只能换后端 = 恰是 w2_npu_offload 模板的定义域。**

**K>G 几何已备好未用**：w2 配置 GPU 池 2 GiB（1,048,576 tok / 2048× 并发）+ Host 池 4 GiB = 2×GPU，
死于 P-2 未到服务态；适配器到位后此配置即可直接跑召回实验。

**新增运维事实**：①共享卡实时性——xpu0 在我们两轮实验之间被邻居吃到 46.6 GiB（早上上线潮），换 xpu1 继续；
**占卡窗口要趁早、中段要复查 xpu-smi**。②vllm_fl worker 自带 gmu-vs-free 启动闸（worker.py:415，报错清晰非崩溃，ascend worker 无此闸）。
③容器重建丢 inductor JIT 缓存（冷启动 ~3.5 min vs 热 ~1 min）——非必要不重建容器。
④服务日志时区=容器内本地时（UTC+8 与宿主一致，与 910C 容器 UTC 不同）。

**下一步（W2-P800，可离线开工）**：移植 XpuCopyBackend（torch copy_ non_blocking + 普通 Stream + torch pin_memory，
对外仍以 kv_connector_module_path 外挂加载；stock 路线差的那一环就是它），再占卡即可跑通"卸载全链 + 小池召回"。

**运维大事记（这轮的核心教训）**：

## 补测 3（同日 17:08-17:27）：OneRec-8B 补测成功（xpu5，基本干净）

## 补测 4（同日 17:31-17:48）：Qwen3-4B 独占卡复测——13.4 tok/s，上午 0.8 实锤为共卡污染

同法同配置（xpu5 独占，40G 池 → 池结算与上午分毫不差：291,264 tok / 71.11×；gmu 闸过 free 94.3）：

| | 上午（xpu1 共卡） | 傍晚（xpu5 独占） |
|---|---|---|
| 单请求 p50 | ~40 s（0.6-0.8 tok/s） | **2.391 s（13.4 tok/s）** |
| 逐请求漂移 | 有干扰 | **2.385-2.408 s 零漂移** |
| prefix cache | 78-84% | 84.4%（同） |

测后驱动 free 42.4G = 引擎自占（8G 权重 + 40G 池 + ~4G 开销）自洽，无邻居。**卡已还。**

**关键推论**：①上午 0.8 tok/s 确系共卡污染（17 倍差），P800 汇报一律以独占数为准；
②4B 独占 13.4 ≈ 8B OneRec 独占 13.8，两者同为 ~72 ms/step——参数量翻倍速度不变，说明**解码步耗时被固定开销主导**

**结论：0.20.2 代昆仑线的可用级速度 ~13.5 tok/s（单流），decode 结构性慢是插件/vendor 内核问题（非我方适配域），记录待上游；我方卸载 A/B 以此为基线锚。**
