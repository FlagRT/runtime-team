# P800 规范验证跑 · 大白话版（2026-10-25）

> 技术版在 `RESULT_规范验证跑_P800_20261025.md`；本文给不想啃术语的读者。
> 看不懂哪里 = 文档的 bug，请直接指出。

## 一、今天干了什么（一句话）

把昨天写的《显存测定规范》在 P800 上从头到尾跑了一遍。两个目的：
测出真实数据 + 检验规范能不能挡住"测了跟没测一样"的垃圾数字。
结果：数据齐了，规范也当场拦下了三批坏数字（见第四节）。

## 二、测试对象（先摆清谁、哪台、哪张卡、什么栈）

- 机器：P800 服务器，第 5 张卡（独占使用，前后都用驱动真值确认过是空卡）
- 模型：OneRec-8B（约 15.6 GiB）
- 栈：昆仑芯 P800 上的 vLLM + FlagRT 插件（vllm-plugin-fl 0.2.0）
- 对照开关：**KV 卸载**。开了之后，显存"草稿纸"装不下的内容可以搬到内存暂存，要用时再搬回来。

## 三、测了什么、测出什么

### ① 草稿纸多大（池画像）

模型处理每个请求都要在显存里记"笔记"（KV）。实测这张卡的笔记容量：
**466,032 个 token**。后面所有负载都按这个数来设计——这就是规范里
"池画像是一切测试的分母"的意思。

### ② 一个请求单独跑多快（单流）

| 阶段 | 大白话 | 实测 | 开卸载后 |
|---|---|---|---|
| prefill | 读题（把你输入的内容读一遍） | 每秒约 400-480 个 token | **逐毫秒一致** |
| decode | 写答案（一个字一个字往外蹦） | **每秒 13.9 个 token** | 13.7（差 1%，等于没差） |

这两个数和 10 月 23 日测的完全对上——跨两天、两次开机复现，数字可信。

### ③ 很多人同时请求会怎样（并发档位，今天的主菜）

按草稿纸容量算出四档"同时来多少人"：28 / 57 / 102 / 125 路
（分别用掉池子的 25% / 50% / 90% / 103%——最后一档是故意超载）。

| 同时请求数 | 池子用量 | 全部完成的耗时 | 状态 |
|---|---|---|---|
| 28 路 | 24% | 43 秒 | 轻松 |
| 57 路 | 49% | 84 秒 | 轻松 |
| 102 路 | 87% | 145 秒 | 正常（每秒还能出 90 个 token） |
| **125 路** | **100%** | **1452 秒（24 分钟！）** | **崩了：121/125 个请求在排队，速度掉到 1/8** |

**关键发现：崩的原因不是"人多"，是"草稿纸写满了"。**
102 路比 125 路人只少两成，却快 10 倍——问题出在池子 100% 满载这个状态本身。
以后把这个问题报给厂商时，可以附上精确的复现条件（池打满即崩）。

### ④ 卸载开关对照（收口数据）

- **池没用满时（前三档）**：开和关完全没区别。符合预期——没超载就没必要搬数据。
- **超载时（125 路）**：开卸载 **快 17%**（24 分钟 → 20 分钟），
  全程实测 846 次"搬到内存"的动作（单次最多 7,040 块），搬运证据确凿。
- 顺便修正昨天的 38%：昨天的题全是新题（冷缓存），今天第二轮池子里
  塞满了自己第一轮的缓存——局面不同，卸载赚的幅度不同。**两个数都对，都如实记录。**

### ④½ 卸载性能总表（开/关对照，暖跑第二轮）

| 测试 | 关 | 开 | 差异 | 怎么理解 |
|---|---|---|---|---|
| 读题 257 tok | 0.62 s | 0.62 s | 0 | 没超载，卸载完全不掺和 |
| 读题 1024 tok | 2.18 s | 2.17 s | 0 | 同上 |
| 读题 3072 tok | 6.35 s | 6.33 s | 0 | 同上 |
| 写答案（单流） | 13.90 tok/s | 13.74 tok/s | −1.2% | 每步多一次"要不要搬"的检查，几乎白送 |
| 28 路并发（池 24%） | 43.0 s | 43.2 s | 0 | 池子没满，没有搬运发生 |
| 57 路并发（池 49%） | 84.1 s | 84.7 s | +0.7% | 同上 |
| 102 路并发（池 87%） | 145.4 s | 149.2 s | +2.6% | 接近满但还没满，仍无代价 |
| **125 路并发（池 100%）** | **1452 s** | **1209 s** | **快 17%** | 唯一超载档：池装不下，卸载把装不下的搬去内存 |
| └ 125 路排队请求 | 121 个 | 121 个 | 持平 | 满载态排队照旧，但搬走后处理更快 |
| └ 吞吐 | 11.0 tok/s | 13.2 tok/s | +20% | 崖底抬升 |
| └ 最长等待 | 1298 s | 1163 s | −10% | 长尾收窄 |

搬运实锤（只在"开"的一侧）：846 次搬出 + 3 次搬回，单次最多 7,040 块。
答案正确性：同题同设置，开/关输出逐字一致。

一句话读表：**前 7 行是"代价账"——全是零或接近零；最后 1 行是"收益账"——
只在池子真装不下时出现（+17%）。** 这正是规范 cost/expand 两级设计的效果：
代价和收益分开测，谁也糊弄不了谁。

### 正确性检查（开卸载会不会算错）

同样的题、同样的设置，开和关的输出**逐字一致**（warm 状态下）。
开卸载不改变答案。✓

## 四、规范自己被抓出的 4 个问题（今天最有价值的部分）

1. **假 prefill**：测读题速度时三轮用了同一道题，第 2、3 轮 0.1 秒"完成"——
   那是查缓存，不是真读题。数字漂亮但全是假的。
   → 修：每轮必须换新题。
2. **腿序**：测完超载实验立刻回头测读题，机器还没从满载里缓过来，
   测出"256 token 反而比 1024 token 慢 4 倍"的鬼数字。
   → 修：轻的先测、重的后测，顺序写进规范。
3. **压线翻车**：题目长度正好顶着上限，28 路里 19 个请求直接被拒
   （题目里注入的编号多一位就超了）。
   → 修：题目长度留 128 token 余量。
4. **假设被推翻**：规范原来写"没超载就不会发生搬运"，
   实测 24% 用量时搬运也在发生（只是不拖慢速度）。
   → 修：判据从"没有搬运"改成"没有代价"。

## 四½、910C 也跑了一遍（同一天下午，跨芯验证）

同一个规范、同一套探针，换到 910C（昇腾 davinci4，vllm-ascend 栈）零修改照跑：

| 测试 | P800（昆仑） | 910C（昇腾） |
|---|---|---|
| 读题速度 | 每秒 480 token | **每秒 13,300 token（快 28 倍）** |
| 写答案（单流） | 13.9 tok/s | **26.0 tok/s** |
| 卸载代价（单流） | −1.2% | −3.2% |
| 卸载代价（批量未满载） | ≈0 | **−20%（昇腾上卸载插件更贵）** |
| 池满载悬崖 | 崩 8 倍 | 只降 3 倍（温和得多） |
| 输出正确性 | 逐字一致 | 逐字一致 |

两个新认识：①"池满崩 8 倍"是昆仑栈特有的病，昇腾没有；②卸载插件的两个移植版
代价形态不同（昆仑零代价、昇腾未满载时要贵 20%）——**同一份代码在不同芯片上
表现不同，汇报必须按栈分开**，这正是规范"数字五要素"要防的事。

技术版：`RESULT_规范验证跑_910C_20261025.md`。

## 五、一句话结论（可汇报口径）

昆仑 P800 栈：单流 13.9 tok/s 可用级；池没满时多快好省且卸载零代价；
**池打满 100% 是明确的性能悬崖**（速度掉 1/8、请求大量排队）；
开 16 GiB 卸载在超载场景快 17%，搬运证据确凿，不改变输出正确性。
