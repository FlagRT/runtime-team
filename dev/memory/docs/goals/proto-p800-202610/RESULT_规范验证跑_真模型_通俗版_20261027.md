## 一、今天干了什么

10-27 深夜到 10-28，我们在昆仑芯 P800 上把**国产真模型 OneRec-8B** 从头到尾测了一遍。这次跑和以往有四点不一样，也都是预先写进计划、跑完不改的：

1. **换了真模型**：不再用小模型试跑，就是国产 8B 真模型（多模型系列的第一轮）。
2. **换了新代码仓**：显存搬运插件的代码从容器内旧地址换成新挂载的代码仓（`/work/memory-manager`）。旧数字一律不作数，全部重测。
3. **池子测了两个档**：一个是照抄上次先例的「64GiB 锁定档」（方便和上次对数，看换仓后有没有跑偏）；一个是「自然池档」（不手动锁定，按部署默认设置，看用户实际拿到多大池、什么性能）。
4. **补测了「往回搬」的路径**：以前的测试只看到数据搬出去（store），很少看到搬回来（load）。这次专门加了 L 腿，把搬回来的动作第一次测成了有效测量。

每个档各跑 8 条测试腿：P 池画像 → S1 首字延迟 → S2 吐字速度 → B 四档并发 → cost（半载代价）→ expand（超载收益）→ L（load 回迁）→ R（正确性）。跑完卡已还、服务器状态恢复（记录卡归还，系运行所有者声明）。

| **冷暖纪律** | 暖跑配对（先热身再计时，冷跑只当检查；测量规范凭证：冷跑抖动可达 ±70%） |

**名词大白话**（后文反复用到）：

- **KV cache（显存池）**：模型同时接待很多人时，每个人占一份「草稿本」显存。池多大，决定了最多能同时服务多少路。
- **卸载 / ON**：显存池放不下时，把暂时不用的草稿本搬到主机内存，腾出显存接更多路；**DMA** 就是搬运动作的计数（每一批一行账）。
- **store / load**：搬出去（显存→内存）/ 搬回来（内存→显存）。
- **TTFT（首字延迟）**：从提问到吐出第一个字的时间。
- **decode tok/s（吐字速度）**：每秒吐多少个字（token，字元）。
- **capW（排队数）**：池满时排着队进不来的请求数；**preempt（驱逐）**：已进去的被赶出来重排。
- **util（池利用率）**：草稿本用了几成。

## 三、数字大白话（+表）

### 3.1 64GiB 锁定档（和 10-25 先例同一配置，专门用来对数）

**池有多大**：草稿本 **466,032 个字元**（引擎日志原文行，逐字同 10-25 先例 → **换新代码仓零漂移**，这是本次第一发现）。每字元占 147,456.56 字节 ≈144KiB；理论最多 **113.78 路**并发（466,032÷4096）。跑完稳态还剩 9.72–9.88 GiB / 96 GiB。

**单流体感（1 个人用）**：

| 测什么 | OFF（不开卸载） | ON（开卸载） | 大白话 |
|---|---|---|---|
| 首字延迟 S1（暖轮，短/中/长输入） | 0.63–0.64 / 2.18–2.19 / 6.33–6.37 s | 0.62–0.64 / 2.17–2.18 / 6.35–6.37 s | 开关**毫秒级一样**，体感无差 |
| 吐字速度 S2（512 字长答） | 中位 **14.09**、最差 14.02 字/秒 | 中位 **13.69**、最差 13.67 字/秒 | 开关差 **−2.8%**（精确 −2.84%），ON 略慢但同量级 |

**多人并发（B 四档，路数按池子算出来，不拍脑袋）**：28 / 57 / 102 / 125 路。池利用率峰值 23.8% / 48.5% / 86.9% / 100%。总完成时间（wall）：OFF 41.9 / 77.9 / 138.7 / **1381.1** 秒，ON 42.5 / 77.7 / 140.1 / **1229.0** 秒。**悬崖复现**：102 路时大家合起来还能吐 ~93 字/秒，125 路直接崩到 12–13 字/秒——超载就是不行，哪个开关都救不了吞吐。

**半载代价（cost）**：28 路差 +1.4%、57 路差 −0.3% → **开着卸载不花钱**（判定=无代价；搬运器半载时也在偷偷搬运，ON 侧 28 路就有 7 批、57 路 36 批 store，但不影响速度）。

**超载收益（expand，125 路=池的 110%）**：OFF 排队 120 人、ON 排队也是 120 人——卸载**没有**消灭排队；但总完成时间 ON 快 **11.0%**（1229.0 vs 1381.1 秒）。收益=每人早做完，不是队伍变短。上次先例是快 17%（1209.1 vs 1451.7 秒、排队 121 人），本次快 11.0%——先后两跑同一个形态（凌晨第一遍全链跑（pass1）的 ON 引擎完工 1207.1 秒、排队 121 人，与先例 1209.1 秒、121 人几乎一样；该遍的对照批因共卡污染判废，单独的收益百分数无法干净配对，不引用）。

**搬运账（全链）**：store 1,247 批/202,388 块 + load 6 批/2,135 块（store/load 分开记，1,253 行账闭合无差）；OFF 引擎 0/0+0/0（没装搬运器就零搬运，对称核对通过）。上次「几乎只搬出、不搬回」的缺口，这次 L 腿测到 load 3 批/964 块>0：搬回路径第一次测成。

**对照先例（仅本档）**：单流吐字 OFF 14.09 vs 先例 13.90（+1.4%，量级复现）；悬崖与超载收益形态同先例；本次 OFF 引擎暖身轮（r1，即 S2 腿「暖 1 测 3」里不计成绩的第 1 轮）的标准输出与先例一字不差（canonical 同值）。

### 3.2 自然池档（部署默认设置，用户真实拿到的）

**池有多大**：不手动锁定时，引擎自己分出 **403,712**（ON）/ **403,936**（OFF）个字元——比锁定档小 13.4%（在预设的 15% 线内，所以不加测中间档）；理论上限 98.56/98.62 路。跑完稳态剩 18.38–18.41 GiB / 96 GiB。

**单流体感**：首字延迟暖轮 0.61–0.64 / 2.16–2.17 / 6.32–6.38 s，双引擎 9 组输出全部一字不差；吐字速度 OFF 中位 **13.30**（最差 13.28）、ON **13.59**（最差 13.47）字/秒，开关差 +2.2%（这次 ON 反而略快）。

**多人并发**：25 / 49 / 89 / 108 路（按本档池子重新推导）。第一轮都有「冷启动卡顿」（排队 21/21/37/16 人，首形状 JIT——引擎头回见到这种输入形状要现场编译，预期内现象，第二轮消失）。第二轮总完成时间：OFF 44.7 / 73.9 / 127.2 / **1062.9** 秒，ON 39.4 / 69.8 / 123.1 / **1069.0** 秒。108 路（池的 110%）排队 104 人、驱逐 5 次，两引擎一样满载。悬崖同样复现：89 路 ~90+ 字/秒 → 108 路 12.9–13.0 字/秒。

**半载代价（cost）**：25/49 路四组配对，ON 3 快 1 慢（−0.7% 到 −11.9% 来回摆）→ 短腿噪声主导，**无单向代价**，结论比锁定档还干净。

**超载收益（expand，108 路）**：OFF 1062.9 vs ON 1069.0 秒，差 **+0.6%** → **自然档下卸载没有完工收益**（排队一样 104 人，搬运来回的工夫和省下的排队互相抵消）。注意：这是本档内的差分结论；两档池子不同，绝对数不能跨档横比（见 §五表格说明）。

**搬运账（全链，从零起账逐行核）**：store 1,187 批/175,149 块 + load 8 批/1,965 块（1,195 行账无断点）；OFF 引擎 0/0。半载 49 路就有 31 批 store——搬运器确实勤快，但没拖慢人。

**L / R 两腿：测了，按预先写定的判据记无效**（两档同判）：搬回路径的功能和代价都测到了（锁定档 load 3 批/964 块、重放代价 ±0.4%≈0；自然档 load 4 批/911 块、代价均值 −4.8%≈0），但「重放输出与首次输出逐字全等」这条**没过**——125 路批里最多 111 个全等（111/125），自然档 100/108。查下来是这版栈在**批量状态下**本来就有「首个字在空格和数字之间二选一」的抖动（锁定档单流也偶发：S1 十八份输出跨引擎配对 6/9 全等，3 对不一致均在 1024/3072 档），批量越大抖得越多，且**不开卸载的引擎也一样抖**（跨引擎不一致率≈同引擎重跑不一致率），**不是搬运器引起的**。判据是跑前写死的，不过就是不过，如实记无效，不修判据。取消测试（cancel）倒是两档四引擎全过：掐断后显存精确归位（ON 9.74→9.74、OFF 9.87→9.87；自然档 ON 18.28→18.28、OFF 18.40→18.40 GiB），后续请求正常。

## 四、抓出的问题

1. **共卡污染一次（已抓出并判废）**：锁定档 OFF 第一次跑（pass1）时邻居上了卡，吐字速度掉到 1.71 字/秒（正常 ~14）——全批数据判废、单独存档不入正文，等邻居退场后重跑（pass2）拿到干净数。**教训再次验证：测前测后各记一次邻卡状态是保命的**。
2. **xpu-smi 不可信（老病复发）**：它报显存 0 MiB 时真值（容器内驱动查询）占用 ~86 GiB（=96.00−9.88，与技术版 §2.1 稳态值同源）。判空闲/占用只认容器内 mem_get_info。
3. **器件 bug 一次**：锁定档 pass1 的 host 内存（RSS）采样解析挂了，为补齐判据件重跑 ON pass2（引擎史重置，操作层已声明）。自然档的测试脚本已自带该器件。
4. **批量态数字翻转（本轮最重要的新发现）**：批越大，输出「首个字是 7 还是空格」这类边缘数字越容易抖，且**开不开卸载都抖**（同引擎重跑也抖）→ L/R 两腿按预注册判据记无效。单流（1 个人）则 9 组输出全部逐字全等——问题只在批量态。
5. **记录间小笔误（已更正）**：锚点文档与汇总记录对 L 腿全等率的记法不一致（110 与 104 之差、分母写法）；以原始 JSON+重算为准（最大 111/125），已写进技术版更正注。G6 第 1 轮还更正了通俗/技术版共用的开关差数字（−2.9% → −2.8%，精确 −2.84%）。
6. **两个与预期不符、如实记录的结果**：① 自然档 110% 超载**没有**完工收益（锁定档有 −11.0%）——「卸载有收益」不是无条件成立，取决于档位；② 本次单流开关差 −2.8%，大于先例的 ≤1.2% 口径——不修饰，照记。
7. **占坑提醒**：锚点记录 xpu5 上有 8 个休眠容器挂载占坑（占坑不活跃），邻居随时可能上线污染——下一轮测前照旧先查卡。

## 五、一句话结论 + 跨档对照表

**一句话结论**：换新代码仓后引擎行为零漂移（池 466,032 与先例逐字一致）；显存卸载**满载超载时是真收益**（锁定档完工快 11.0%，形态与先例一致）、**半载以内零代价**，但在自然部署池的 110% 档收益消失（+0.6%）；正确性上批量态有与卸载无关的数字翻转，L/R 两腿按预注册判据如实记无效；单流体感两档两开关都在可用区间（吐字 13–14 字/秒；首字：短输入约 0.6 秒、中等输入约 2 秒、长输入约 6 秒）。
