## 0. 结论摘要（一屏）

**2.4 显存与缓存管理的"调研验证"阶段已完成，工程起点定稿，进入开发期。** 定稿时的关键事实：

- ✅ **显存池第一层已验证**：torch_fl caching allocator（块复用/切分/相邻合并/stream 安全/OOM 重试/统计）实测通过——默认开启、接口齐全、随机尺寸抖动碎片冗余仅 4.9%（探针实测，2026-08-17）。动态缓存池无需改造。
- ✅ **显存结构画像完成**：Qwen3-4B 单卡加载 31.89GiB / 24.6s，其中 **KV cache 预分配 ~24.3GiB（占 76%）**，170,224 tokens——**分层缓存/可控溢出的主对象就是 KV**。
- ✅ **vLLM 分层/溢出机制调研完成**：offloader 双后端（UVA/prefetch）抽象 + `evict_blocks` 挂载点 + flagcx_connector 连接器模式——子项 B 有现成设计骨架。
- 🔴 **P0：长序列 prefill 极慢（开发期第一主线）**：2048-token 输入 22 分钟未完成 prefill（AICore 满载，每 token 秒级）——阶段 4 只验证过短序列，长序列是未探索区。定位+修复需跨组（运行时/编译/算子）。
- ❌ **"依据执行计划复用显存块"未做**：子项 A 的静态规划部分，依赖编译组执行计划接口确认（问询文档已备，待发出）。
- ❌ **分层缓存与可控溢出（Host/Device/SSD）未开发**：子项 B 待开发（V3 原型可并行启动，不受 P0 阻塞）。

**开发期主线（排序）：① P0 长序列 prefill 定位修复（跨组，阻塞 V2 与长场景评测）→ ② V3 分层缓存原型（KV Host 溢出，并行线）→ ③ V2 显存池 A/B（P0 解决后）→ ④ V4 SSD 评估（随时）→ ⑤ 执行计划感知分配（编译组接口确认后）。**

### 1.2 显存相关已有资产（本次盘点重点）

**① torch_fl CachingDeviceAllocator —— 显存池第一层（动态缓存分配器）**
源码位置（宿主 `workspace/PyTorch-Plugin-FL/`）：
- `csrc/runtime/allocator/caching_device_allocator.h:30-122` — 类定义。能力：per-device 空闲块池（大/小分池，h:63-64）、按需切分 `try_split_block`（h:90）、相邻块合并 `try_merge_blocks`（h:93）、stream 事件延迟释放 `record_stream`/`process_events`（h:48/99）、OOM 时释放缓存块重试 `release_cached_blocks`（h:96）、统计 `AllocatorStats`（h:51）。
- `csrc/runtime/allocator/caching_device_allocator.cc:39-41` — 开关：环境变量 `FLAGOS_USE_CACHING_ALLOCATOR`。
- `csrc/runtime/device_allocator.cc:13-21,40` — 已注册为 PrivateUse1 默认分配器（开关开启时走 caching，否则 passthrough）。
- `csrc/runtime/allocator/backends/ascend_memory.h:17-116` — 底层封装 aclrtMalloc/Free、memcpy、event（走 ACL_HBM_MEM，h:55）。

大白话：这就是一个"PyTorch CUDA caching allocator 的简化版"——分配过的块不急着还给设备，先放池子里复用，省去反复向 CANN 申请/释放的开销；块太大就切开用，释放了就和邻居合并，减轻碎片；跨 stream 使用时用事件保证安全。**但它不感知执行计划，也没有碎片整理/统计可视化，更没有任何分层概念。**

**② vLLM 的 KV Cache 管理 —— 已在闭环中工作**
vLLM 0.20.2 自带：KV Cache 按块（block）预分配（块表 BlockTable）、prefix caching（前缀复用）、chunked prefill。在 FL 链路上，KV Cache 是整块 tensor 从 torch_fl 分配器拿内存，块级复用是 vLLM 自己的逻辑。**这块不重复造轮子，显存优化要围绕它做文章**（它是最大的"可溢出"候选）。

**③ vllm-plugin-FL 分布式 KV 传输连接器**
`vllm_fl/distributed/kv_transfer/flagcx_connector.py` — 基于 vLLM 的 KVConnectorBase_V1 接口 + FlagCX 实现跨机 KV 传输。说明插件侧已经预留了 KV 相关的挂载点（对接 2.4 分层缓存时可以借道）。

**④ CANN 9.0.0 接口事实（已核实）**
容器内 `/usr/local/Ascend/ascend-toolkit/latest/include/acl/acl_rt.h`：
- `aclrtMallocCached`（行 1668）— 多 stream 场景的缓存分配接口；
- `aclrtMallocWithCfg`（行 ~1695）— 带配置分配；
- **无独立的 MemPool 创建/管理 API**（grep 无结果）。
→ 结论：显存池必须自研（torch_fl 已有雏形），或评估 `aclrtMallocCached` 是否够用。

## 2. 差距分析（对照 2.4 两个子项）

| 子项 | 目标 | 已有 | 缺口 |
|---|---|---|---|
| **显存池与分层缓存** | 依据执行计划复用显存块并回收碎片，降低峰值显存和频繁分配开销 | 动态缓存池（复用/合并/stream 安全/OOM 重试/统计）；KV 块级管理（vLLM） | ① **执行计划感知的静态规划**（编译层计划 → 预分配/复用决策）② 碎片与分配开销的**实测数据**（从未量化过）③ 碎片整理与可视化诊断 |
| **分层缓存与可控溢出** | Host/Device/SSD 分层存储、按需释放与低优先级张量可控溢出 | 无（vllm-plugin-FL 有跨机 KV 传输连接器，可借道） | ① **优先级语义**（哪些张量算"低优先级"——KV cache 块是最现实候选）② Host 层（pinned 内存暂存、按需释放）③ SSD 层（NVMe 评估未做）④ 淘汰策略 + 异步拷贝 + 一致性 |

**原则提醒**（来自《开展计划》阶段4 第 7 步与 8.5 节）：显存管理**不预实现**，按实际 OOM/碎片问题逐步接入。所以 V1 画像（§4）是必经第一步——先证明问题存在、量化问题大小，再决定投入。
