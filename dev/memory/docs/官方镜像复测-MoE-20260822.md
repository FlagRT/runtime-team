## D. 一句话判定（先给结论）

> **真实缺口。** 官方发布镜像（triton 3.0.0 栈）上默认模式在 CUDA graph capture 阶段同样复现
> `xpudnn::causal_conv1d_update failed, ret=1` 硬失败（与 dev 容器同栈同错误）；
> enforce_eager=True 同样跑完但输出乱码 + `seq_len (5) < num_heads (16)` format mismatch 警告
> （输出与 dev 容器逐字节一致）。昨日失败**不能**归因于 dev 容器 triton 版本偏差；
> 阻塞项 #2 归属保持「厂商 SDK」（xtorch_ops/xpudnn 算子缺口），且官方发布镜像与其模型命名
> 不符——镜像连自己命名的模型（Qwen3.6-35B-A3B-nomtp-kunlunxin-FlagOS）默认模式都跑不通，
> 值得向智源（BAAI）反馈。

| 组件 | dev（flagos-fl-dev-p800） | 官方发布镜像 :2604161518 | 差异 |

| flag_gems | 4.2.1rc0 @73c5aff1（editable /env/FlagGems） | 4.2.1rc0 @73c5aff1（editable /env/FlagGems） | 无 |

| flagcx | 0.10.0 | 0.10.0 | 无 |
| **xtorch_ops**（失败算子所在库） | 0.1.2640+9bc36a18 | 0.1.2640+9bc36a18 | **无** |

**结论**：失败路径（vendor xpudnn causal_conv1d_update）涉及的 xtorch_ops/xmlir/torch_plugin
两容器完全同版本；triton 3.6.0 vs 3.0.0 差异与此算子无关（该算子走 xtorch_ops C++ 库，不经 triton）。
→ 昨日失败非环境偏差。

## C. 官方脚本/参数记录（任务步骤 2）

镜像内发现：
1. **官方示例脚本** `/env/xvllm-plugin-FL/examples/qwen3_5_offline_inference.py`：
   - `enforce_eager=False`（**默认模式即官方意图**，示例未设 eager）
   - `tensor_parallel_size=8, pipeline_parallel_size=2`（针对 Qwen3.5-397B-A17B 示例；35B-A3B 单卡 96GB 可容纳，本测沿用昨日 TP=1）
   - 唯一特殊环境变量：`VLLM_ALLOW_LONG_MAX_MODEL_LEN=1`
   - 采样：max_tokens=10, temperature=0.0
2. 镜像内**无**该模型的专用 README/启动脚本；`kunlunxin_example/README.md` 为昆仑芯通用 docker 部署说明（百度 iregistry 镜像 + 设备挂载），与模型无关。
3. 插件 `kunlunxin.yaml`（官方与 dev 相同）：prefer=flagos；`causal_conv1d_update` → vendor（kunlunxin C++ kernel），并在 flagos_blacklist 中。
