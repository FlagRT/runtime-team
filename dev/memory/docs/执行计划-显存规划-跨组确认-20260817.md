# 跨组确认：执行计划与显存规划接口（2.4 任务 #4）

> 日期：2026-08-17 ｜ 致：编译组 ｜ 由：运行时组（xliu969）
> 背景：2.4 子项 A「显存池与分层缓存」要求"依据执行计划复用显存块并回收碎片"。当前 torch_fl 只有**动态缓存**（分配后复用，caching_device_allocator.h:30-122），没有**计划感知**的静态规划。是否上静态规划、怎么上，取决于编译层执行计划里有什么。

## 问题清单（请编译组答复）

1. **执行计划产物里目前有哪些信息？**
   我们已知的交付物是 FlagTree kernel 的 launch 原语（阶段 0 契约）。请问编译层是否产出"整图/子图执行计划"（含算子顺序、张量 shape/dtype/layout）？如果有，格式是什么（JSON/protobuf/内部结构）？

2. **执行计划里是否含显存相关信息？** 具体而言：
   - 每个中间张量的**生命周期**（live range，从哪个算子产生、到哪个算子不再用）？
   - 显存块**复用提示**（哪些张量可共享同一块内存，如 in-place 合并/死张量覆盖）？
   - 峰值显存**估算**或**规划结果**？
   以上有哪几项？

3. **"执行计划"在推理链路的哪个环节产生？** 我们当前推理闭环是 vLLM（动态图，eager 模式）——vLLM 的动态执行没有离线执行计划。请问编译组规划的"执行计划驱动显存"主要面向：
   - (a) 编译静态图场景（FlagTree 编译产物直接执行）？
   - (b) 也要覆盖 vLLM 这类动态推理框架（若有，接口形态是"按需查询"还是"整图计划"）？

4. **launch 原语/设备侧能否感知"内存块"？** 即：编译产物是否接受"显存块句柄"作为输入（由运行时分配好块再喂给 kernel），还是 kernel 自己 alloc？这决定显存池在链路上的位置（运行时分配 vs 编译层预留）。

## 对我们（运行时组）的影响

- 若执行计划含生命周期/复用提示 → 子项 A 走"静态规划 + 动态缓存兜底"，收益最大
- 若不含（或 vLLM 场景拿不到）→ 子项 A 以动态缓存优化为主（碎片整理、扩容、池化），"依据执行计划"降级为"依据 vLLM 块表/KV 分配模式"
- 答复形式不限（会议/文档/代码示例），书面留档即可

## 我们已完成的现状盘点（供参考）

- torch_fl 动态缓存池已可用：复用/切分/相邻合并/stream 安全/OOM 重试/统计（probe 实测：10 次同尺寸循环仅 1 次设备 malloc；随机尺寸抖动碎片冗余 4.9%）
- vLLM 侧 KV 块表/prefix cache 由 vLLM 自己管理（KVCacheManager，evict_blocks 为可挂载点）
- CANN 9.0.0 无内存池 API（仅 aclrtMallocCached/aclrtMallocWithCfg），池化须自研（已有雏形）
