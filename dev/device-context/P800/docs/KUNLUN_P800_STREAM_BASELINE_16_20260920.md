### 3.2 ⚠️ 自我纠错：首测"不支持"的结论是错的

**首次探测时得到失败**：

```
AcceleratorError: CUDA error: unrecognized error code
```

按此写下的第一版判断是"P800 图捕获不支持、XPytorch 未适配"——**该判断不成立，已撤回**。

**真实原因是我探针的用法错了**：在 `with torch.cuda.graph(g):` 捕获区内调用了 `dev.synchronize()`。
CUDA Graph 的语义明确**禁止在捕获区内做同步**（捕获期要求所有工作留在被捕获的流上），
这不是厂商适配问题，而是调用方契约违反——与 910C 侧那条"107015 = 调用方契约违反，非设备缺陷"是同类。

**修正用法后（移出捕获区内的同步）即 5/5 全通过。**

⇒ 教训与本方向既有纪律一致：**出现失败先核对调用方用法是否符合上游契约，再怀疑芯片/厂商**。

#### 3.2.1 更正（2026-09-22）：§3.2 的根因**不完整**

"捕获区内调 `synchronize`"只解释了**其中一类**失败。按归档口径复跑时又出现一类
**无需任何同步**也会失败**的用法（即上表 G4*）：

```python
with torch.cuda.graph(g4):          # 捕获开始
    with torch.cuda.stream(s):      # 区内切到 s —— 但 s 未纳入捕获
        y4 = (x4 @ w4).sum()
```

- **实测**：P800 稳定失败（`AcceleratorError: CUDA error: unrecognized error code`，独立进程 3/3）；
  910C（torch_npu）与 MLU590（torch_mlu）**通过**。
- **归属**：这是**上游契约之外**的写法 —— 捕获区内的工作应留在捕获流上；要用副流必须经
  `graph(g, stream=s)`（= G5）或显式 fork/join 把副流**纳入捕获**。只是在区内 `with stream(s)`
  切过去，该副流并未进入捕获状态。
  ⇒ 它失败**不是厂商缺陷**，通过也不代表能力更强，**只代表该运行时更宽松**。
- **因此已把该项从判据降级为"宽容度观察项"**（不计入 PASS/FAIL），并把这一条写进了探针的
  docstring 与三实例报告中。

**另外一条踩坑（值得记）**：一次**失败**的捕获会弄脏分配器/捕获状态，
让**本可单独通过**的后续条目连带失败（实测：G4 失败后 G5 报
`Offset increment outside graph capture encountered unexpectedly`；而 G5 单跑是通过的）。
⇒ 探针已改为：观察项**放在最后**跑 + 每个条目失败后做状态清理。

### 3.3 S-12 流优先级：P800 不支持（上游缺陷，如实标注）

- **现象**：裸调 `Stream.priority_range()` 会触发 PyTorch 自身的
  `INTERNAL ASSERT FAILED at c10/cuda/CUDAStream.h:188`（`greatest_priority <= -1 ... Unexpected CUDA stream priority range`）
- **归属**：XPytorch 后端上报了**非法的优先级区间** → 属上游，非本层可修
- **本层处置**：`kunlun` 后端**主动拦截、绝不透传**（`stream_priority_range()` 返回 `None`），
  避免触发 C++ 断言导致进程级 abort；因此 `_capabilities` 中**不声明** `stream_priority`（如实）
- **仍有价值的部分**：多流并发正确性已验证（hi=5.0 / lo=8.0 各按自己语义完成）

> 安全提示：探针**不得裸调** `dev.Stream.priority_range()`（进程 abort 风险），一律经统一 API 取。
