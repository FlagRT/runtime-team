## 4. 两个真实发现（对机制设计有直接影响）

### 发现 1：**真实流同步超时是"进程级致命"错误，不能靠进程内重放**

- 现象：在 910C 上真实触发流同步超时（507046）后，进程直接终止（`ERR99999 UNKNOWN application exception`），Python 无法在进程内捕获；更严重的是它会连带影响同容器内其它进程对设备的访问。
- 结论：**L3 的"重放"在超时场景下不成立**——超时类错误的恢复必须在**进程外**编排（重启 / 重调度 / 设备恢复），由监控方向负责。
- 已落入脚本：超时注入改为**子进程取证**并加 `--no-timeout` 默认跳过（结论已记录，不重复触发）。

### 发现 2：**超大额单次显存申请会拖死进程**（OOM 注入方式需改进）

- 现象：一次性申请 3 倍显存触发 NPU OOM 后，进程在后续步骤异常终止。
- 结论：OOM 注入应改为**渐进式分配**（逐步放大直到失败即停），避免把设备/进程拖死。
- 影响：推理腿 L4 项验证因此未完成，需按渐进式改法复跑。

## 5. 过程中的代码修正（都是跑出来才发现的）

1. **flagos 后端 `_to_unified` 字段错位**：用了 `raw/message/code`，统一错误对象的字段是 `root_cause/error_code/...` → `translate_error` 抛 `TypeError`，已按 ascend 写法对齐。
2. **能力声明键名不一致**：ascend 用 `sync_timeout`、flagos 用 `bounded_sync`，导致 ascend 已实现的有界同步被误判为不支持 → 统一键名（ascend 补 `bounded_sync`，flagos 改为同一套 `_capabilities`）。
3. **脚本 L4 注入函数返回异常而非抛出** → 改为 `raise`。
4. **脚本 sys.path 层级不足**（`import runtime` 失败）→ 补 `prototype` 目录。
