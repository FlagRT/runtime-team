## 3. 归因核查：**此前两条"发现"均不成立**（2026-09-09 补）

上一版记录了两条发现。按要求逐条复核，**两条都被受控实验推翻**。当时的现象是真的，但归因错了。

### 3.1 归因 A「真实流同步超时是进程级致命错误」—— ❌ 不成立

| 场景 | 结果 | 结论 |
|---|---|---|
| A：直调 pyACL `synchronize_stream_with_timeout(1ms)` | `rc=507046`，`ALIVE 1.0` | 可捕获、进程存活 |
| B：统一封装 `synchronize_stream`（干净进程） | `TimeoutError rc=507046`，`ALIVE 1.0` | 同上 |
| M1：捕获超时后不做同步 | `ALIVE 1.0` | 安全 |
| M2：捕获超时后做 `torch.npu.synchronize()` | `ALIVE 1.0` | 安全 |
| E：OOM 之后紧接着超时（同进程） | `rc=507046`，`ALIVE 1.0` | 安全 |
| K：shape 错误 → OOM → 超时（同进程，复刻原顺序） | `rc=507046`，`ALIVE 1.0` | 安全 |
| **完整脚本（含超时项）** | **5 闭环 / 0 失败**，超时项 `L3_EXECUTION / replay / 业务继续=True` | **L3 进程内重放成立** |

**修正后结论**：流同步超时**可以**在进程内捕获（`TimeoutError`，pyACL `507046`），进程存活、后续业务正常，**L3 重放在进程内可行**。脚本已改回进程内真实触发。

### 3.2 归因 B「超大额单次显存申请会拖死进程」—— ❌ 不成立

| 场景 | 结果 |
|---|---|
| C：一次性申请 3 倍显存 | `rc=0`，正常抛 `OutOfMemoryError`，`ALIVE 256.0`，用时 9.0s |
| D：渐进式分配 | 同样正常，`ALIVE 256.0`，用时 **38.4s** |

一次性分配**既安全又快 4 倍**，故保持一次性（并在脚本内注明核查依据）。

### 3.3 那么当时观察到的 `ERR99999` 是什么？

- 现象真实：进程终止时打印 `ERR99999 UNKNOWN application exception`。
- **但它是偶发的**：复现 1 次后，后续 **4 次**同类运行（去掉归零同步、恢复归零同步、重置后推理腿、训练腿）均未复现。
- 首次出现前，设备上刚跑过 `recover_device(probe)` 异常退出的实验，**怀疑与残留状态相关，但未证实**。
- 处理态度：**记为观察项，不写成结论**。它支持一条保守建议（见 §5），但不构成"L3 重放无效"的依据。

> 教训：单次观察到的崩溃，在排除替代解释前不能上升为机制性结论。这一条与 9-02 撤回"物理限制"结论是同一类错误。

## 4. 真实缺陷（这才是本轮有价值的产出）

归因 A/B 被推翻后，排查过程中暴露出**两个接口层真实缺陷**，都已修复：

### 4.1 `recover_device` 跨后端返回类型不一致

| 后端 | 修复前返回 |
|---|---|
| ascend | `bool` |
| flagos | `dict{ordinal, mode, recovered, detail}` |

同一接口跨后端返回不同类型，上层无法统一处理——闭环脚本在 ascend 上抛 `AttributeError: 'bool' object has no attribute 'get'` 而中断（这正是当时"进程被终止"的**部分**原因）。

**修复**：抽象基类声明改为 `-> dict`，ascend 包装为 dict，顶层 API 与文档示例同步，脚本兼容 dict/bool。

### 4.2 `recovered` 语义不一致（更隐蔽）

底层 `recovery.recover_device` **仅在设备处于 ISOLATED 状态时才执行重建**，否则直接 `return False`。于是「设备本来就正常、无需重建」被上报成「恢复失败」——实测推理腿 L4 报 `recovered=False`，而业务其实完全正常。

**修复**：ascend 后端补充设备状态查询与探活判定，`recovered` 统一为「**设备当前可用**」，`detail` 区分三种情况（重建成功 / 无需重建·探活可用 / 恢复失败·探活不可用），并附 `state` 字段。

修复后推理腿 L4 由 `recover_probe=fail` → **`recover_probe=ok`**，与训练腿一致。

## 5. 给监控方向的一条建议（保守，非结论）

超时类错误虽然可在进程内重放，但存在两点现实约束，建议接口约定中保留进程外兜底：

1. 超时发生时**流上仍有未完成任务**，重放前需先处置这些遗留任务（本脚本采用"等设备归零"，实测安全）；
2. `ERR99999` 偶发终止**未复现但未排除**，关键链路不应只依赖进程内恢复。

> 表述口径：这是**建议**，不是"L3 重放无效"的结论。上一版把偶发现象写成机制性结论，已撤回。

## 6. 过程中的代码修正（都是跑出来才发现的）

1. `recover_device` 跨后端返回类型不一致（bool vs dict）→ 统一为 dict
2. `recovered` 语义不一致（"无需重建"被误报为"恢复失败"）→ 统一为"设备可用" + detail 区分
3. flagos 后端 `_to_unified` 字段错位（`raw/message/code` → `root_cause/error_code`）→ `translate_error` 曾抛 `TypeError`
4. 能力声明键名不一致（ascend `sync_timeout` vs flagos `bounded_sync`）→ 统一键名
5. 脚本 L4 注入函数返回异常而非抛出 → 改为 `raise`
6. 脚本 sys.path 层级不足（`import runtime` 失败）→ 补 `prototype` 目录
