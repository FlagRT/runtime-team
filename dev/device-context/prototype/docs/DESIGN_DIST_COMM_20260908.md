## 1. 已达成的环境事实（实测取证）

| 事实 | 证据 |
|---|---|
| 组里主路线是 **torch_npu** | 推理腿锁定镜像自带 torch_npu；我们的 `runtime/backends/ascend` 后端基于此 |
| 训练腿锁定镜像走 **flagos（torch_fl）**，且**禁止 torch_npu 共存** | 镜像自带 `verify_flagcx_runtime.py` 直接报 `torch_npu must not coexist with the Torch-FL runtime` |
| 训练腿镜像自带 **flagcx 0.13.0**（多芯片统一通信库） | `pip list`：`flagcx 0.13.0`；`import flagcx` 成功，含 `dist` 能力 |
| 带卡容器并发上限 **3** | 4 个并发时 `acl.init()`=500000，降到 3 个后=0（已写入 stack.lock 置顶规则） |
| 我们的原型已支持**双设备后端** | `ascend`（torch_npu）13/13 + 6/6；`flagos`（torch_fl）13/13 |

**一个直接结论**：训练腿用 flagos 不是路线选择，而是**该锁定镜像的环境约束**；组里走 torch_npu 与我们在训练腿上用 flagos **不矛盾**——我们的后端是可插拔的，两条路都能接。

## 2. 三个选项的对比

| 选项 | 优点 | 风险/代价 | 结论 |
|---|---|---|---|
| **A. torch.distributed**（backend 随芯片：hccl / nccl / …） | 生态成熟，DDP 现成，社区资料多 | backend 名与实现随芯片不同，**极易出现"910C 能跑、换芯片就不适配"**；与"换芯片不改代码"目标直接冲突；flagos 后端下支持情况未验证 | ❌ 不作为主路线 |
| **B. flagcx 作为统一通信后端** | 本身就是为**多芯片统一**设计的通信库（与我们"新增后端=实现接口+跑 conformance"完全同构）；镜像自带；跨芯片语义一致 | 需分布式子方向给出接口约定（通信组生命周期 / 集合通信 / 异步完成语义 / 能力声明）；启动方式待定（torchrun 还是 flagcx 自带 launcher） | ✅ **推荐** |
| **C. 上层 torch.distributed 兼容 + 底层 flagcx** | 兼顾生态与统一 | 多一层适配，短期内收益不明确 | ⏸ 视 B 的落地成本再评估 |

**推荐 B 的核心理由**：flagcx 与我们的设计哲学一致——**把芯片差异收在一层里，上层不改代码**。用 torch.distributed 等于把"芯片差异"暴露到了用户代码层（backend 名要跟着换），正是我们要避免的。

## 3. 职责边界（我们 vs 分布式子方向）

通信能力**归属分布式子方向**，我们（设备上下文）提供设备侧支撑。交界处约定如下：

| 我们（设备上下文）提供 | 分布式子方向负责 |
|---|---|
| rank → device 绑定（`set_device`、多设备流/事件） | 通信后端选择与注册（flagcx） |
| 通信所用 Stream / Event（含跨流依赖、有界同步） | 集合通信接口约定（all_reduce / all_gather / P2P 等） |
| 通信/设备错误码 → L1–L4 分级（`translate_error`） | 通信正确性对照证据（验收标准 1 的通信部分） |
| 卡故障的设备级恢复（`recover_device` 原语） | 通信异常检测、任务重启与检查点恢复 |

**两条硬要求**（写进接口约定）：
1. 分布式侧**经我们的统一 API** 获取设备/流/事件，不直接 `import torch_npu` 或框架扩展；
2. 通信相关异常一律过 `translate_error` 拿 `FlagosError`，按 `disposition` 处置，不按消息字符串自行判断。
