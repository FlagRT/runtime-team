## 0 结论先行

1. **四处薄弱全部确认存在**，其中两处是**已登记但未修复**的既有缺口（`record_stream` 能力位、`.native` 逃生舱约束）。
2. **但只有一项该由我们做实现**（流语义/接口/判据）；**另三项的核心实现分属显存方向与调度方向** —— 我们只出
   **接口 + 语义 + 判据 + 证据**。这条边界若失守，本计划会变成我们替别家写实现，也违反方向职责。
3. **最高优先级不是补接口，而是补价值证据**（工作包 A）—— 目前我们只证明了"分歧存在且可检出"，
   **没证明"不为分歧做抽象会有实际损失"**。这是本层全部主张的地基。
4. 接口扩容（B/C）会走 **v0.2 变更流程**（改契约 → 知会下游 → conformance 回归），不是随手加方法。

## 3 工作包

### 工作包 A ·「分歧的业务代价」实验 —— `P0`，最高优先

**问题**：现在只能说"三家语义有分歧且我们能检出"，**说不出"不做抽象会损失什么"**。

**目标**：把同一段典型上层功能，在两条路径上各实现一次，**量化统一层消除的成本**。

**方法**（实验设计先固化，再取数）：
- 取一段**真实的上层需求**（不是构造玩具）：错误处理（L1–L4 处置）+ 有界同步 + 设备恢复判定，三者串起来；
- 路径 ①：只用 `runtime` 统一 API；路径 ②：直接调三家原生（`torch_npu` / XPytorch / `torch_mlu` + `acl`/`cnrt`），
  **允许按厂商分支**（这正是"不做抽象"的真实形态）；
- 度量：**分支数**（`if vendor == ...` 计数）· **代码行数** · **需要厂商私有知识的点数**（必须查厂商码表/文档才能写对的地方）·
  **单次调试到通过的时间**。

**交付物**：`prototype/probes/exp_divergence_cost.py`（可复跑）+ 实验报告 + 三家原始数据 JSON。

**判据（先写死，不许事后解释）**：
1. 两条路径的功能**等价性**必须先被证明（同一组输入 → 同一组 `disposition`），否则比较无意义；
2. 三家 × 两条路径 = **6 组数据齐全**，缺一组就如实标"未取得"，不补零；
3. **结论方向不做预设**：若统一层只减少 1–2 个分支，**如实写"本层价值有限"**。

**边界**：纯自做（价值证据属本层）。**依赖**：三实例真机可达（910C 名额 / 寒武纪网络间歇 ⇒ 需排期容忍）。

**风险**：这是本次唯一可能得出**不利结论**的工作包 —— 但正因如此才必须先做。

### 工作包 B · 内存域：句柄与生命周期接口 —— `P1`

**目标**：把内存域从"只有统计"补到"有句柄语义 + 跨流保护可预判"。

**做**：
1. `base.py` 新增抽象：`allocate(size_bytes) -> handle` / `free(handle)`（**句柄语义**，不做池化策略）；
2. `memory_stats` 扩字段：在保持现有三键**不变**的前提下增加 `allocated_mb`（分配器视角），供显存方向采集；
3. `record_stream` **能力位**：`supports("record_stream")`；上层跨流传递前先判能力，不支持时走**保守同步路径**
   （而不是等 `getattr` 失败才报错）—— 此项即修订建议 §3 的既有补漏；
4. `.native` 逃生舱**审计计数**：后端记录 `.native` 被取用次数，进 `info()`（同一条补漏）。

**不做**：池化 / 碎片 / 峰值 / 扩容 → 显存方向。

**判据**：三后端 `allocate → 写入 → free` 全绿；`memory_stats` 值自洽（`total ≈ used + free` 已有判据，
新增 `allocated ≥ 0`）；`record_stream` 能力位**逐家如实取值**（有就说有，无就说无）；
**新增判据必须做非空转验证**（注入缺陷证明能 FAIL）。

**交付物**：`base.py` 接口 + 三后端实现 + 离线自检/职责审计各加判据 + `INTERFACE_CONTRACT` v0.2 变更条目。

**边界**：只出接口与判据；分配器实现对外。**依赖**：三家真机（kunlun 的 alloc 语义与本机行为需实测，不类推）。
**风险**：v0.2 接口变更 ⇒ 必须知会下游 + conformance 回归全绿。

### 工作包 C · 设备上下文生命周期 —— `P1`

**现状澄清**：`stream_context` 是**切换流的上下文管理器**，与"设备上下文（context）的创建/销毁"是两件事 ——
现原型**没有任何 context 生命周期接口**，而 `recover_device(mode="real")` 内部却会执行
`destroyContext → ResetDevice → 重建`（见 `base.py:107-117`）—— **执行了但完全不暴露**。

**做**：
1. `context_create(ordinal)` / `context_destroy(ordinal)` / `context_count()` 抽象（语义对三家统一）；
2. **绑定语义**：context 销毁后，其上已建流/事件的行为必须**明确**（报错 or 隐式失效），不能"看运气"；
3. `recover_device` 返回值补 context 维度（重建前后 context 计数 / 是否被销毁重建），让监控方向**能看见**；
4. 探针：多 context 隔离性（至少证明 pairwise 不串）。

**不做**：何时恢复、恢复到哪一级的编排 → 监控方向。

**判据**：`context_count()` 可用；销毁后使用其流须**如实报错**（不得静默成功）；多 context 隔离探针有取证；
`recover_device` 五键基础上新增字段**不破坏现有契约**（只增不改）。

**边界**：执行 semantics 属我们，编排属监控方向。**风险**：`real` 模式会重置进程默认上下文（`base.py:115`），
多进程下需压测 —— 与 §2 遗留项「D11 real 多卡多进程压测」**合并推进**。

### 工作包 D · 流优先级与配额的「效果」验证 —— `P2`

**现状**：优先级**能读到范围**（ascend `7/0`、cambricon `(0,-3)`、kunlun 不支持），但**没有任何判据回答"它真的生效吗"**；
配额只证"2000 个能建"，**不发现真实上限**。

**做**：
1. **优先级效果判据**：两条同构工作流、不同优先级，测**执行顺序/完成时间**是否被优先级影响
   （若三家都测不出效果，**这也是一条有价值的结论**：范围可读 ≠ 效果可用）；
2. **配额上限发现**：二分逼近真实上限（而非只测 2000 能过），留同口径数据；
3. 两项都进 S-1~S-16 基线的**同口径三实例对照**。

**不做**：调度策略 → 调度方向。**本项正是 §2 挂账 4 项遗留里的「流优先级调度效果」**。

**判据**：三实例同口径；不支持的如实标 `unsupported`（kunlun 已知不支持，因上游 PyTorch `INTERNAL ASSERT`，
**且已登记为上游缺陷候选**，不属我方）。

**风险**：效果可能不可观测（不能因此改判据变绿）；三实例硬件可及性。

## 5 验收口径（本计划自身怎么算完成）
