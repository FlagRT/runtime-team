## 6 本次核查自身踩到的坑（供下一次照抄）

1. ⭐ **"清单缺一行"等于"这一步永远不会被跑"** —— PPU 首轮漏跑契约不变式，根因不是"忘了"，而是**看板矩阵没有这一行**：
   对齐时自然只对着看得见的行做。⇒ **凡"按清单对齐"的动作，第一件事是核清单本身是否完整**
   （本轮用 `grep -c` 逐份看板扫关键词才暴露：四家看板该关键词**全为 0**）。
2. ⭐ **证据矩阵工具必须"递归 + 两种命中分列"** —— 首版只扫 `probes/` 顶层 ⇒ 漏掉 `m1_*_out/`、`d2_*_out/` 里的产物，
   误报 MLU590「B/C 契约从未跑」（**实际跑了**，文件名是 `m1_bc_probe_cambricon.json`）。
   分列"文件名命中 / 内容判据命中"才能把"文件在但内容是空的"挑出来。
3. ⭐ **状态列＝僵尸高发区**：`VERIFICATION_MANIFEST` §3 的 G6/G7 停在登记当日，后续落地**不会回写**
   ⇒ 与专项审计报告矛盾。⇒ 回填时**逐条实物复核**，并给状态列加"本列只是索引"的说明。
4. **本机 `grep` 在部分组合下会静默 0 命中**（本轮 3 次）⇒ 结论性命中一律换可靠检索工具复核，
   或把模式写成单模式多次调用。
5. **`_extract` 类小工具要先自证**：能力对齐工具首版因"行尾注释未剥 + 匹配到非赋值处"产出
   「PPU 声明 0 项」的**假结论**（差点写成"PPU 能力声明缺失"的重缺陷）。
   ⇒ 提取类工具必须先跑一遍**已知答案**（本例：PPU 声明集非空）。
6. **文档内相对路径必须写明"基准"** —— 同一个 `910C/probes/…`，在主看板（根目录）能点开、在 `prototype/docs/` 下点不开。
   本轮新报告因此在**文件头显式声明基准**（§0 上方那句）；历史文档未动（见 §3 C8）。
7. **"工具报 ❌"不等于"缺口"**：`S1`（910C/P800）与 `S16`（P800/MLU590）都被工具报 ❌，
   但前者是"脚本 09-22 才诞生"、后者是"该能力如实不具备"⇒ **工具只给候选，定性必须人做**（§2.1 末注已列编号对应）。
