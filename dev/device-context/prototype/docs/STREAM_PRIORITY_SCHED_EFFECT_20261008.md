## 1 结论速览

**一句话**：在 MLU590 上，流优先级**不是**「接口能设、与调度无关的装饰」——
**有一条流已在运行、另一条才提交**这个**真实场景**下，它确实改变设备份额，让高优先级流
**反超先提交的低优先级流 5.3–8.1 ms（≈ 37–57% 的工作量级）**；
但在**两条流同时就绪**的场景下，它**不改变完成顺序**（两条流并行跑完，只剩一个量测步长的差异）。

| 场景 | 实测结论 | 读数（MLU590） |
|---|---|---|
| **A. 同时就绪**（两流同一 gate 一起放行） | ❌ **无实质效果** —— 两条流**并行跑完**，差异只有 **1 个量测步长** | 高优先级（取值 0）先完成 **1/8**；中位差 **−0.227 ms**（工作量级 14.185 ms 的 **1.6%**） |
| **B. 有排队/争用**（一条已在运行、另一条才提交） | ✅ **有实质效果** —— 取值 0 在**两种提交顺序下都大胜** | G4（取值 7 先提交）= **+6.24 ms**、G8（取值 0 先提交）= **+7.15 ms**，各 **8/8**；同取值同顺序对照 = **−1.84 ms** ⇒ 净效应 **5.3–8.1 ms** |

**P800 的结论是「如实不适用」**：`cuCtxGetStreamPriorityRange` 报 **least=0, greatest=0**
（优先级空间**退化为单点**）⇒ 构不成对照 ⇒ `STREAM_PRIORITY_SCHED_EFFECT_NOT_APPLICABLE`。
⚠️ 但**仪器有效性照样验过**（正对照 8/8、中位差 9.87 ms）⇒ 这个「不适用」是**设备属性**，
不是「探针没工作」。

**910C 的结论也是「如实不适用」，但原因不同**：本实例**不声明 `stream_priority_control`**
（实测 `stream_priority=True` / `control=False` / `readback=True`，区间**可读** `(7, 0)`）
⇒ 与 P800 的「空间退化为单点」是**两种不同的不适用**。同样**仪器有效性照样验过**
（正对照 8/8、中位差 12.75 ms、分辨力 0.021%）。

⭐ **三台一起看，还得到一条独立证据（910C 轮的增量，见 §4.5）**：三台的**同优先级基线（G3）**
都是**同一个量级的负偏斜**（910C **−0.197 ms** / MLU590 **−0.226 ms** / P800 **−0.153 ms**），
而 **G3 里两条流的优先级完全相同**；**910C 设不了（未声明 `control`）、P800 只有单档（`(0,0)`，构不成优先级差）**（`applicable=False`）
⇒ **在零优先级差的条件下，同样量级的差异照样出现** ⇒ 场景 A 那个「1 个量子」的差异
**不宜归因于优先级**（§5 第 3 条已据此更新）。

**对 D2 要回答的问题**（「上层能不能拿优先级做调度决策」）：
- 想让关键流**插队到已有低优先级流之前** ⇒ **可以**（本场景实测有效，方向与契约声明一致）；
- 想靠优先级让**同时就绪**的两条流**按优先级排序完成** ⇒ **不行**（同时就绪时并行完成，顺序不受优先级支配）。

## 3 实验设计与判据纪律

设计上**必须**先解决四件事，否则结论不可信（每一条都是前几轮踩出来的教训）：

| # | 设计要点 | 为什么必须这样 |
|---|---|---|
| ① | **必须经本层统一面建流**（`runtime.create_stream(priority=…)`） | MLU590 实测**厂商 torch 侧会静默丢弃**该参数（设备 C API 回读 `4`，而 `.priority` 属性回显 `7`，见第十二轮 D5）⇒ 用 `torch.mlu.Stream(priority=…)` 做实验等于测了一条**参数并没进设备**的路径，「无效果」会是**假结论**。 |
| ② | **入队顺序每轮随机化** | 同优先级时「谁先提交谁先跑」；写死顺序会把**顺序效应**读成**优先级效应**。 |
| ③ | **扫描顺序每轮随机化 + 平局检测** | 固定「先查 hi 再查 lo」会让同轮内两者都完成时**必然记 hi 先完成**（偏向）。本探针改「两条都完成后才读结果」，并把「同一趟扫描里两条都完成」记为 `indeterminate`（平局），**不计入胜负**、单独上报。 |
| ④ | **gate 必须是真 gate** | 旧探针把「两流 wait gate」**先入队**、`gate.record()` **后调用**；对**未记录**事件的等待在 CUDA 语义下等价于**空操作** ⇒ 两条流其实在入队时就放行了，「gated 组」退化成 naive 组。本探针改为**先把一段慢活排在同一条流上、再记录 gate**，使两次等待都**在 gate 触发前**入队；并由 **V1** 判据守住（两流完成时刻必须 ≥ 慢活的 80%）。 |
| ⑤ | **配正对照（非空转）** | 让「高优先级」那条流**工作量减半**、优先级**相同** ⇒ 测量**必须**判出「hi 先完成」。否则「未观测到效果」与「测量分辨不出」无法区分——后者会把**仪器缺陷**伪装成**设备结论**。 |
| ⑥ | **判定 = 胜率 ∧ 幅度**（≥75% ∧ ≥工作量级的 25%） | 只看胜率会把「差一个量测步长」读成效果——本轮实测**正是如此**（8/8 稳定领先，幅度只有 0.228 ms）。这类差异对调度决策毫无价值。 |

另有两条**量测本身**的判据：**D1**「一趟扫描耗时 ≪ 工作量级」（实测 5.66 µs = 工作量级的 **0.040%**，
阈值 ≤5%）与 **E2**「设置后回读必须等于请求」（不回读就不放行，否则整场实验测的不是我们以为的东西）。

**九个组的分工**（`hi`/`lo` 是角色标签，取值按 `hi=min(range)`、`lo=max(range)`，即官方语义「数值越小越高」）：

| 组 | 构造 | 作用 |
|---|---|---|
| G2 | 同取值、gate、hi 工作量减半 | **正对照（仪器有效性）** |
| G3 | 同取值、等量、gate、顺序随机 | **噪声基线** |
| V1 | gate 有效性（3 轮） | 判 gate 是否真的 gate |
| G1 | 取值 0 vs 7、gate、顺序随机 | **主判据（场景 A）** |
| G4 | **固定**取值 7 先提交、0 后提交 | 场景 B：后提交者能否反超 |
| G7 | 同 G4 但**两流取值相同** | G4 的**必要对照**：排除「恒为后提交者获胜」 |
| G8 | 与 G4 **顺序相反** | 与 G4/G7 合成 2×2 |
| G5/G6/G9 | 角色对调 / 1 vs 0 / 7 vs 1（均 gate） | 判定那个 0.228 ms 偏斜跟着**取值**还是**角色/非 0** |

## 4 实测结果（MLU590，8 轮/组。工作量级 = 60 次链式 2048² matmul = **14.185 ms**）

| 组 | 读数 | 中位差 | 解读 |
|---|---|---|---|
| G2 正对照 | **8/8** | **+14.07 ms** | ✅ 与工作量级同量级 ⇒ **仪器能判出真实差异** |
| G3 同取值基线 | 3/8 | −0.226 ms | 干净的**噪声基线**（掷硬币） |
| V1 gate 有效性 | — | 慢活基准 59.185 ms | ✅ 两流完成时刻（86.0–86.3 ms）都在 gate 之后 ⇒ 等待非空操作 |

| G5 角色对调 | 取值 7 胜 **8/8** | +0.227 ms | 获胜方**跟取值走**，不跟角色 |

## 5 结论与边界

**结论（分场景，不得合并）**：

1. **场景 A（两流同时就绪）：优先级不改变完成顺序。** 两条流**并行跑完**，中位差仅 0.227 ms
   （工作量级的 1.6%），且 8 轮里 7 轮是低优先级那条先完成。⇒ 若上层的意图是
   「都就绪时让高优先级先做完」，**在该栈上不成立**。
2. **场景 B（有排队/争用）：优先级有实质效果。** 取值 0 相对取值 7 净得 **5.3–8.1 ms**
   （工作量级的 37%–57%），且在**两种提交顺序下都成立**；同取值同顺序的对照为 −1.84 ms
   ⇒ 效应**可归因于优先级差值**，不是提交顺序。**方向与契约声明一致**（数值越小优先级越高，
   G4/G8 两向合计 **16/16**）。
3. ⚠️ **场景 A 的 0.228 ms 偏斜：量级已被 910C 的加入解释，方向仍未解释**（2026-10-08 更新，
   原写「一处未解释的矛盾」）：
   · **方向**仍是「数值大者领先」（MLU590 的 G1/G5/G6/G9 = 8/8 一致），与场景 B 的 5–8 ms 效应
     **方向相反** ⇒ **仍不就方向下统一结论**，**不要用场景 A 的 0.228 ms 去推断优先级方向**；
   · **但量级有了独立对照**：三台的**同优先级基线 G3 都是同一量级**
     （910C −0.197 / MLU590 −0.226 / P800 −0.153 ms），而 **910C 设不了、P800 只有单档**
     ⇒ **该量级的差异在零优先级差时同样出现** ⇒ 它是一个**设备派发量子**量级的现象，
     **不宜归因于优先级**。这与「场景 A 无实质效果」的判定一致 —— 判定阈值是**工作量级的 25%**，
     而这是 **1.4–1.6%**。

**边界（必须随结论一起引用）**：

- 单卡 · 同进程两条流 · **人为构造的争用**；**不等于**生产负载下的收益。
- 只测了**端点一对取值**（0 与 7）与中间档 1；**档位间隔**对效应大小的影响**未测**。
- 负载形态为**同规模 matmul 链**（每条 ~14 ms）；别的形态（小块 kernel、通信、memcpy）**未测**。
- 「未观测到效果」**不等于**「优先级无效」；本探针只回答「**在本场景下**完成顺序/份额是否与优先级一致」。
- 结论**只对本栈成立**：MLU590 / 驱动 6.2.29 / `neuware4.4.3` / torch 2.7.1 / torch_mlu 1.29.2。
- **未引用任何厂商调度文档作机制依据**（MLU590 侧未取得对应文档；CANN 侧「不抢占已运行任务、
  不动态重评估队列」的表述**不得**外推到本家）。
