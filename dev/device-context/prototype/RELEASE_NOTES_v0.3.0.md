## 2. 本次交付（相对 v0.2.0 的增量）

### 2.1 契约新增五个 sub-part（§1.6–§1.10 · **全部只增不改**）

| 章节 | 承诺什么 | 关键设计 |
|---|---|---|
| **§1.6 内存句柄与生命周期** | `allocate` / `free` / `memory_handle_count` | 句柄**不含厂商指针**；`.native` 与「退化」**双审计**；`record_stream` 能力位 + **保守同步路径** |
| **§1.7 设备上下文生命周期** | `context_create` / `set` / `destroy` / `count` / `query` | **`context_lifecycle`（能管）与 `context_query`（只能看）分开声明**；「上下文失效后用其流」由本层在**使用点**拦截 |
| **§1.8 契约不变式 I1–I4** | 「诚实声明 / 禁止伪造 / 失效受管 / 降级可观测」**有定义、有判据** | 真机与离线**共用同一套核心函数**（离线按文件路径加载同一模块，防两处漂移） |
| **§1.9 流优先级** | `create_stream(priority=)` + `stream_priority_readback()` + `stream_priority_range()` | 能力键**拆三把钥匙**（能读范围 / 能设置 / 能回读）+ **四道约束**（未声明⇒显式拒绝；越界⇒ `ValueError`；**创建后强制回读**；`None` 逐位不变） |
| **§1.10 流所有权与释放** | `release_stream()` / `Stream.release()` / `owns_stream` | 「**本层拥有**的流才由本层释放」；对**已释放对象**再使用**明确报错**（`RuntimeError` 含「已释放」） |

### 2.2 统一面新增 18 个出口（28 → 46 · **移除 0**）

| 分类 | 出口 |
|---|---|
| 流 | `create_stream(priority=…)`（扩展）· `stream_priority_readback` · `stream_priority_range` · `release_stream` |
| 内存 | `allocate` · `free` · `memory_handle_count` · `MEMORY_HANDLE_KEYS` |
| 设备上下文 | `context_create` · `context_set` · `context_destroy` · `context_count` · `context_query` · `CONTEXT_HANDLE_KEYS` |
| 恢复与状态 | `set_device_state` · `handle_error` |
| 元信息 | `DEVICE_STATE_TOKENS` · `native_accesses` · `degradations` |

### 2.3 三个「把跨实例分歧变成可消费信号」的设计（本版方法论）

1. **能力键拆钥匙**：`X`（读范围）/ `X_control`（能设置）/ `X_readback`（能回读）——
   **能读 ≠ 能改 ≠ 能校验**；声明 `control` **必须**同时声明 `readback`（否则设置无法校验）。
2. **未声明能力 ⇒ 显式拒绝，不静默降级**：抛 `NotImplementedError` 且文案含**能力键名**。
   ⛔ 绝不「返回一条没有该属性的对象」——那会把「不支持」伪装成「支持」。
3. **给上层可判定的信号（不是文档口径）**：`stream_priority_range()` 返回 `(least, greatest)`，
   **`range[0] == range[1]` ⇒ 该实例上优先级无区分**，不得据此做调度决策。

### 2.4 行为修正（修在 v0.2.0 之后 —— 下游需换到本版才可追溯）

| # | 问题 | v0.2.0 的后果 | 现在 |
|---|---|---|---|
| 1 | 未声明 `error_map` 的后端仍用**他厂错误码表**定分级 | 他厂码喂进来被判 `L4_FATAL` ⇒ **误触发设备级重建（最贵的动作）** | 无码表后端**从源头不查外来码表**，四字段**结构上不可能不一致** |
| 2 | `recover_device()["state"]` 取值域 | 返回 `'DeviceState.AVAILABLE'` ⇒ 下游 `state == "available"` **判假** | 统一 token 归一（`DEVICE_STATE_TOKENS`） |
| 3 | L2 分级规则**按个别厂商文案枚举** | 设备序号越界的厂商原文落不到 L2 ⇒ 兜底 `L3_EXECUTION`（`replay`）⇒ **对永久性参数错误反复重放（动作反了）** | L2 规则改**按等价类覆盖** |
| 4 | 流登记表以 `id()` 为键 | **id 复用**让 `release_stream()` **越权销毁厂商的流** | 改按**对象身份**复核 |
| 5 | 「诚实降级」只降 `graded_by` | `mapped` / `error_code` 未降 ⇒ **假「确定分级」** | 三字段**整组一致**降级 |
| 6 | `ascend.info()` 缺 `device_type`；三家 `info()` 各手写一份公共字段 | 契约与冒烟都要求该键却 `KeyError`；同一份清单**三个来源** | 补键 + 并入**基类唯一来源** |
| 7 | 服务启动脚本：冒烟超时**硬编码 60 s**；某后端分支默认 `MODEL` 是**宿主路径** | 把耗时 63.6 s 的**成功**请求判成失败（假失败）；容器内模型路径**永不可用** | `SMOKE_TIMEOUT`（默认 180 s）+ 打印实际耗时；默认值改容器路径 + **存在性断言** |
| 8 | 演示脚本根解析 off-by-one；`--backend` **写死** | 换机器即 `ModuleNotFoundError`；换芯片仍走原后端 | 修根解析（+ 静态自检脚本）· 统一读 `DC_BACKEND` |

## 3. 接入方式

```python
import sys; sys.path.insert(0, "<path-to>/prototype")
import runtime

runtime.use("kunlun")                 # 或 "ascend" / "cambricon"；切换芯片只改这一行
runtime.set_device(0)
s = runtime.create_stream()

# ── 本版新增能力（按需，全部可选）──
h   = runtime.allocate(4 * 1024 * 1024)     # 句柄不含厂商指针；重复释放会如实报错
runtime.free(h)
ctx = runtime.context_create(0)             # 只在声明了 context_lifecycle 的后端可用
print(runtime.context_query(0))             # 只读观测（两家都可用）
runtime.context_destroy(ctx)

r = runtime.stream_priority_range()         # (least, greatest) 或 None
if r and r[0] != r[1]:                      # ⭐ 可判定信号：区间是单点 ⇒ 无区分
    s2 = runtime.create_stream(priority=r[0])
    assert runtime.stream_priority_readback(s2) == r[0]
    runtime.release_stream(s2)              # 本层拥有的流才由本层释放

runtime.set_device_state(0, "isolated")     # 公开面驱动四态（本层账本）
res = runtime.handle_error(exc, mode="probe")   # R1–R5 错误编排
```

**各实例环境前置**（实测硬前置，沿用 v0.2.0）：

| 实例 | 前置 |
|---|---|
| P800（昆仑芯） | `export PYTHONPATH=/env/FlagGems/src` · `export FLAGCX_ADAPTOR=klx`（集合通信唯一可用路径） |
| MLU590（寒武纪） | **服务化须用 vLLM 应用镜像**（运行时不带 vLLM）；`import triton` 前须先 `import torch_mlu` |
| 910C（昇腾） | 训练腿用容器内**带 torch_npu 的解释器**；拼设备串 / 集合通信后端名前**必须先经后端触碰一次设备** |

> `prototype/` **自包含**：conformance 依赖的模块（errors / recovery / device_state / npu_events）已内置，整体拷出即可用。
> 详细 API 与硬纪律见 `prototype/README.md`；接入流程见《新芯片接入手册》。

## 4. 纪律

**沿用（v0.1.0/v0.2.0 实测结论）**：

1. **跨流传递内存必须 `record_stream`** —— 否则缓冲可能被提前回收 → 数据竞争。
2. **错误隔离是分层的** —— API 级错误只影响该次调用、可流级重试；芯片级故障影响该设备全部流，
   流级重试无效，必须走 `recover_device`。处置一律按 `FlagosError.disposition`，
   **禁止按错误消息字符串判断**；`translate_error` 必须传**完整原始消息**（截断会误判成可重放）。
3. **错误对象必须归一为 api 层枚举** —— 后端返回的 `category` 必须是 `api/errors.py` 的 `ErrorCategory`
   实例，**不得使用其他模块自行定义的、取值相同的枚举或整数**（否则字典查找失败）。

**本版新增两条**：

4. ⛔ **不要用「能力位」代替「取值域」**：`supports("stream_priority_control")` 为真**不代表**优先级有区分 ——
   必须再看 `stream_priority_range()` 是否单点。
5. ⛔ **「能设置」≠「有效果」**：本版给出分场景实测（§5 末），**不要**把「能设」当成「能排序」。

- 服务化就绪时间含**首次请求编译开销**，跨实例差异很大（30 s ~ 360 s）⇒ **不可当性能指标横比**；

### ⭐ 流优先级「调度效果」（本版新增的跨三实例对照实验）

**结论分场景，不得合并**：

| 场景 | 实测（唯一能出结论的实例，工作量级 14.185 ms，8 轮/组） | 结论 |
|---|---|---|
| **两流同时就绪**（同一 gate 放行） | 高优先级先完成 **1/8**；中位差 **0.227 ms** = 工作量级的 **1.6%**；两流**并行跑完** | ❌ **无实质效果** ⇒ 不能指望「同时就绪时按优先级排序完成」 |
| **有排队争用**（一条在跑、另一条才提交） | 取值 0 在**两种提交顺序下都赢**（各 **8/8**）：反超 **+6.24** / 大胜 **+7.15 ms**；同取值同顺序对照 **−1.84 ms** ⇒ **净效应 5.3–8.1 ms** | ✅ **有实质效果** ⇒ **可以**用优先级表达「插队到已在运行的低优先级流之前」 |

**另两实例如实不适用，但原因不同**（不得合并成一句）：

| 实例 | 不适用原因 | 仪器有效性 |
|---|---|---|
| **910C** | **不声明 `stream_priority_control`**（设备侧具备该能力 —— 原生接口保留 0/3/7；**上游 PyTorch 插件未暴露入口**） | ✅ 正对照 8/8 · 分辨力 0.021% |
| **P800** | **优先级空间退化为单点** `(0,0)`（设备只报一个档位） | ✅ 正对照 8/8 · 分辨力 0.016% |

## 6. 已知限制（如实列出）

| # | 限制 |
|---|---|
| 1 | **910C 流优先级不可设**：设备侧具备该能力（原生接口保留 0/3/7），受阻于**上游 PyTorch 插件的接口面未暴露入口**。本层已**如实不声明**并结构化登记（含 6 条证据与可执行诉求）；**待上游补绑定**，不影响本方向验收。 |
| 2 | **P800 优先级区间为单点** `(0,0)`：接口可设、可回读，但**设置不产生任何区分** ⇒ 上层**不得**据此做调度决策。 |
| 3 | **调度效果的适用面窄**：仅在「一条流已在运行、另一条才提交」时观测到实质效果；**两流同时就绪时无实质效果**；档位间隔、其他负载形态未测。 |
| 4 | **P800 两条厂商侧问题**：① KL3 事件同步概率性永久挂死（约 89%，**不影响单进程设备上下文路径**）② **物理卡 1 计算通路故障**（控制面正常 ⇒ 「能查到卡」≠「能用卡」）。均归属厂商侧，已对外提交正式报告。 |
| 5 | **P800 镜像尚未入锁**：结论建立在未入锁镜像上；建议以官方 `-base` 入锁（等价性验证已通过），配方须含 `flagtree` 补齐步骤。 |
| 6 | 非昇腾两家的**有界同步口径不同**，超时类能力须如实声明（`bounded_sync_scope` 已在 `info()` 显式暴露）。 |
| 7 | `real` 设备重建仍**未作生产默认**：多卡多进程压测已通过（3 rank × 30 轮 · 30 次真重建零失败 · 非恢复者结果逐位不变），但**芯片级错误是构造的**（公开面无置隔离入口时由本层提供），非真实硬件故障。 |
| 8 | **CNCL 走片间互联、非 RDMA** ⇒ 寒武纪训练数据**只代表单机 2 卡**，跨机 / RDMA 路径未验证。 |
| 9 | 历史模型（Qwen2.5-1.5B / Qwen3-4B）**尚未在统一原型上复跑**（既有两条腿用的是验收模型）。 |
| 10 | 跨芯片性能数字**不可直接横向比对**（栈与形态均不同，见 §5 说明）。 |
| 11 | 910C 宿主**带卡容器名额**：独占单位是「已初始化容器所挂载的设备集」，**空闲容器不占名额** ⇒ 只挂自己要用的空闲卡即可与现网并存。使用前请先读使用规则。 |

  属接口约定对 v0.1.x 的承诺范围。
- **升级建议**：**建议全部下游升级到本版** —— v0.2.0 存在会**误导动作**的行为缺陷（§2.4 第 1/3 条：
  误触发设备级重建、对永久性参数错误反复重放），且本版新增的 18 个出口在 v0.2.0 上会 `AttributeError`。
