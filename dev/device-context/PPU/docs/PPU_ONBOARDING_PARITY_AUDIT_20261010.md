### 4.1bis 「修复」的原始记录（⚠️ 结论已被否定）

**修复点**：`../../prototype/runtime/backends/base.py::_register_owned_stream` —— 该表以 `id(native)` 为键，
而**归属判定只能靠「`holder() is native`」这一条身份复核**；复核**只有在被登记对象仍存活时才可靠**：
对象一旦被回收，其 `id` 立刻可被新对象复用，而弱引用只能给出 `None`，无法区分「同一个 id」与「同一个对象」。
实测（本机）`id()` 复用是**高频常态**（一次 78 项审计里同一 address 被反复命中，同一 handle 甚至以同一 id 被登记两次）。
⇒ 改为**强持有**（`lambda: native_stream`）：**在册 ⇒ 对象一定存活 ⇒ 其 id 不可能被复用**，
`holder() is native` 于是成为**可靠**的同一性判据（能匹配上的只能是当初登记的那个对象）。
代价是条目在被显式释放前让包装对象多活一会儿（数百字节）；按契约该流本就**必须被显式释放**
（否则泄漏的是设备级流，代价大得多）⇒ 这是正确方向上的取舍。
⚠️ 与 `_released_streams` / `_stream_ctx` 的区别：那两张表误判的后果是**误拦**（保守可恢复），弱引用足够；
本表误判的后果是**越权销毁**（不可恢复），故必须强持有。

**修复前后（同机、同脚本、重复跑）**：

| | 次数 | 结果 |
|---|---|---|
| **修复前**（弱引用） | 4 | **全部 `OK 71 / FAIL 1 / SKIP 6`** ⇒ `DUTY_RESPONSE_FAIL` |
| **修复后**（强持有） | **8** | **全部 `OK 72 / FAIL 0 / SKIP 6`** ⇒ L1 `[OK]` |
| ⚠️ **复核重跑（弱引用，审计路径）** | 3 + 15 | **18/18 全部 `OK 72 / FAIL 0 / SKIP 6`** ⇒ 原分组对照不成立（时间混淆） |
| ⚠️ **复核交替对照（探针路径）** | 弱 5 / 强 5 | **弱引用 5/5 `FAIL` · 强持有 5/5 `OK`** ⇒ **改动确实消除现象**（根因仍未知） |

证据：`../probes/l1_fix_20261010_out/SUMMARY.md` + `pre/`、`post/` 逐次日志。

**回归（四家离线自检，含「id 复用不得越权销毁」那条非空转注入判据）**：
`ascend 90/0/1 · kunlun 108/0/1 · cambricon 97/0/0 · ppu 112/0/1`，**与修复前逐字相同**；跨后端对称性 **7/0**。

**非空转证据（复核后的准确版）**：
该判据本身**确有牙齿** —— ① 本机用真实 `base.py` 代码构造「同一对象（真拥有）」场景 ⇒ `release_stream` 返回 `True`；
② **交替对照**下，探针序列弱引用 **5/5 FAIL**、强持有 **5/5 OK** ⇒ 判据能真 FAIL，改动也真能消除它。
⚠️ 但原「修复前稳定 FAIL 4/4 → 修复后 8/8 全绿」因**分组跑**而不足以作为因果证据。

**遗留的诚实边界**：
① 未能用调试手段钉到 CPython 分配层面的精确时序（探针本身会扰动分配序列，使该 FAIL 在插桩下不复现 ——
   典型 heisenbug），故 §4.2 里「身份复核通过」的那处**矛盾仍未解释清楚**；

② 真机复跑只做了 PPU（8/8）；**P800 容器处于 stopped 状态 ⇒ 未擅自启动**，故 P800 真机未复跑

### 4.1 现象与判据原文（修复前的原始记录）

```
[FAIL] L1 默认路径的流由厂商拥有 ⇒ release_stream 必须 no-op 返回 False（不得越权销毁）
       release_stream(默认路径的流) 返回 True —— 契约：厂商拥有的流必须 no-op 返回 False
       （越权销毁别人的流会让厂商栈内部状态崩坏，比泄漏更糟）
```

审计用例（`../../prototype/scripts/duty_response_audit.py`）：
```python
st = rt.create_stream()          # 默认路径 ⇒ 厂商拥有
rel = rt.release_stream(st)
if rel is not False: return _fail(...)
```

**为什么这条重要**：契约 §1.10 规则 2 —— 本层只能销毁**自己用 C API 建的**流；
误判归属 ⇒ 调 `cuStreamDestroy_v2` 去销毁**厂商/torch 拥有的流** ⇒ 厂商栈内部状态崩坏。
**同族的缺陷在 MLU590 上修过一次**（「id 复用越权销毁」），故不是理论风险。

### 4.3 目前能说的 / 不能说的

**能说**：
- 这是**本层（基类归属登记 + 后端登记时机）**范围内的问题，**不是**设备/厂商缺陷的表象 ——
  因为「默认路径的流不该出现在 `_owned_streams`」是本层的约定，而它出现了。
- 触发条件是**「先建本层拥有的流并弃置（K6）→ 再建默认路径的流（L1）」**这一序列；
  单点调用不复现 ⇒ **属"状态累积型"缺陷**，与 base.py 顶部注释已经记录的那一族同源
  （注释里预言的正是「`_owned_streams` 误判 ⇒ `release_stream()` 越权销毁」）。
- 反过来说：**这条判据在本栈是真能 FAIL 的**（非空转），即审计工具本身有效。

**不能说**（不下结论）：
- **不说**「守卫失效」——第 4 条里 `holder` 复核**是通过的**，与"id 复用被守卫拦下"的预期不符，
  **矛盾点尚未解释**，可能还有未发现的第三因素（例如两种 native 的登记路径混用）。
- **不改判据、不改 SKIP、不放宽措辞**（纪律：厂商/本层缺陷都不得"改判据变绿"）。
