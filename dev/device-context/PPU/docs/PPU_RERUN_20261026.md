## 3 两处如实登记

### 3.1 契约不变式段退出期 `rc=139` —— 第 5 个载体，**不是回归**（✅ **已于 10-26 收口**）

> ✅ **收口结果（2026-10-26，本报告写作之后完成）**：已采到原生现场并定位到**具体用例**
> （只有 `i3_invalidated_governed` 单独即复现）、暴露面（`_stream_ctx` 是本层最后一处弱引用）
> 与修法（改强持有）；修后该段 **`rc=0`**、判据仍 `4/4`，**13 段全量 13/13 段 `rc=0`**。
> 全文与注入对照读数见 **`PPU_EXIT_SEGV_CARRIER5_20261026.md`**；证据在
> `../probes/s06_exit_segv_20261026_out/`。⚠️ 复现时**不得在退出前手动 `gc.collect()`**（会把缺陷掩盖）。
> 下面保留写作当时（收口前）的记录，供对照。

- 现象：`s06` 判据 **4/4 PASS**、结论 `CONTRACT_INVARIANTS_PASS`，但**进程退出时 SIGSEGV**（`rc=139`）。
- 与 T11 的关系：T11 报告 §"`rc=139` 是否还会出现在别处"**原文已写明**「未验证：本轮只覆盖 PPU 的四个载体
  （两条腿 / T4 / T6）。**不得**外推为『PPU 全部退出路径已干净』」。契约不变式是**第 5 个载体**，
  首次进入全量清单 ⇒ 该结果**落在已声明边界之内**。
- **未采集原生现场**（本轮未跑 native capture）⇒ **不能断言与 T11 同签名**（`si_code=1` / `si_addr=0xab`）。
  要定性须补 `probes/run_t11_native_capture_20261014.sh` 的同类采集。
- 处置建议：① 若要收口，把该载体加入 T11 的载体矩阵（修法是机制无关的，但需确认它走的是同一条登记路径）；
  ② 在收口前，**契约不变式的判定一律以 stdout 判据为准、退出码单独标注**，不得把 `rc=139` 读成判据失败。

### 3.2 共享层缺陷：推理腿默认模型路径写死 910C（**已修**）

- 现象：`proto_infer_leg.py` 不传 `DC_MODEL` 时，默认值是 `/mnt/raid/hliu553/models/…`（**910C 专有**）
  ⇒ 在 PPU 上直接抛
  `HFValidationError: Repo id must be in the form 'repo_name' or 'namespace/repo_name': '/mnt/raid/hliu553/…'`
  （报错长得像"模型 id 格式错误"，与真实原因无关——同族于"共享层不该带实例实现"这条铁律）。
- 修法：`DC_MODEL` 显式优先 → 否则**按各实例已知布局依次探测**（910C `/mnt/raid/…` · P800/PPU `/workspace/…` ·
  MLU590 `/work/…` · P800 HF 缓存）→ 命中即用并记 `model_source`；**探测不到则早失败**并打印候选与给法（`rc=4`）。
- 三条路径真机验证：显式 `DC_MODEL` → 13/13 ✅ · 不传（自动探测）→ 13/13 ✅ · 坏路径 → 早失败并给指引 ✅
  （三者区分度均 **0.6391**）。

### 3.4 多流/事件职责的两处「假通过」（**已修**，10-26 二次修正）

判据 `C13 event.elapsed_time(end)` 首轮结果读起来像"厂商不具备"，实际是**我们自己的两处缺陷**：

| # | 现象（修正前） | 真因 | 修正 |
|---|---|---|---|
| 1 | 抛 `ValueError: Both events must be created with argument 'enable_timing=True'` ⇒ 判 **SKIP** | **统一 API 没有「建可计时事件」的入口**：`runtime/__init__.py`、`base.py` 与四家 backend 的 `create_event()` 均无参数 ⇒ 该判据在**四家恒 SKIP**，等于**从未执行过** | `create_event(enable_timing: bool = False)` 贯通公共 API / 抽象 / 四家后端；无法提供者**必须抛 `NotImplementedError`**（不静默返回不可计时事件） |
| 2 | 修正 #1 后判 **OK**，但读数 `-11.1365 ms`（负值） | C13 把方向写成了 `e2.elapsed_time(e1)`；契约是 `start.elapsed_time(end)` ⇒ 起点终点反置必得负值。而判据只校验 `isinstance(dt, float)` ⇒ **负值也算通过** | 改为 `e1.elapsed_time(e2)`，并加**量纲/方向强校验**：判据内部显式 sleep **10 ms** ⇒ `dt` 必须落在 **[5, 5000] ms**；`<5`（负值或 ≈0.01 秒）判 **FAIL** |

**真机读数（PPU `ppu0`）**：

- 设备能力本身没问题：`torch.cuda.Event(enable_timing=True)` 对 → `e1.elapsed_time(e2) = 46.2765 ms`（独立探针）。
- 判据修正后：`elapsed_time = 10.089 ms`（跨 10 ms 睡眠，落在合理带内）。
- 审计：`DUTY_RESPONSE_AUDIT ppu: OK 73 / FAIL 0 / SKIP 5（共 78 项）` · `rc=0`。

**证据**：`../probes/rerun_20261026_out/batch-c-s13-c13fix/`（假 SKIP→OK，读数 −11.14 ms 的错误方向）
与 `batch-d-s13-c13dir/`（方向与量纲修正后 10.089 ms）。

**边界（必须一并看）**：

- `enable_timing` 分支**只在 PPU 上实测过**；`kunlun` / `cambricon` / `ascend` 三家**未实测**
  （910C 处于 RAID 重建窗口）⇒ 其首次使用须按本表补读数，失败即 `NotImplementedError`，**不得**当成已支持。
- 剩余 **5 项 SKIP 全部为如实不具备/不适用**（逐项真实原因见 `batch-d-*/s13-duty.log` 的缩进明细行）：
  `D5`/`F1`（本后端无数字错误码，未声明 `error_map`）· `K2`/`K3`（**已声明** ⇒ 该分支不适用）·
  `K8`（本机区间 `(-3, 0)` 非单点 ⇒ 由 `K6` 覆盖）。
- ⚠️ **读日志的坑**：`[SKIP] <sid> <判据描述>` 打印的是**判据文本**（字面读起来像"厂商未声明"），
  **真实原因在下一行缩进的 detail**。只看 `grep "\[SKIP\]"` 会把"已声明所以不适用"误读成"不具备"。
