## 关键发现（可复用）

### 1. TP 数值等价对照必须用 greedy（纪律级）

随机采样（temperature=1.0）下 TP=1/2 输出**必然发散**——TP=2 的 HCCL all_reduce 浮点累加顺序差异被随机采样放大，实测 0/4 一致（但语义均正常）。改用 greedy（temperature=0，argmax 对微扰鲁棒）后 **4/4 逐字一致**。

> 影响：任何以「多卡输出逐字一致」为验收标准的对照实验，都应以 greedy 为前提，否则会误判为同步缺陷。

### 2. ACL 107015 根因定位（stream callback 契约）

```
rt_error_codes.h:36  ACL_ERROR_RT_STREAM_NO_CB_REG 107015 // callback not register to stream
```

单变量 A/B 对照（唯一变量 = 是否 `subscribe_report`）：

| 组 | 操作 | 返回 |
|---|---|---|
| A | `create_stream` → 直接 `launch_callback` | **107015** |
| B | `create_stream` → `subscribe_report` → `launch_callback` | **0（成功）** |

**结论：对未注册 callback 的 stream 投递 callback 即命中——调用方契约违反，非设备缺陷。**

### 3. 错误码映射表优先级高于消息语义

构造 `"device lost, error code is 507021"` 期望判 L4_FATAL，实际因 507021 已映射为 L1_RESOURCE，消息关键词**未生效**。
→ 验证 L4 类行为时，须使用**不带已知错误码**的纯消息。

### 4. 双缓冲瓶颈定位（Level1 kernel 时间线）

昇腾多流**真并发**成立（copy 与 matmul 重叠可观测），推翻「并发能力受限」推测；真实瓶颈是 `EVENT_WAIT`（3.37ms / 12 次，单次最高 391us ≈ 39 个 matmul）——**优化方向是减少同步点，而非提升并发**。

### 5. 环境结论：A 线走 vllm-ascend 官方镜像

- `VLLM_PLUGINS=fl` 会破坏 platform 选择 → `RuntimeError: Device string must not be empty`（vllm-plugin-FL 是 torch_fl 原生栈插件，与 torch_npu 冲突）。
- 昇腾平台由 `quay.io/ascend/vllm-ascend:v0.20.2rc1-a3` 镜像内置提供，vllm-plugin-FL 路线在同构 A 线不适用。

## 同步语义验证结论（FlagCX 相关）

| 项 | 结论 |
|---|---|
| TP 通信流绑定 | ✅ collective 与当前流绑定正确，all_reduce 后设备侧消费正确 |
| 异步 all_reduce 后数据可见性 | ✅ `TP_COMM_PASS 4/4`，未复现「异步无同步导致 NaN」类问题 |

> 说明：`recovery.handle_error` 仅对 L4_FATAL 触发 R2-R5 设备恢复，L1-L3 仅标记 replayable——这是 R2「避免不必要高代价重建」的设计意图，已在 P3 验证中确认。
