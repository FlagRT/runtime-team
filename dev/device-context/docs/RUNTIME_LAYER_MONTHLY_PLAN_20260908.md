## 2. 七子方向耦合关系与协同开发机制（本轮核心）

### 2.1 层次与依赖：纵切执行链 + 横切观测面

```
【运行时层外·上层】算子层 / 编译层（算子库、并行计划、统一 IR）
        ▲ 算子映射与优化诉求（经子方向 2）        ▲ 并行计划承接（经子方向 5）
┌───────┴────────────────────────────────────────┐
│ 纵切·编排层：  3 任务调度与执行引擎                │
│               （编排任务，调用 2/4/5 的能力）      │
├────────────────────────────────────────────────┤
│ 纵切·执行层：  2 算子调用适配   4 显存与缓存管理    │
│               5 分布式训练与推理支撑（多卡/上规模） │
├────────────────────────────────────────────────┤
│ 纵切·底座：    1 设备抽象与执行上下文（我们）       │
│               （统一设备/内存/流/错误/恢复）        │
└────────────────────────────────────────────────┘
        ▲ 指标与状态（被观测）           ▼ 恢复原语/定位证据（供使用）
┌───────┴────────────────────────────────────────┐
│ 横切·观测面：  6 监控诊断与可靠性（采集/检测/编排）  │
│               7 精度与性能分析（Profiling/回归）    │
└────────────────────────────────────────────────┘
```

- **纵切**：1 是底座 → 2/4/5 是执行能力层 → 3 是编排层。上层算子/编译层经 2（算子映射）和 5（并行计划）进入运行时层。
- **横切**：6/7 不在执行链上，它们**观测全部纵切层**（指标/精度/性能），并把结论**路由**回纵切层修复。

| 1↔6 | recover_device 原语（检测编排归 6、恢复执行归 1）；设备侧指标源 | 恢复编排；监控接入新芯片 |

| 5↔7 | 规模化性能数据（多卡扩展效率、通信占比） | 通信瓶颈定位（2027.01） |

### 2.3 问题定位与路由机制（替代"所有问题丢给 dc"）

**原则：先定位、后路由；谁的孩子谁抱走；跨层问题按升级路径走。**

定位主角是**横切面**（6 检测故障、7 定位精度/性能），定位结论按下表路由到**纵切层**责任方：

| 症状 | 定位工具（横切面） | 定位结果 → 责任方（纵切层） |
|---|---|---|
| **精度差距 >5%** | 7 的 Oracle-Device 回归 | 算子实现差异 → **2**（统一算子库优化适配；涉及算子实现 → **升级上层算子层联调**）；设备上下文异常（同步缺失/流语义）→ **1**；通信归约差异 → **5**；调度/显存异常 → 3/4 |
| **性能不达标** | 7 的 Profiling 三段分解 | 算子耗时 → 2/上层算子层；同步等待 → 1；显存带宽/碎片 → 4；调度等待 → 3；通信占比 → 5 |
| **任务失败/崩溃** | 6 检测 + 1 的 translate_error 分级 | L1 资源 → 4（显存扩容）或 1（重试）；L2 参数 → 上抛上层调用方；L3 执行 → 1 重放 + 3 任务重调度；L4 致命 → 1 设备恢复 + 6 编排 + 5 检查点恢复 |
| **规模化通信异常** | 5 在 8 卡/多机上检测 | 底座抽象问题 → 1 修；并行策略问题 → 5 自优；厂商通信栈缺陷 → 5 跟进厂商 |
| **长驻泄漏/稳定性** | 6 慢泄漏检测 | 设备句柄/显存泄漏 → 1；任务级泄漏 → 3/5；缓存膨胀 → 4 |
| **新芯片接入问题** | 双芯片 conformance | 接口缺失 → 1 补接口；算子映射缺失 → 2；调度不适配 → 3；以此类推 |

**路由规则**：
1. 定位责任在**横切面**（6/7 出证据），修复责任在**纵切层**（1/2/3/4/5 各归其主）；
2. 定位结论有争议 → 责任双方 + 定位方三方会诊 → 总组裁决；
3. 修复后必须**回归**：由定位方（7）复测确认闭环。

### 2.4 规模递进原则（回应"都用 2 卡通信"的问题）

**每个子方向有明确的"验证规模责任"，不重复在小规模上各自验证：**

| 递进阶段 | 规模 | 主责方 | 验证目的 | 深层问题示例 |
|---|---|---|---|---|
| **基础正确性** | 单卡 / 2 卡 | **1 设备上下文** | API 语义、流语义、错误分级、恢复能力——底座对不对 | 流同步缺失、错误误分级 |
| **规模扩展** | 8 卡 / 单机多卡 | **5 分布式支撑** | 并行策略、通信拓扑、批量策略——上量才暴露的问题 | 通信竞争、检查点一致性、跨卡同步死锁 |
| **跨机扩展** | 多机 | **5**（配合集群/网络） | 跨机通信、容错、跨机拓扑差异 | 跨机带宽瓶颈、分区容错 |
| **高并发** | 服务化高 QPS | **3 调度引擎** | 在线调度、Batch 合并、SLA 管控 | 队头阻塞、降级策略失效 |
| **规模化观测** | 全规模 | **6/7 横切面** | 指标覆盖、故障率、性能分布 | 监控盲区、精度长尾 |

**递进规则**：
1. 底座（1）的验收口径 = **最小正确规模**（≤2 卡）——dc 不负责上规模，**避免各方向都挤在 2 卡上重复验证**；
2. 子方向 5 在底座验证通过后**主动上量**（8 卡 → 多机），发现的深层问题按 §2.3 路由：底座问题回流 1，并行策略问题 5 自优；
3. 规模化数据（故障率/扩展效率）由 6 采集、7 分析，反哺下一轮递进；
4. 递进节奏与月度计划绑定：9 月基础（2 卡）→ 10-12 月模型批量（单卡为主+多卡样本）→ 2027 上半年训练框架（8 卡+多机）。

### 2.5 升级路径（跨子方向 → 跨层）

```
Level 0  子方向内解决（责任方自修）
Level 1  跨子方向联调（责任双方 + 定位方三方会诊；定位争议 → 总组裁决）
Level 2  总组升级（涉及接口规范变更、镜像/环境、进度裁决）
Level 3  运行时层外升级 —— 与上层算子层/编译层联调：
         · 算子实现级精度/性能问题（经子方向 2 发起）
         · 并行计划问题（经子方向 5 发起）
         · IR/转换器问题（经转换器方向发起）
```

**联调对（固定 pairing，每月至少一次同步）**：
`1↔5（规模化）`、`2↔7（精度定位）`、`3↔5（调度执行）`、`4↔3（显存调度）`、`6↔7（指标口径）`、`1↔6（恢复原语）`。

## 5. 月底合稿机制（制度化）

```
每月 20 日   各子方向自检：本月产物是否覆盖 §3 对应指标
每月 22 日   交叉评审：七方向轮转互查（1↔4、2↔7、3↔5、6↔全体）+ 联调对月度同步
每月 25 日   各子方向向总组提交：产物清单 + 证据链接 + 遗留问题 + 本月路由闭环统计
每月 26-28 日 总组合稿：运行时层月度报告（对外指标逐条对应产物；跨方向问题升级裁决）
每月底       提交 + 下月计划发布（子方向 1 出组件 release note）
```

**合稿固定章节模板**（运行时层月度报告，七方向分节）：
1. 本月考核指标逐条对照
2. 七子方向交付明细（各方向一节）
3. **问题路由闭环统计**（症状→定位→路由→修复→回归；闭环时长；跨方向分布）——协同机制健康度
4. 组内迭代记录（组件版本 × 下游反馈 × 修复闭环）
5. 跨层升级记录（Level 3：与算子层/编译层联调项）
6. 遗留与下月输入
