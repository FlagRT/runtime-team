# 运行时层 · 月度分工与交付计划

## 1. 运行时层七个子方向与职责域

| 关键词     | 子方向          | 职责域                                                                                                                 |
| ------- | ------------ | ------------------------------------------------------------------------------------------------------------------- |
| **设备**  | 设备抽象与执行上下文   | 抽象不同芯片 Runtime 接口，统一设备、内存和执行句柄及生命周期管理；统一 Stream 语义、Host/Device 异步传输、页锁定内存与双缓冲流水线、同步语义、错误码翻译和设备状态恢复；Backend 插件机制与注册表 |
| **算子**  | 数据流接入与算子调用适配 | 统一算子库 → 各框架默认实现的映射；算子级/实现级/芯片三级安全回调与多后端兜底；**统一算子库的优化与适配**                                                           |
| **调度**  | 任务调度与执行引擎    | 在线/离线任务调度（动态 Batch、优先级与 SLA、离线批量引擎）；检索-排序-生成流水编排                                                                    |
| **显存**  | 显存与缓存管理      | 显存池与碎片整理、峰值控制；Embedding/KV Cache 卸载、Host/Device 分层存储                                                                |
| **分布式** | 分布式训练与推理支撑   | 承接编译层并行计划，统一多卡执行、跨卡同步；**规模扩展（8 卡→多机）**；通信异常检测、任务重启与检查点恢复                                                            |
| **监控**  | 监控诊断与可靠性     | 算子与全链路指标采集；**故障检测与多级恢复的编排**（OOM/通信中断检测→路由处置）；模型热加载与多卡迁移                                                             |
| **精度**  | 精度与性能分析      | Oracle-Device 中间结果回归（精度问题定位）；性能 Profiling 助手（瓶颈定位）；Benchmark 与评测                                                    |
| **总组**  | 协调层          | stack.lock、接口约定、合入把关、跨方向联调裁决、月底合稿、**跨层升级（对接算子层/编译层）**                                                               |

**两个底座衔接约定**：

- **监控**的多级恢复**调用**设备的 `recover_device`（probe/real/hybrid）能力原语——检测与编排归监控，恢复执行归设备；
- **调度/分布式**的执行经设备的统一设备抽象获取设备/流/事件——换卡不改代码由设备保证。

## 2. 七子方向耦合关系与协同开发机制

### 2.1 层次与依赖：纵切执行链 + 横切观测面

```
【运行时层外·上层】算子层 / 编译层（算子库、并行计划、统一 IR）
        ▲ 算子映射与优化诉求（经「算子」）      ▲ 并行计划承接（经「分布式」）
┌───────┴────────────────────────────────────────┐
│ 纵切·编排层：  调度 —— 任务调度与执行引擎            │
│             （编排任务，调用 算子/显存/分布式）      │
├────────────────────────────────────────────────┤
│ 纵切·执行层：  算子 —— 数据流接入与算子调用适配       │
│              显存 —— 显存与缓存管理               │
│              分布式 —— 分布式训练与推理支撑（上规模）│
├────────────────────────────────────────────────┤
│ 纵切·底座：    设备 —— 设备抽象与执行上下文          │
│              （统一设备/内存/流/错误/恢复）         │
└────────────────────────────────────────────────┘
        ▲ 指标与状态（被观测）        ▼ 恢复原语/定位证据（供使用）
┌───────┴────────────────────────────────────────┐
│ 横切·观测面：  监控 —— 采集/检测/恢复编排            │
│              精度 —— Profiling/Oracle-Device 回归│
└────────────────────────────────────────────────┘
```

- **纵切**：**设备**是底座 → **算子/显存/分布式**是执行能力层 → **调度**是编排层。上层算子/编译层经**算子**（算子映射）和**分布式**（并行计划）进入运行时层。
- **横切**：**监控/精度**不在执行链上，它们**观测全部纵切层**（指标/精度/性能），并把结论**路由**回纵切层修复。

### 2.2 耦合关系矩阵（谁与谁有联调点）

| 方向对    | 耦合点                                       | 典型联调场景                  |
| ------ | ----------------------------------------- | ----------------------- |
| 设备↔算子  | 统一抽象上的算子执行；厂商错误 → 分级对接                    | 新芯片接入；算子报错的分级归属确认       |
| 设备↔调度  | 设备/流/事件抽象供调度使用；有界同步语义                     | 调度策略变更；SLA 超时与设备有界等待配合  |
| 设备↔显存  | memory_stats 与显存接口口径                      | 显存画像口径；碎片整理不破坏句柄语义      |
| 设备↔分布式 | 流/事件用于多卡同步；recover 用于卡故障恢复                | **规模化演练**（见 §2.4）；卡故障迁移 |
| 设备↔监控  | recover_device 原语（检测编排归监控、恢复执行归设备）；设备侧指标源 | 恢复编排；监控接入新芯片            |
| 设备↔精度  | Profiling 数据源（设备侧耗时）；自身开销基线               | 瓶颈定位中排除设备层因素            |
| 算子↔精度  | **算子精度问题定位→修复闭环**（精度对照定位 → 算子优化统一算子库）     | 精度对齐（12 月）；精度回归（持续）     |
| 算子↔上层  | 统一算子库与算子层/编译层联调                           | 算子实现级问题上升到算子层           |
| 调度↔分布式 | 调度编排调用多卡执行（任务→卡的分发）                       | 在线任务多卡分发；批量任务并行策略       |
| 调度↔显存  | 调度决策依赖显存水位（不足时排队/降级）                      | 高峰期降级策略                 |
| 分布式↔精度 | 规模化性能数据（多卡扩展效率、通信占比）                      | 通信瓶颈定位（2027.01）         |
| 监控↔精度  | 指标共享（监控采集喂给 Profiling/回归）                 | 指标口径统一（每月 22 日交叉评审）     |


### 2.3 问题定位与路由机制

定位主角是**横切面**（**监控**检测故障、**精度**定位精度/性能），定位结论按下表路由到**纵切层**责任方：

| 症状           | 定位工具（横切面）                       | 定位结果 → 责任方（纵切层）                                                                                                           |
| ------------ | ------------------------------- | ------------------------------------------------------------------------------------------------------------------------- |
| **精度差距 >5%** | 精度 的 Oracle-Device 回归           | 算子实现差异 → **算子**（统一算子库优化适配；涉及算子实现 → **升级上层算子层联调**）；设备上下文异常（同步缺失/流语义）→ **设备**；通信归约差异 → **分布式**；调度/显存异常 → **调度/显存**          |
| **性能不达标**    | 精度 的 Profiling **五段分解**         | 算子耗时 → **算子**/上层算子层；同步等待 → **设备**；显存带宽/碎片 → **显存**；调度等待 → **调度**；通信占比 → **分布式**                                           |
| **任务失败/崩溃**  | 监控 检测 + 设备 的 translate_error 分级 | L1 资源 → **显存**（扩容）或**设备**（重试）；L2 参数 → 上抛上层调用方；L3 执行 → **设备**重放 + **调度**任务重调度；L4 致命 → **设备**设备恢复 + **监控**编排 + **分布式**检查点恢复 |
| **规模化通信异常**  | 分布式 在 8 卡/多机上检测                 | 底座抽象问题 → **设备**修；并行策略问题 → **分布式**自优；厂商通信栈缺陷 → **分布式**跟进厂商                                                                 |
| **长驻泄漏/稳定性** | 监控 慢泄漏检测                        | 设备句柄/显存泄漏 → **设备**；任务级泄漏 → **调度/分布式**；缓存膨胀 → **显存**                                                                       |
| **新芯片接入问题**  | 双芯片 conformance                 | 接口缺失 → **设备**补接口；算子映射缺失 → **算子**；调度不适配 → **调度**；以此类推                                                                      |

**路由规则**：

1. 定位责任在**横切面**（**监控/精度**出证据），修复责任在**纵切层**（**设备/算子/调度/显存/分布式**各归其主）；
2. 定位结论有争议 → 责任双方 + 定位方三方会诊 → 总组裁决；
3. 修复后必须**回归**：由定位方（**精度**）复测确认闭环。

### 2.4 规模递进原则

**每个子方向有明确的"验证规模责任"，不重复在小规模上各自验证：**

| 递进阶段      | 规模         | 主责方              | 验证目的                        | 深层问题示例             |
| --------- | ---------- | ---------------- | --------------------------- | ------------------ |
| **基础正确性** | 单卡 / 2 卡   | **设备**           | API 语义、流语义、错误分级、恢复能力——底座对不对 | 流同步缺失、错误误分级        |
| **规模扩展**  | 8 卡 / 单机多卡 | **分布式**          | 并行策略、通信拓扑、批量策略——上量才暴露的问题    | 通信竞争、检查点一致性、跨卡同步死锁 |
| **跨机扩展**  | 多机         | **分布式**（配合集群/网络） | 跨机通信、容错、跨机拓扑差异              | 跨机带宽瓶颈、分区容错        |
| **高并发**   | 服务化高 QPS   | **调度**           | 在线调度、Batch 合并、SLA 管控        | 队头阻塞、降级策略失效        |
| **规模化观测** | 全规模        | **监控/精度**        | 指标覆盖、故障率、性能分布               | 监控盲区、精度长尾          |

**递进规则**：

1. 底座（**设备**）的验收口径 = **最小正确规模**（≤2 卡）——设备上下文不负责上规模，**避免各方向都重复验证**；
2. **分布式**在底座验证通过后**主动上量**（8 卡 → 多机），发现的深层问题按 §2.3 路由：底座问题回流**设备**，并行策略问题**分布式**自优；
3. 规模化数据（故障率/扩展效率）由**监控**采集、**精度**分析，反哺下一轮递进；
4. 递进节奏与月度计划绑定：9 月基础（2 卡）→ 10–12 月模型批量（单卡为主 + 多卡样本）→ 2027 上半年训练框架（8 卡 + 多机）。

### 2.5 升级路径（跨子方向 → 跨层）

```
Level 0  子方向内解决（责任方自修）
Level 1  跨子方向联调（责任双方 + 定位方三方会诊；定位争议 → 总组裁决）
Level 2  总组升级（涉及接口规范变更、镜像/环境、进度裁决）
Level 3  运行时层外升级 —— 与上层算子层/编译层联调：
         · 算子实现级精度/性能问题（经「算子」发起）
         · 并行计划问题（经「分布式」发起）
         · IR/转换器问题（经转换器方向发起）
```

**联调对（固定 pairing，每月至少一次同步）**：  
`设备↔分布式（规模化）`、`算子↔精度（精度定位）`、`调度↔分布式（调度执行）`、`显存↔调度（显存调度）`、`监控↔精度（指标口径）`、`设备↔监控（恢复原语）`。

## 5. 月底合稿机制（制度化）

```
每月 20 日    各子方向自检：本月产物是否覆盖 §3 对应指标
每月 22 日    交叉评审：七方向轮转互查（设备↔显存、算子↔精度、调度↔分布式、监控↔全体）
              + 固定联调对月度同步（见 §2.5）
每月 25 日    各子方向向总组提交：产物清单 + 证据链接 + 遗留问题 + 本月路由闭环统计
每月 26-28 日 总组合稿：运行时层月度报告（对外指标逐条对应产物；跨方向问题升级裁决）
每月底        提交 + 下月计划发布（设备方向出组件 release note）
```

**合稿固定章节模板**（运行时层月度报告，七方向分节）：
1. 本月考核指标逐条对照
2. 七子方向交付明细（设备 / 算子 / 调度 / 显存 / 分布式 / 监控 / 精度 各一节）
3. **问题路由闭环统计**（症状→定位→路由→修复→回归；闭环时长；跨方向分布）——协同机制健康度
4. **规模化递进进展**（当前规模、本轮上量发现的问题、按 §2.4 归属）——防止各方向停在 2 卡
5. 组内迭代记录（组件版本 × 下游反馈 × 修复闭环）
6. 跨层升级记录（Level 3：与算子层/编译层联调项）
7. 遗留与下月输入

## 附：本计划遵循的三条行文口径

1. **不用数字编号、不用英文别名指代方向**——统一使用 设备 / 算子 / 调度 / 显存 / 分布式 / 监控 / 精度 关键词（映射见文首表格）。
2. **定位与修复分离**——监控/精度负责"看出问题"，设备/算子/调度/显存/分布式负责"修自己的问题"；定位争议走 §2.5 升级路径。
3. **规模不重叠**——设备只到最小正确规模（≤2 卡），分布式负责 8 卡→多机上量，避免各方向在同一小规模上重复验证而错失深层问题。
