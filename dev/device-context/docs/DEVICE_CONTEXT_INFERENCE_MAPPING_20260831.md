### 4.1 验收标准 vs 用例判定的对齐说明（2026-09-02 新增）

**问题**：A3 在 conformance i6 用例中判为 PASS，但按本文档 §2 的验收标准（"重叠率可观测为正"）并未达标。
差异根源在于两者判定口径不同：

| 口径 | 判定内容 | 对重叠率的处置 |
|---|---|---|
| **conformance i6 用例** | `ok = 数据正确性`（末轮 rel_err ≤ 1e-6） | 仅作**观测输出**，不参与 PASS/FAIL 判定 |
| **本文档验收标准** | 功能（数据一致）+ **性能（重叠率为正）** | 性能项为**硬标准** |

**为何不把重叠率改成用例硬断言**：当前重叠率为负属**性能缺口**而非功能缺陷，
若加成硬断言会让 conformance 回归从 6/6 变成 5/6，掩盖"功能其实是对的"这一事实，
也会让后续每次回归因性能波动而红。故维持用例只验功能，性能缺口单列跟踪（O2）。

**纪律**：凡"功能 + 性能"复合验收项，文档须拆成两条分别标注（如 A3/D6/D8 已按此拆分），
不得用"机制通过"笼统替代性能达标。

### 4.2 吞吐口径对照（2026-09-02 重测，修正 A1 数字）

**问题**：历史记录中同一模型出现三个差异极大的吞吐数字，不可互相比较：

| 来源 | 数字 | 真实口径 | 结论 |
|---|---|---|---|
| P0 原始记录 | 19.5 tok/s | 4 条批处理、121 token / 6.21s、结果 JSON 未记模型名 | ❌ **作废**（预热不足污染，坑 A1） |
| serve（P3） | 68.4 tok/s | 4 条**串行** HTTP 请求（每次仅 1 条在飞） | ⚠️ 仅代表串行口径 |
| **同口径重测** | **283 ~ 285 tok/s** | 16 条**批量并发**、max_tokens=256 | ✅ **可信基线** |

**重测结果**（`test_tp_equivalence_rigorous.py`，16 prompt × 256 token，TP=1，`enforce_eager=True`）：

| 模型 | 加载 | 生成 | 总 token | 吞吐 |
|---|---|---|---|---|
| Qwen2.5-1.5B | 12.7s | 8.2s | 2318 | **283.0 tok/s** |
| Qwen3-4B | 14.2s | 14.4s | 4096 | **285.2 tok/s** |

**结论**：
1. 两模型批量吞吐**几乎相同**（283 vs 285）——大 batch 下瓶颈在**显存带宽**而非算力，
   故 1.5B 相对 4B 并无吞吐优势（4B 反而生成了更多 token）。
2. **批量（~284）vs 串行（68.4）差 4.2 倍**，差异来自 batching 而非模型或设备。
3. **纪律**：引用吞吐必须标注「批量/串行 + prompt 数 + max_tokens + 是否预热」，否则不可比。

### 4.3 TP 输出分叉的性质（2026-09-02 修正 A5）

**数值层面：不等价。** 16 prompt × 256 token 下仅 4/16 全长一致，一致 token 50.1%，一致前缀中位 ~80 token。

**语义层面：等价。** 分叉后两侧输出均为合理、完整、正确的答案，只是生成路径不同。三个代表性样本：

| 样本 | 一致前缀 | TP=1 | TP=2 | 判断 |
|---|---|---|---|---|
| [8] 技术博客大纲 | 0 | "1. Introduction, 2. Understanding LLMs, 3. Challenges…" | "Introduction, The Role of Inference in LLMs, Challenges…" | 两者均为合格大纲，仅编号风格不同 |
| [4] `def fibonacci(n):` | 10 | 返回**列表**版本 | 返回**标量**版本 | 两者均为正确实现，仅接口设计不同 |
| [1] 秋雨短诗 | 50 | 前 50 token 一致后分叉 | 同左 | 均围绕同一韵律要求生成 |

**规律：分叉早晚与任务的"选择空间"负相关**
- 选择空间小（质数列表、数数、markdown 表格、短确定性代码）→ **全长一致**（4/16 全为此类）
- 选择空间大（创意写作、开放式大纲）→ 早期即分叉（[8] 从第 0 个 token 起）

**定性**：这是**自回归生成 + 并行归约的固有特性**（TP 的 all_reduce 浮点累加顺序差异 → 微小数值差 →
argmax 在某步选择不同分支 → 自回归放大），**不是同步缺陷，也不是 NaN**。
与 B2（异步无同步 → NaN）性质完全不同，验收时必须区分。

**联调压测指引**：同事 B 线若观察到 TP 分叉，**不应判定为缺陷**；判定缺陷的标准是
「随机性 / NaN / 乱码 / 语义崩坏」，而非「与 TP=1 逐字不同」。

## 5. 双缓冲深挖（A4）专项设计

**问题**：DBUF2_PARTIAL，pipe 0.074s vs serial 0.005s（慢 14 倍），重叠率 -1306%。

**分段计时探针**（定位"同步退化" vs "流切换开销"）：
1. 纯传输：6 × `copy_(host_pinned, non_blocking=True)` 到固定流，墙钟（无计算）
2. 纯计算：6 × `buf@buf.sum()` 计算流，墙钟（无传输）
3. 事件链开销：6 × record/wait 空操作，墙钟
4. 大张量（2048²）复测完整流水线：计算时间 >> 同步开销时是否出现重叠
5. 结论判定：
   - 若 1 明显 > 同步拷贝理论时间 → **copy_ non_blocking 退化同步**（torch_npu 缺口）
   - 若 3 显著（每事件 ~ms 级）→ **事件链 CANN 开销主导**
   - 若 4 重叠出现 → **同步开销主导，增大计算可掩盖**（流水线设计时注意粒度）

**结论影响**：决定 torch_npu 多流方案的实现路径（低层 aclrtMemcpyAsync 封装 vs 接受同步开销 vs 事件链优化）。

### 5.2 求解结论（2026-09-02 严谨重测）

> ⚠️ **上表作废**：该表所用 `test_dbuf_sync_variants.py` 存在测量缺陷——**跨规模复用小尺寸预热**
> （用 256×256 预热后直接测 2048），导致大尺寸的首次算子开销污染 serial 基线，
> 使 n=2048 出现虚假的 +31% 正值。严谨重测后该值实为 **-15.2%**。

**严谨重测**（`test_dbuf_variants_rigorous.py`：每规模独立预热、rounds=7 取中位、
分段计时给出「拷贝+计算」无重叠基准）：

| n | 无重叠基准 | V0（12 次同步） | V1（6 次） | V4（2 次，牺牲批间流水） | V5 同流顺序 |
|---|---|---|---|---|---|
| 512 | 0.478 | 0.985 (-106%) | 0.785 (-64%) | **0.559 (-17%)** | **0.296** ← 最快 |
| 1024 | 0.911 | 0.966 (-6%) | **0.790 (+13.3%)** | **0.783 (+14.1%)** | 0.771 |
| 2048 | 3.240 | **2.194 (+32.3%)** | 2.218 (+31.6%) | 3.190 (+1.6%) | 3.330 |
| 4096 | 16.867 | **11.190 (+33.7%)** | 11.222 (+33.5%) | 16.934 (-0.4%) | 17.181 |

（单位 ms；括号内为相对「无重叠基准」的重叠率）

**三条正确结论**：

1. **转折点约在 n=1024，且各方案有清晰适用边界**：
   - `n ≤ 512`：**所有流水线方案重叠率均为负**。此时**同流顺序执行（V5, 0.296ms）比任何流水线都快**
     （V0 0.985 / V4 0.559）——小负载上流水线是纯亏。
   - `n = 1024`：V1/V4 转正（+13.3% / +14.1%），V0 仍为负（-6.0%）。
   - `n ≥ 2048`：V0/V1 达 **+32~34%**，而 V4 退化至 ~0（牺牲批间流水后，拷贝与计算无法重叠）。
2. **V4 的价值与代价都很明确**：把同步次数从 6 压到 2，同步开销从 0.507ms 降到 **0.082ms**（降 84%）；
   但丧失批间流水，大负载下反而最差。**它是小负载专用方案**。
3. **V1 是综合最稳健的选择**：n≥1024 全程为正（+13.3% ~ +33.5%），且经
   `test_dbuf_v1_equivalence.py` 验证**逐批 D2H 结果与 V0 逐位等价（最大相对差 0.000e+00）**——
   提速来自去掉「计算→D2H」这条**过度同步**（计算流本不必等回传），非牺牲功能。

**工程指引（可直接落地）**：

| 负载特征 | 建议 |
|---|---|
| 每批计算 < ~1ms（如小张量、短 chunk） | **不要流水线**，同流顺序执行最快 |
| 中等负载（转折点附近） | V1（精简同步链）或 V4（压同步次数） |
| 大负载（计算 >> 同步开销） | V0/V1 保留批间流水，重叠率可达 +30% 以上 |

**测量纪律（本次教训）**：
1. **每规模独立预热**——跨规模复用小尺寸预热 = 系统性偏差（这是 +31% 假象的根源）。
2. **重叠率的分母要用「同步拷贝 + 纯计算」**——用另一种实现的实测时间作分母会混淆口径。
3. **自身数据的反证优先于假设**——V3（计算×8）在大负载反而最差，早就提示"计算粒度决定论"不成立。
4. **"物理限制"是最危险的归因**——它把"我没搞定"包装成"不可能搞定"，且不可证伪。
   本例中所谓"物理限制"实为**实现层同步开销**（V4 证明可压降 84%），并非不可逾越。

### O2 设计要点（待细化）

瓶颈已定位：`EVENT_WAIT` **3.37ms / 12 次**（单次最高 391us ≈ 39 个 matmul）。
多流**真并发**已由 Level1 kernel 时间线证实 → **不是并发能力问题，优化方向是减少同步点**。

候选方案（待实测对比）：

| 方案 | 思路 | 风险 |
|---|---|---|
| 批量提交替代逐批事件链 | 一次提交 N 批，把 12 次 EVENT_WAIT 摊薄为 1 次 | 需改流水线结构 |
| 用 stream 间依赖替代显式 event | 减少 record/wait 调用点 | torch_npu 流依赖 API 完备性待验 |
| 增大批次摊薄同步成本 | 计算粒度 >> 同步开销时重叠自然显现（§5 第 4 点已验证此方向有效） | 不改变单位同步成本 |

**实验纪律**：最小变更 + 单变量隔离，先用 §5 的分段计时探针复现基线，再逐方案对比重叠率。

**两条重要工程语义（本次查明）**：
1. **S-8**：PyTorch 缓存分配器跨流复用内存时，必须 `tensor.record_stream(using_stream)`，否则该内存可能被分配器提前回收重用 → 数据竞争。这是多流流水线实现的硬纪律。
2. **S-9**：错误隔离是**分层的**——API 调用级错误（如 107015）只影响该次调用，其他流不受影响；但**芯片级错误（AICORE_TIMEOUT/EXCEPTION）语义上影响该设备全部流**，恢复须走设备级（aclrtResetDevice），流级重试无效。这与 D11 的 L4 分级恢复设计一致。
