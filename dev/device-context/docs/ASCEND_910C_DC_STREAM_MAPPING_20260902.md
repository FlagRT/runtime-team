## 1. 双载体与双视角

### 1.1 分布式训练载体

| 项 | 配置 |
|---|---|
| 并行方式 | **DDP**（DistributedSampler + `dist.init_process_group`），多进程对等（每进程绑一卡） |
| 后端 | `BACKEND` 参数化：`flagcx`（FlagCX torch 插件 / HCCL adaptor）或 `hccl`（torch_npu 原生） |
| 启动 | `torchrun --nproc_per_node=2 --master_port=29522 train_qwen_1_5b_npu.py` |
| 规模 | Qwen2.5-1.5B（1.54B bf16），BATCH_SIZE=1，MAX_LEN=512，AdamW，wikitext-2 |
| **基准** | **2481 步 loss 1.9501 / 4245 tok/s（flagcx）｜5428 tok/s（hccl）** |
| 本次复测 | `MAX_STEPS=100`：loss **2.64 → 1.37**、tok/s **642 → 5166**、HBM 无泄漏、进程残留 0 |
| 脚本参数化 | `BACKEND` / `MAX_STEPS` / `PROFILE` 环境变量控制 |

### 1.2 分布式推理载体

| 项 | 配置 |
|---|---|
| 引擎 | vLLM（`vllm-ascend` 官方镜像路线），`vllm serve` 长驻服务 |
| 并行方式 | **TP**（Tensor Parallel），已验 TP=1 / TP=2 / TP=4 |
| 进程模型 | **父子进程**（API Server → EngineCore spawn 子进程，非对等） |
| 通信 | HCCL（torch_npu 原生） |
| 模型 | Qwen3-4B（主）、Qwen2.5-1.5B（对照） |
| **基准** | 16 prompt × 256 token 批量：**285.2 tok/s（Qwen3-4B）｜283.0 tok/s（Qwen2.5-1.5B）** |
| 集成 | D10 错误码翻译挂接 vLLM 异常路径 + D11 设备状态监控并行运行 |

### 1.3 两侧差异的本质（为什么必须分开写）

| 维度 | 分布式训练 | 分布式推理 |
|---|---|---|
| **进程模型** | 多进程**对等**（torchrun，每进程一卡） | **父子进程**（API Server → EngineCore spawn） |
| **执行节奏** | 固定循环（每步：前向→反向→all_reduce→更新） | 动态（随请求到达，连续批处理） |
| **通信模式** | 每步一次梯度 all_reduce（**大块、低频**） | 每层 TP all_reduce（**小块、高频**） |
| **生命周期** | 有限时长（跑完即止） | 长驻（数小时至数天） |
| **核心风险** | 显存反复分配稳定性、长跑 event 泄漏、吞吐瓶颈 | 长驻泄漏、请求级错误隔离、上下文/句柄残留 |
| **失败后果** | 可从 checkpoint 重放 | 需请求级重放边界，用户可见 |

**结论**：训练侧关注"**固定循环下的稳定性与吞吐**"，推理侧关注"**长驻下的泄漏与错误隔离**"。
判据标准天然不同，**不能用推理侧证据顶替训练侧验收，反之亦然**。

### 1.4 硬件与软件栈（共用）

| 项 | 配置 |
|---|---|
| 主机 | 昇腾 910C（10.120.72.27，SSH 别名 `910C`），8 卡 × 2 chip = **16 个逻辑 NPU 设备** |
| 容器 | `flagos-infer-910c`（A 线主线） |
| 框架 | torch 2.10.0+cpu + **torch_npu 2.10.0** + transformers 5.5.3 + vLLM |
| CANN | `/usr/local/Ascend/ascend-toolkit/latest`（pyACL 可用） |

**环境坑（已归档）**：
- 训练容器 `flagos-910c-train-850` 的 torch_npu 为 2.6.0rc1（只认 1 卡），**不可用于双卡训练**
- 容器 1 号进程为 `sleep infinity`（非真 init）→ 不回收子进程，任务结束留 zombie（无害，占 PID）
- `pin_memory` 需设备预热后生效（坑 B4）

## 3. 职责详解 D1-D11（双侧对称）

### D1 封装不同芯片 Runtime 接口

**【原理】**
不同芯片 Runtime API 完全不同（ACL/aclrt vs CUDA）。职责要求统一封装，使上层无感。
昇腾侧关键选型：**vLLM 官方无 ascend platform**，必须走 `vllm-ascend` 插件路线。

**【训练侧】**
- **实现**：torch_npu + `dist.init_process_group(backend=BACKEND)`，BACKEND 支持
  `flagcx` / `hccl` 切换；`setup_flagcx_plugin.sh` 幂等安装 FlagCX torch 插件
- **完成判据**：双卡 DDP 训练闭环跑通 + loss 收敛 + 吞吐可记录
- **现状** ✅：2481 步 loss 1.9501 / 4245 tok/s（flagcx）｜5428 tok/s（hccl）

**【推理侧】**
- **实现**：`vllm-ascend` 官方镜像 + torch_npu；dense 与 TP 推理均跑通
  （曾尝试 `vllm-plugin-FL`，**失败**：其 `vendor/` 只有 metax/musa/sunrise/thead/txda，
  **无 ascend 后端**，且注明 "currently CUDA only"——已归档为**坑 A5**）
- **完成判据**：dense 推理输出正确（`DENSE_INFER_PASS`）+ TP=1/2/4 均可正常产出
- **现状** ✅

**【两侧差异】**
训练依赖 **FlagCX 插件**（HCCL adaptor）以便与通信方向对齐；
推理走 **torch_npu 原生 HCCL**（vLLM 生态更成熟）。两条路径都验证了 Runtime 封装的可用性。

**【进度】✅ 双侧达标**

---

### D2 统一设备句柄 + 生命周期管理

**【原理】**
封装 device 枚举、初始化、上下文创建销毁。核心是**防句柄泄漏**——
尤其多进程场景下，子进程持有的设备句柄退出时必须释放，否则持续占用 NPU 名额。

**【训练侧】**
- **实现**：双卡枚举（`torchrun --nproc_per_node=2`）；conformance 设备无关化
  （`--backend {npu,flagos}` 同一套用例跑两种后端）
- **完成判据**：多卡枚举正确 + 训练进程结束无设备占用残留
- **现状** ✅：双卡 DDP 完整复测后 HBM 回落基线（卡2 3161MB / 卡3 2880MB）、进程残留 **0**

**【推理侧】**
- **实现**：i1（加载后上下文可用）+ **A8 探针**（`probe_enginecore_handle_detail.py`）
  对 EngineCore 子进程做 `/proc/<pid>` 取证：
  - 运行中：**7 个 davinci fd**（均指向 `/dev/davinci_manager`）、
    设备映射 **davinci 78 + CANN 库 524 + 文件 3010（总 3619）**、RSS 5952MB
  - 停止后：EngineCore / Worker 残留均为 **0**，`released: True`
  - **口径订正**：早期"fd=1"实为去重路径数、"124 处映射"为过滤子集
- **完成判据**：加载后可用 + 子进程句柄可取证 + **正常停止与 SIGKILL 均无残留**
- **现状** ✅（SIGKILL 验证：`kill -9` 后进程 0 残留、HBM ~46GB 完全释放 →
  **坑 A2 的"SIGKILL 残留占位"在当前环境未复现**）

**【两侧差异】**
训练是**对等多进程**（结束即全部退出，验证简单）；
推理是**父子进程**（子进程可能异常退出、需单独取证，还要覆盖 SIGKILL 强杀路径）。

**【进度】✅ 双侧达标**

---

### D3 统一内存句柄 + 生命周期

**【原理】**
封装显存分配释放。训练关注的是**反复分配释放下的稳定性**（每步都分配激活值）；
推理关注的是**长驻不泄漏**（KV cache 长驻数小时）。

**【训练侧】**
- **实现**：六探针中的 `pinned_pool` 探针（锁页池画像）+ `ai_cpu_core` 探针（AI CPU core 画像）；
  训练显存与 B 线一致
- **完成判据**：反复分配释放无异常增长 + 训练全程无 OOM
- **现状** ✅：100 步完整复测 + 历史 2481 步长跑均稳定

**【推理侧】**
- **实现**：i3（KV 模拟缓冲跨流可见性）、i4（D2H 采样回传）、i5（长驻 20 轮无 NaN/Inf）+
  **serve 长驻多点采样**（Qwen3-4B TP=1）：

  | 采样点 | HBM | EngineCore RSS |
  |---|---|---|
  | T1 加载后（11:06） | 61129MB | 5855MB |
  | T2（11:08） | **61129MB（零增长）** | **5855MB** |
  | T3（12 条请求后） | +107MB（KV cache） | +81MB |
  | T4（21 分钟后 11:26） | 61237MB（与 T3 一致） | 5936MB（与 T3 一致） |
  | **T5（跨天 28 小时后 9-03 15:43）** | **61279MB（较 T4 +42MB，+0.07%）** | **5972MB（较 T4 +36MB，+0.6%）** |

- **完成判据**：分配访问正确 + **长驻窗口内 HBM/RSS 不持续增长**
- **现状** ✅：**跨天 28 小时长驻，HBM 仅增 42MB（+0.07%）、RSS 增 36MB（+0.6%），
  基本零增长无泄漏**（serve pid 21865 全程未重启，跨天观察样本）

**【两侧差异】**
训练看"**每步回收是否干净**"，推理看"**长驻水位是否走平**"。
推理允许请求后 KV cache 一次性抬升后走平（这是 vLLM 正常缓存行为，非泄漏）。

**【进度】✅ 双侧达标**

### D4 统一执行句柄

**【原理】**
抽象执行队列的提交通道。判据侧重**执行确定性**——同输入同通道多次执行结果应一致。

**【训练侧】**
- **实现**：S1-S4（流语义）+ E1-E3（事件语义）conformance 用例；
  `npu_events.py` 适配层（**未 record query 修正** + wait_host 有界等待）
- **完成判据**：S/E 系列用例全过 + 训练执行通道全程无异常
- **现状** ✅（B2 conformance 13/13、B4/B5 全过）

**【推理侧】**
- **实现**：i2 用例——固定输入做 3 轮前向（模拟 3 轮 decode），逐轮结果一致
- **完成判据**：多轮前向相对误差 < 1e-3
- **现状** ✅：**误差 0.00e+00**

**【两侧差异】**
训练有**前向 + 反向**两条执行通道（反向是训练独有）；推理只有前向，
但对**逐轮确定性**要求更高（同一请求上下文连续 decode）。

**【进度】✅ 双侧达标**

---

### D8 双缓冲流水线

**【原理】**
双缓冲（buf[0]/buf[1] 交替）+ 多流 + Event 依赖，让**第 i+1 批的 H2D 与第 i 批的计算重叠**。
重叠能否为正取决于**计算粒度 vs 同步开销**的比例——昇腾 `EVENT_WAIT` 单次约 **280μs**
（910C 实测 3.37ms/12 次），小负载下同步开销远超计算，流水线必然"亏本"。

**【训练侧】**
- **实现**：**B9/B10 回补**（2026-09-02）
  - `DataLoader(pin_memory=True)` + `batch.to(dev, non_blocking=True)`
  - 语义等价、数值不变；num_workers 保持 0（容器 fork 风险）
  - **完整复测**：双卡 hccl `MAX_STEPS=100`
- **完成判据**：训练全程无崩溃 + loss 正常收敛 + HBM 无泄漏 + 进程残留 0
- **现状** ✅：`TORCHRUN_EXIT=0` 无崩溃无 traceback；loss **2.64 → 1.37**（s50，
  历史基准 1.9 同量级）；tok/s **642 → 5166** 单调爬升；
  HBM 完全回落基线（无泄漏）；进程残留 **0** → **训练映射 11/11 全绿**

**【推理侧】**
- **实现**：`test_double_buffer_pipeline.py` **v2**——四模式真实现 + 按负载自动选型

  | 模式 | 结构 | 同步点 | 适用 |
  |---|---|---|---|
  | V0 基线 | H2D→计算→D2H 完整 event 链 | 2 wait/批 | 大负载（保留批间流水） |
  | V1 精简链 | 只保留 H2D→计算，D2H 末尾统一 wait_stream | 1 wait/批 | 中等负载（综合最稳健） |
  | V4 批量提交 | 全部 H2D→1 次同步→全部计算→1 次同步→全部 D2H | 2 次（牺牲批间流水） | 小负载（同步开销 -84%） |
  | V5 同流顺序 | 同一流顺序执行（无流水线） | 0 | 极小负载（理论下界） |

  **三档实测**（rounds=5 中位，分母 = 同步拷贝+纯计算基准；
  数据取自补 `record_stream` 后的最新运行）：

  | n | 基准 | V0 | V1 | V4 | V5 | 选型 |
  |---|---|---|---|---|---|---|
  | 512 | 0.960 | -41.7% | -16.6% | +6.5% | **+33.1%** | V5 |
  | 1024 | 1.340 | -0.1% | +15.7% | **+27.0%** | +18.1% | V4 |
  | 2048 | 3.873 | **+38.8%** | +38.1% | +12.8% | +6.9% | V0 |

  > **噪声观察**：n=512 档两次运行波动显著（V0 -25.6%→-41.7%，V4 +20.9%→+6.5%），
  > n=2048 档稳定（+40.1%→+38.8%）。印证**ms 级小负载噪声极大**；
  > 但**选型结论（V5/V4/V0）两次完全一致，选型本身稳健**。

- **完成判据**：① 功能——四模式 D2H 数据与主机参考逐批一致（**rel_err < 1e-3**，
  必须用相对误差）② 性能——按负载选型后重叠率为正（或正确降级 V5 并说明）
- **现状** ✅ `DBUF2_PASS`

**【两侧差异】**
训练侧是"**数据预取重叠**"（DataLoader 层，让下一批数据加载与当前批计算重叠）；
推理侧是"**多流流水线**"（算子层，让 H2D 与计算重叠）。
两者目标一致但层次不同——**这也是为什么训练侧回补后吞吐提升体现在 tok/s 稳定爬升**。

**【进度】✅ 双侧达标**

## 4. 多流 Stream 子项详解（S-1~S-16，双侧）

> 探针：`benchmarks/ascend_regression/probe_stream_semantics_full.py`（`STREAM_SEMANTICS_PASS 8/8`）

### S-1 流内顺序性（FIFO）

**【原理】**同一流上任务按提交顺序执行——流语义最基本保证。乱序会让依赖前序结果的算子读到未初始化数据。
**【训练侧】**S1 用例（原为框架层近似）→ 已补强（真创建流验证）
**【推理侧】**i2（同流多轮一致）+ 补强真创建流
**【实现】**在流上提交 4 个串行算子 `ones → ×3 → +2 → mean`
**【判据】**结果 = `((1×3)+2).mean() = 5.0`
**【现状】✅ 5.000000（双侧共用探针）**

### S-2 显式依赖 / 无隐式同步

**【原理】**不同流之间**无隐式同步**——流 A 完成不会自动对流 B 可见，依赖必须显式建立。
**【训练侧】**S2 用例（原为近似）→ 已补强
**【推理侧】**补强真创建两流
**【判据】**流 A 均值 = 7.0、流 B 均值 = 11.0（互不干扰）
**【现状】✅ A=7.0000 B=11.0000**

### S-3 跨流可见性（event）

**【原理】**`event.record(streamA)` + `streamB.wait_event(event)` 建立跨流依赖后结果可见。
**【训练侧】**S3 用例（真实验证）
**【推理侧】**i3 KV 模拟缓冲跨流可见性（写入流 record → 计算流 wait → 读取）
**【判据】**依赖建立后读取结果正确（S3: z 全 3）
**【现状】✅ 双侧**

### S-4 wait_stream 传递

**【原理】**`streamB.wait_stream(streamA)` = "B 等待 A 此前所有任务完成"。粒度比 event 粗
（V2 变体教训：**过度等待反而更慢**）。
**【训练侧】**S4 用例（真实验证）
**【推理侧】**—（推理侧主要用 event 粒度）
**【判据】**`b 全 10 = True`
**【现状】✅ 训练侧**

### S-5 多流并发重叠

**【原理】**多流并行，使 H2D / 计算 / D2H 重叠，隐藏传输延迟。
**【训练侧】**多流流水线（H2D / 计算 / 梯度同步）
**【推理侧】**双缓冲 v2 四模式 + TP 通信 F 场景
**【判据】**按负载选型后重叠率为正（DBUF2_PASS）
**【现状】✅ 双侧**

### S-6 集合通信与流绑定

**【原理】**集合通信应与**当前流**正确绑定：只阻塞自己所在流，**不阻塞其他流的独立计算**。
**【训练侧】**DDP 梯度 all_reduce 与流（2481 步长跑验证）
**【推理侧】**F 场景（排他证据）：流 S 通信 + 流 T 计算重叠效率 54.5%~97.7%
**【判据】**重叠效率 > 5% 且结果正确
**【现状】✅ 双侧** ⚠️ 原场景 A（"立即消费正确"）**不具排他性**，必须补 F 场景

### S-7 图捕获（graph capture）流语义

**【原理】**CUDA Graph 语义移植：录制设备工作为图，后续低成本重放，消除逐算子提交开销。
**【训练侧】**—（训练暂未使用 graph capture）
**【推理侧】**`probe_graph_capture_stream.py` 5 项验证
**【判据】**G1 capture 与 eager 一致 / G2 两次 replay 逐位一致 / G3 输入更新后 replay 用新值 /
G4 capture 内切换流正确 / G5 显式 stream 参数正确
**【现状】✅ GRAPH_CAPTURE_PASS 5/5**（rel_err 全 0）
⚠️ **踩坑**：**capture 只记录不执行，必须先 replay 才产生结果**（首版违反此语义误判 G1/G2）

### S-8 默认流 vs 命名流 + 跨流分配器安全 ★

**【原理】**关键陷阱：PyTorch 缓存分配器按流跟踪内存。若 tensor 在流 A 分配、在流 B 使用后
于流 A 释放，分配器**不知道流 B 还在使用**，可能重分配给流 A 的新 tensor → **数据竞争**。
**正确做法**：`tensor.record_stream(using_stream)` 显式告知分配器。
**【训练侧】**共用探针验证（训练侧多流同样适用此纪律）
**【推理侧】**探针验证 + **修复真实缺口**：双缓冲 v2 的 V0/V1/V4 缓冲在命名流间传递
但**未调 record_stream**——当前"碰巧安全"仅因 Python 引用长期持有，
一旦改为批间释放即暴露竞争。已补并注明。
**【判据】**默认流/命名流各自正确 + `record_stream` 后跨流复用正确（10.0）
**【现状】✅ 双侧（含实现修复，重跑三档仍 DBUF2_PASS）**

### S-9 流错误隔离（分层）★

**【原理】**错误隔离是**分层的**：

| 层级 | 影响范围 | 恢复方式 |
|---|---|---|
| **API 调用级**（如 107015） | 仅该次调用失败 | 修正前置条件，其他流不受影响 |
| **设备级**（507014 AICORE_TIMEOUT / 507015 AICORE_EXCEPTION） | **该设备全部流** | 必须**设备级恢复**（`aclrtResetDevice`），**流级重试无效** |

**【训练侧】**共用探针（训练侧同样适用；梯度同步出错时的隔离边界同理）
**【推理侧】**流 A 注入真实 107015，验证流 B 仍正常
**【判据】**流 A `rc=107015` 且流 B 结果正确（6.0）
**【现状】✅ API 级已实测** ⚠️ **设备级为语义推断**——
依据 `rt_error_codes.h` 定义与 D11 分级设计推断，**未做真实触发**（触发风险高）

### S-10 流/事件生命周期与配额

**【原理】**流与事件是有限资源，长期运行需防耗尽。
**【训练侧】**★ **真实缺陷已修复**：每步累积 ~120 个 aclrtEvent → 补析构 + work 完成语义
（这是**训练长跑才会暴露**的问题，短跑测试发现不了）
**【推理侧】**500 次创建销毁后仍可正常创建使用新流
**【判据】**长跑无累积 + 循环后新流可用且结果正确（9.0）
**【现状】✅ 双侧（训练侧有真实修复案例）**

### S-11 跨流内存分配

**【原理】**流 A 分配的设备内存，经显式依赖后可被流 B 安全使用。
**【训练侧】**共用探针
**【推理侧】**流 A 分配 → event → 流 B `wait_event` → 流 B 使用
**【判据】**流 B 使用结果正确（6.0）
**【现状】✅ 双侧**

### S-12 流优先级

**【原理】**昇腾支持流优先级（`aclrtCreateStreamWithConfig(stream, priority, flag)`，
priority 范围 **0~7**）；`aclrtDeviceGetStreamPriorityRange(least, greatest)` 查询范围。
**【训练侧】**共用探针（通信流可设高优先级以加快梯度同步）
**【推理侧】**查询范围 + 多流并发正确性
**【判据】**范围查询成功 + 并发结果正确
**【现状】✅ leastPriority=7 / greatestPriority=0**——**值越小优先级越高**

⚠️ **调度效果**（高优先级是否真优先）需压力测试，非职责验收项

### S-13 多设备流绑定

**【原理】**流绑定于创建时的当前设备，多卡场景下各卡流相互独立、不互串。

**【推理侧】**双设备各建独立流，结果 [2.0, 3.0] 正确不互串

## 5. 关键纠错历程（3 项错误结论的撤回与重做）

> **"看起来达标"比"知道没达标"更危险。**

| # | 原错误结论 | 错误性质 | 修正后 |
|---|---|---|---|
| 1 | **D8/A3**：n≤1024 重叠率为负系"物理限制" | **归因错误 + 不可证伪** | 实为**实现层同步开销**（V4 可压降 84%），非硬件不可逾越 |
| 2 | **A5**：TP=1/2/4 greedy 逐字一致 4/4 | **样本量不足** | 16×256 下**数值不等价**（4/16，50.1%）但**语义等价** |
| 3 | **A1**：dense 推理 19.5 tok/s | **测量污染** | 同口径重测 **283.0 tok/s**（预热不足，差 14.5 倍） |

### 纠错 1：为什么"物理限制"是危险归因
规模扫描复测：n=512 的 V1 实为 **-41.0%**（首轮 +21.6% 是噪声）；
严谨重测（每规模独立预热 + rounds=7）n=2048 实为 **-15.2%**，
之前"+31%"是**跨规模复用小尺寸预热**导致 serial 基线被高估的假象。
**V3 反证早就在表上**（计算×8 却只有 15.5%，低于 V0 31.0%）——
直接说明"计算粒度决定论"不成立，但当时只挑了支持假设的行看。

### 纠错 2：TP 分叉是固有特性而非缺陷
**对照实验**：TP=1 vs TP=1（重跑）**100% 一致** → 排除调度变量；
TP=1 vs TP=2 **50.1%** → 分叉源自 TP 并行归约顺序差异。
**分叉后语义质量**：[8] 博客大纲两个都是正确答案；[4] fibonacci
TP=1 返回列表版 / TP=2 返回标量版——**均正确**。
**结论**：是"选择分叉"非质量退化；分叉早晚与任务选择空间负相关。
**判别标准**：应看「随机性 / NaN / 乱码 / 语义崩坏」，**不是「与 TP=1 逐字不同」**。

### 纠错 3：吞吐口径
| 数字 | 口径 | 可信度 |
|---|---|---|
| 19.5 tok/s | P0 的 4 条批处理 | ❌ 预热不足污染 |
| 68.4 tok/s | 4 条**串行**请求 | ✅ 但非批量峰值 |
| **283.0 / 285.2** | 16 prompt × 256 token **批量** | ✅ **同口径基准** |

批量（284）vs 串行（68.4）差 4.2 倍来自 batching；
两模型吞吐接近 → 大 batch 下瓶颈在**显存带宽**而非算力。

## 9. 附录 C：方法沉淀（测量与归因纪律）

> 用 3 次纠错换来的，适用于所有昇腾性能与语义验证工作。

1. **自身数据的反证优先于假设** —— V3 的反常早就在表上，不能只挑支持假设的行看
2. **测量必须按被测规模预热** —— 跨规模复用小尺寸预热 = 系统性偏差（+31% 假象根源）
3. **样本量要匹配结论强度** —— 256 token 撑不起"数值等价"这类强结论
4. **因果结论前先排除替代解释** —— 自重复对照 / 可逆性对照（TP=1 自重复 100%）
5. **"物理限制"是最危险的归因** —— 把"我没搞定"包装成"不可能搞定"，且不可证伪
6. **验证 ≠ 集成** —— 集成才暴露真实边界（框架错误类型、异步语义、进程管理）
7. **证伪 ≠ 求解** —— 证伪只是起点，要继续做实验直到拿到"什么是对的"

**补充四条工程纪律**：
- **数据一致性判据用相对误差**（主机/设备累加顺序不同，绝对差随规模增长）
- **比值型指标检查极端比例下的区分度**（改用 `实际节省 / 理论最大可节省 min(a,b)`）
- **多流传递内存必须 `record_stream`**（缓存分配器跨流复用会提前回收）
- **错误隔离分层认知**（API 级可流级重试；设备级必须设备级恢复）

**双侧验收纪律（本轮新增）**：
- **训练侧与推理侧判据必须各自成立，不能互相顶替**
- 训练抓"固定循环下的稳定性与吞吐"，推理抓"长驻下的泄漏与错误隔离"
- 两侧互补：训练长跑抓到 event 泄漏，推理集成抓到分级缺口
