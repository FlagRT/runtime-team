# 多芯片环境与代表算子验证（2026-09-09）

> 本文记录当天跨芯片探索，不作为本月 910C 锁定基座验收。周会后的主线规划见 [STATUS](../STATUS.md) 与 [9 月任务规划](框架接入与安全回退-9月任务规划-20260909.md)。

## 结论与边界

本轮新增检查昆仑芯 P800、平头哥 PPU、壁仞三类资源。平头哥已验证原生算子、FlagGems 直接调用及现有注册机制；壁仞验证了 BF16 原生算子，但 FP16 有错误；昆仑芯停在环境使用权限。

这是**跨芯片基线与接入机制验证**，不是把 Ascend 的 `PreferGems` 安全选择原型移植到了这些芯片，也不是完成了多芯片安全回退。没有运行训练、加载模型、测试 vLLM 推理、多卡通信或性能。

| 平台 | 连接与资源快照 | 本轮结果 | 下一步条件 |
|---|---|---|---|
| 昆仑芯 P800 | SSH 成功；8 个 P800 OAM 设备，单设备 96 GiB；14:51 的设备 3–7 为 0 MiB / 0% | Docker socket 拒绝访问，认证后的 `sudo -l` 也拒绝；宿主机默认 Python 没有 torch / FlagGems / Triton，未执行算子 | 管理员授权 Docker 或分配可用的个人开发环境；有空卡不等于已有环境权限 |
| 平头哥 PPU-ZW810E | SSH 成功；16 个设备，单设备 96 GiB；使用物理设备 1，容器只识别一个逻辑设备 | 原生 8/8；FlagGems 直接调用 8/8；现有 `use_gems` 注册、数值与退出恢复 8/8 | 可作为第二个接入开发平台；仍需做安全选择规则、异步及模型验证 |
| 壁仞 Biren166M | SSH 成功；8 个设备，单设备约 63.5 GiB；使用物理设备 1 | 数据拷贝和 FP32 加法通过；BF16 SiLU / RMSNorm 共 4/4；FP16 两个算子均在首个 shape 报错 | 先限定已通过的 BF16 小输入；核实 FP16 的镜像支持情况；当前镜像未安装 FlagGems |
| NVIDIA | 尚无可直接使用的 SSH 信息 | 未测试；本地资料仅有平台注册入口 | 获取明确的服务器/平台资源后另测 |

资源占用只代表检查时刻；重跑前仍需查看设备使用情况。平头哥本轮经现有网络直接 SSH 成功，没有操作 VPN、绑定 MFA 或修改网络配置。

## 测试内容

脚本：`probes/cross_vendor_smoke.py`。每种模式单独启动进程，推理模式下使用固定随机种子 135：

- 算子：标准 `torch.nn.functional.silu`、`rms_norm`；或直接调用 FlagGems 对应函数。
- 输入大小：`(1, 128)`、`(7, 512)`；FP16、BF16；RMSNorm 单个末维、带权重、eps=1e-6。
- 数值参考：CPU FP32 SiLU / RMSNorm 公式。FP16 atol/rtol=0.005，BF16=0.03；没有为了通过测试而放宽阈值。
- 检查输出设备与 dtype 不变，输入和权重不被修改；设备操作显式同步。CPU 仅作测试参考，不是运行时回退目标。
- 注册模式使用现有 `flag_gems.use_gems(include=[op])`；通过 Python 调用跟踪确认确实进入 FlagGems 函数，退出作用域后不再进入该函数，原生调用数值仍正确。
- 支持 `--dtype` 和 `--op` 单独指定，便于把失败路径放到独立进程中排查。发生执行错误直接退出，不做异常后的原生重试。

这些是小输入冒烟测试，不能替代完整算子兼容性、精度或性能验收。没有测试非连续输入、反向传播、compile、其他线程/进程、并发注册及与外部替换机制组合。

## 平头哥记录

版本：torch 2.9.0、FlagGems 5.0.1rc0、Triton 3.5.0+ppu2.0.0.oe；宿主机驱动 1.5.1-1d747a。
镜像 ID：`ffbf86430046`；完整镜像名和 SHA256 见 `evidence-multichip-20260909/ppu/environment.txt`。

个人容器 `flagos-cgu135-probe-ppu` 使用现有镜像，4 CPU / 32 GiB RAM / 2 GiB shm，只映射 `/dev/alixpu`、`/dev/alixpu_ctl`、`/dev/alixpu_ppu1`。源码和结果保存在宿主机 `/home/cgu135/framework-adapter-ppu`，挂到 `/workspace/cgu135`。

初次把物理编号 1 直接写成 `CUDA_VISIBLE_DEVICES=1` 时，容器内设备初始化失败。该单设备映射下逻辑编号为 0；改为每次 exec 显式传入 `CUDA_VISIBLE_DEVICES=0` 后识别为 `cuda:0`，device_count=1。**已有容器创建配置仍是 1，因此复现必须保留下列 exec 覆盖参数。**未修改宿主机驱动。

```bash
# 先确认设备 1 没有他人的运行任务，再启动自己的容器。
sudo docker start flagos-cgu135-probe-ppu
for probe_mode in native gems registration; do
  sudo docker exec -e CUDA_VISIBLE_DEVICES=0 flagos-cgu135-probe-ppu \
    timeout -k 5 240 python /workspace/cgu135/cross_vendor_smoke.py \
    --device cuda:0 --mode "$probe_mode"
done
sudo docker stop flagos-cgu135-probe-ppu
```

依赖边界：脚本不导入 vLLM、不启动模型，但该镜像里的 FlagGems 导入后会间接加载 vLLM 的部分模块。首轮 `gems.log` 的 8 组算子均通过，最后因探针原先的“不得有 vLLM 模块”断言而失败；随后将这一项改成如实记录依赖，未改数值条件，重跑 `gems-v2.log` 和 `registration-v2.log` 均通过。因此只能说“不通过 vLLM 模型入口运行”，不能说“这套镜像完全不依赖 vLLM”。

## 壁仞记录

版本：torch 2.8.0+cpu、torch-br 1.8.7.20800+br1xx、Triton 3.6.0；FlagGems 未安装。`torch-br` 提供 `supa` 设备后端，torch 版本带 `+cpu` 不代表无法调用壁仞设备。
镜像为 `birensupa-smartinfer-vllm:26.07.09-py310-pt2.8.0-vllm0.21.0-c066s001t001b24145-br1xx`（ID `081634a335d4`），镜像 SDK 为 `1.10.0.0-24145.lkg`；宿主机 brsmi 报驱动/SUPA 1.12.0。仅记录组合，不把版本差异直接认定为错误根因。

个人容器 `flagos-cgu135-probe-biren` 使用 `biren` runtime，4 CPU / 24 GiB RAM / 2 GiB shm，只显式映射 `/dev/biren/card_1`、`/dev/biren-m`；个人目录 `/home/cgu135/framework-adapter-biren` 挂到 `/workspace/cgu135`。

环境初始化需要 source 镜像自带 `brsw_set_env.sh`，否则 `import torch_br` 缺少 `libsupti.so.1`。单设备映射下显式覆盖 `SUPA_VISIBLE_DEVICES=0`、`CUDA_VISIBLE_DEVICES=0` 后 `torch.supa` 识别一个 `Biren166M`，编号 `supa:0`。初次错误 mask 的测试进程异常后没有及时退出，已通过停止并重启**自己的**容器清理；之后探针禁用 core dump 并设置超时。

| 精度 / 算子 | 结果 |
|---|---|
| BF16 SiLU | 两种 shape 通过 |
| BF16 RMSNorm | 两种 shape 通过 |
| FP16 SiLU | `(1,128)` 报 `Failed to find supa function`，错误参数中为 FP16 pointwise；后续 shape 未运行 |
| FP16 RMSNorm | `(1,128)` 报 `BRCopy.cpp:279` / `BR Torch Internal Error`；后续 shape 未运行 |

FP16 失败不应转换成静默的跨设备或跨精度回退；本轮也没有这么做。尚未证明错误属于哪个具体软件层，不能泛化成“壁仞不支持 FP16”。BF16 各路径在独立进程验证，避免沿用已报错的进程。

```bash
sudo docker start flagos-cgu135-probe-biren
sudo docker exec -e SUPA_VISIBLE_DEVICES=0 -e CUDA_VISIBLE_DEVICES=0 \
  flagos-cgu135-probe-biren /bin/bash -c '
    ulimit -c 0
    source /usr/local/birensupa/br_container_tools/brsw_set_env.sh
    timeout -k 5 120 python3 /workspace/cgu135/cross_vendor_smoke.py \
      --plugin torch_br --device supa:0 --mode native --dtype bfloat16
  '
sudo docker stop flagos-cgu135-probe-biren
```

隔离测试最终日志为 `native-精度-算子-v2.log`。无 `-v2` 的四份分类日志是最初 shell 包装参数被 source 脚本消耗后的 argparse 错误，不计为算子失败或通过；保留便于追溯。完整首轮 `native.log` 和独立 `basic.log` 也保留。
