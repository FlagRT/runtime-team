# dev/model-defs —— 场景对齐参考模型定义与构建代码

> 状态：新建（2026-09-21）

## 1. 本目录的职责

对**跨方向复用的场景对齐参考模型**做归档：模型来自哪里（预训练 checkpoint 的
准确 tag，或需要自定义架构代码的模型）、架构由什么组成、如何构建/做最小可用性验证。

**只回答**：这个模型是什么、代码/权重从哪来、怎么构建、怎么做最小验证。

**不回答**：为什么选它、用在验收流程的哪个环节、要不要接入某个运行时后端——
这些由 `docs/` 阶段目标文档（见「更新说明」）、各子方向 `STATUS.md` 声明，
不在本目录重复。（与 `dev/images/README.md` 对镜像目录的职责边界原则一致。）

## 2. 结构

```
dev/model-defs/
├── README.md              # 本文件：职责 + 规范 + 结构
├── model_list.md           # 索引：场景 → 模型 → 当前版本/来源 → 状态
└── <model-name>/           # 只有需要自定义架构代码的模型才建目录
    ├── README.md           # 该模型跨版本共性说明（场景归属、谁在用、上游出处）
    └── v<N>/                # 一个版本一目录，多版本共存，目录本身不可变
        ├── model.py         # 架构定义
        ├── config.py        # 构建配置
        ├── build.py         # 构建入口 + 最小可用性验证（smoke test）
        ├── README.md        # 该版本说明：来源、超参、已验证范围、使用方式
        ├── requirements.txt # 依赖（能少则少）
        └── LICENSE          # 若代码来自外部开源项目，原样保留其 license
```

纯 checkpoint 型模型（如 `OneRec-8B`，无自定义代码，直接拉 HuggingFace 权重）
**不建目录**，只在 `model_list.md` 登记 tag / commit，避免和真正的代码目录混淆。

## 3. 命名与版本化

- `<model-name>/v<N>/` 目录不可变，对应一次架构/接口定稿。
- 架构或接口有变更 → 新建 `v<N+1>/`，旧目录保留，旧版本首行加
  `> superseded_by: v<N+1>`。
- 不影响已有接口的措辞修正（改 README 描述、补充注释）：直接改当前版本目录，
  不必新开版本。
- （与 `docs/` 阶段目标文档 §8.1、`dev/images/README.md` §3 的版本化规则一致。）

## 4. 设计原则（跨方向复用、跨芯片迁移的前提）

- **环境无关**：模型定义只使用稳定、跨 torch 版本兼容的 `torch.nn` 原语；
  不硬编码设备（cpu/cuda/npu/...）、不 `import` 任何厂商专属包
  （如 `torch_npu`）。设备选择是调用方的事——模型代码本身要能不改一行地被
  拷进任意芯片的容器里跑。这一条是本目录存在的核心前提：模型如果和特定
  torch 版本/芯片环境强绑定，就失去了"总组统一维护、各方向直接复用"的意义。
- **优先复用主流开源方案**：如果目标模型已有通用、主流、且本身就与具体环境
  解耦的开源实现（如 DeepFM 之于 `rixwew/pytorch-fm`），直接vendor该实现
  （保留原始 license、注明来源与改动），不重复造轮子；只有确无合适上游时才
  从零写。是否"主流"以社区认可度（star 数、是否 archived、更新活跃度）和
  实现是否干净解耦（无强绑定的数据/设备依赖）综合判断。
- **零/最小外部依赖**：构建与最小验证（`build.py`）不要求联网、不要求真实
  数据集，任何机器/容器装好 `requirements.txt` 就能跑通 smoke test。
- **可独立拷贝**：整个 `<model-name>/v<N>/` 目录可被其他方向原样复制到自己
  项目里使用，内部只用同目录相对 import，不依赖 `dev/model-defs/` 之外的路径。
