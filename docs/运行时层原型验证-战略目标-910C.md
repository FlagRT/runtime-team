# 运行时层原型验证 — 战略目标文档（910C）

> 状态：战略目标定稿 ｜ 范围：昇腾 910C 单芯片 ｜ 验收模型：`Qwen/Qwen3-Embedding-0.6B`
> 本文档面向运行时层全体子方向（device-context / communication / memory / performance），是原型阶段的唯一目标依据，内容自成一体，不依赖其他文档解读。

---

## 1. 战略目标

**本月内，在 910C 单芯片、两个版本锁死的镜像上，跑通"2 卡分布式微调 + 单卡推理服务"两段式 demo，验证运行时层核心能力（设备执行上下文管理、多卡通信、显存管理、监控与故障恢复）真实可用，并产出统一验收报告。**

不追求：跨芯片适配、生产级性能调优、自研任务调度与框架接入能力（见 §5 范围说明）。

---

## 2. 现状概述

- **device-context（设备执行上下文）**：进展最扎实，设备句柄、内存句柄、执行句柄、流/事件管理、错误处理、状态恢复等各项能力已在同构 910C 的训练与推理场景下逐项验证通过；但部分资产仍带着此前一条已放弃的自研设备层方案（`torch_fl`）的命名痕迹，且相关改动一直未合入团队公共开发分支。
- **communication（多卡通信）**：计划中的多项任务大部分尚未启动。经核查，实际的通信库适配、双卡训练问题定位与修复工作，此前已经由 device-context 方向的同学做过一遍——名义上属于通信方向的工作，技术产出并未正式沉淀为该方向自己的资产。已决定由 device-context 与 communication 共同承担相关工作，具体分工见 §5。
- **memory（显存与缓存管理）**：设备层技术路线刚完成一次调整（放弃自研设备层，统一采用芯片厂商官方设备插件方案）。在另一款芯片上已有显存卸载的实测数据；在 910C 上，官方推理框架的原生显存卸载路径目前不可用，基础的显存画像工作需要在新锁定的环境上重新做一遍。
- **performance（性能评测）**：验证依赖独立仓库维护，目前本地验证均为部分完成状态，相关镜像尚未发布到团队可稳定拉取的镜像仓库。
- **环境现状**：910C 上同时存在多套镜像（此前自研设备层方案遗留的开发底座镜像、通用算子运行时镜像、集成了通信库的算子运行时镜像、芯片厂商官方推理镜像），已出现过因镜像版本不一致而污染实验结论的情况。本文档已将本次原型所需环境收敛为两个锁定镜像（见 §4）。

---

## 3. 验收 Demo 定义

**模型**：`Qwen/Qwen3-Embedding-0.6B`

| 段 | 内容 | 主责 |
|---|---|---|
| 段一 | 2 卡分布式微调 | device-context + communication（共同承担） |
| 段二 | 单卡推理服务（推理框架锁定版本见 §4） | device-context 主导，memory 提供显存侧支撑，performance 采集性能数据 |

**验收标准**（全部满足 = 原型达成）：

1. 段一：2 卡分布式微调在锁定训练镜像内跑通，loss 正常下降，全程无死锁、无数据错乱，多卡通信正确性（如全量规约、全量收集等集合通信操作）有对照证据。
2. 段二：单卡推理服务在锁定推理镜像内正常启动，产出向量结果正确，有吞吐/时延数据。
3. 两段验证过程中，至少注入一次真实错误，能观察到"统一错误识别 → 恢复处理"的完整闭环。
4. memory 方向产出锁定环境下的显存池定义与显存占用峰值画像（KV 缓存相关验证不作为本次硬性指标，理由见 §7）。
5. performance 方向产出一份基于两段 demo 实际证据自动生成的统一验收报告。
6. 全程只使用 §4 锁定的两个镜像，不引入第三方临时镜像或容器。

## 5. 各组职责、依赖与交付

### 总组（协调层）
- 维护 `dev/stack.lock.910c.yaml` 与接口约定文档，任何变更需知会全组
- 组织跨方向联调，裁决进度卡点
- **合入把关（适用于全部子方向的合入门槛）**：一项改动要合入团队公共开发分支，须同时满足——① 使用的镜像与 `dev/stack.lock.910c.yaml` 一致 ② 容器/分支命名合规 ③ 自己负责的接口约定章节已写完，且至少有一个下游方向确认可用 ④ 能跑通自己负责的那段 demo ⑤ 没有引入新镜像或新的环境分叉。五项全部满足即可合入，不再等待额外信号。

### device-context ＋ communication
两方向围绕"段一：2 卡分布式微调"共同交付，具体工作：

1. 在锁定训练镜像上复现设备执行上下文各项能力（设备句柄、内存句柄、执行句柄、流/事件管理、错误处理、状态恢复）
2. 打通 2 卡分布式微调（`Qwen/Qwen3-Embedding-0.6B`），并完成通信正确性验证（全量规约、全量收集、点对点收发等）
3. 整理此前已定位的通信库昇腾适配问题与核心缺陷修复，形成可提交的干净改动
4. 产出一份最小可用的通信接口约定说明（覆盖通信组生命周期、常用集合通信操作、异步完成语义、能力声明）
5. 将设备执行上下文能力打包为独立可复用的组件（三大句柄 + 流/事件 + 错误处理 + 状态管理 + 恢复逻辑），去除历史自研路线遗留的命名痕迹

**交付物**：训练腿闭环证据（loss 曲线 + 通信正确性记录）、通信库改动的干净提交、通信接口约定文档、设备执行上下文可复用组件
**验收对应**：§3 验收标准第 1、3 条；接口约定文档中设备执行上下文与通信两个章节定稿

### memory
**依赖基座**：训练腿与推理腿镜像均可能涉及（画像覆盖两段场景）

1. 在锁定推理镜像上重新完成一轮显存画像（此前基于旧环境的结论需要在新锁定环境上复核）
2. 定义推理框架层的显存池与复用/回收策略，产出对照数据
3. ⚠️ **显存分层缓存、按需释放、向 Host 溢出等能力**，在本次验收模型上没有天然的验证场景（该模型是一次性前向计算出向量，不存在生成式模型那种随生成步数持续增长的缓存占用）——本次不作为硬性指标，相关验证继续用现有的生成式模型场景单独进行，不影响本次原型的整体验收

**交付物**：锁定环境下的显存画像报告、显存池定义文档 + 对照数据
**验收对应**：§3 验收标准第 4 条

### performance
**依赖基座**：两个锁定镜像

1. 将两个锁定镜像发布到团队可稳定拉取的镜像仓库，记录固定的镜像标识，并回写到 `dev/stack.lock.910c.yaml`
2. 在锁定镜像上跑通基础规格评测用例，确保执行、测量、监控三方面状态均正常完成
3. 为两段 demo 采集性能数据（训练侧吞吐、推理侧吞吐与时延），采集口径需对齐（相同预热方式、相同并发设置）
4. 产出统一验收报告，汇总设备执行上下文与通信、memory 两个方向的验证证据及性能数据

**交付物**：镜像标识记录、基础规格评测结果、demo 性能数据、统一验收报告
**验收对应**：§3 验收标准第 2、5 条

### 现状收编：框架接入能力与任务调度能力（本月不新增实现）

对应规划中"统一框架接入与多级安全回退"、"动态批处理与任务调度"两块能力：

- 本月原型验收**不要求新增实现**，两者直接沿用推理框架自带的默认行为。
- 但要求：此前接触过这两块内容的相关人员，无论是调研结论、测试记录还是复现进展，不论完整与否，都按照运行时层统一的子方向目录规范（README 说明目标与现状、docs 存放调研与执行记录、probes 或 benchmarks 存放脚本）整理后提交，纳入统一管理，作为后续正式排期的基础。
- 由总组负责找到现有材料的持有人并推动其提交；提交内容本身不计入本次原型验收范围。

## 6. 推进步骤（阶段式，不含具体时间点）

1. **基座对齐**：`dev/stack.lock.910c.yaml` 落地；公共或各子方向的容器配置切到锁定镜像；接口约定文档搭好框架；device-context 与 communication 就共同任务范围完成对齐。
2. **单腿打通**：训练腿（2 卡分布式微调）与推理腿（单卡服务）分别在各自锁定镜像上独立跑通，两者互不等待。
3. **接口约定与自查**：各方向把自己负责的接口约定章节写完；逐条过一遍 §4 自查清单；提交待合入的改动。
4. **合并与联调**：按 §5 合入把关标准逐条核对，满足即合入；随后做跨方向联调（通信与设备执行上下文互相验证、memory 的显存池方案对接推理腿）。
5. **验收与固化**：跑通两段 demo，产出统一验收报告，固化本次原型作为后续基线；汇总遗留能力缺口（框架接入与调度能力、跨芯片扩展、更大规模的通信性能验证等）作为下阶段输入。

## 7. 风险与待确认项

- **memory 方向的验证场景与验收模型不完全匹配**：`Qwen/Qwen3-Embedding-0.6B` 不存在生成式模型那种随生成步数增长的缓存占用，显存分层缓存相关能力本次难以验证——已相应收窄该方向的交付范围（见 §5），需确认是否认可。
- **推理框架对该类模型的服务化支持尚未验证**：建议在推理腿工作开始时优先确认，避免后续才发现需要绕路解决。
- **镜像发布节奏**：performance 方向需尽快完成镜像发布，否则其他方向自查清单中"镜像来源核对"这一项无法真正落实。
