## 1. 决策①：吸收 sync 修复（声明式覆盖层方式）

### 1.1 技术事实（round 3 已证实）

- 缺 sync 假说真机 2 卡证实：broadcast/all_gather 无 sync 复现错误（目标 rank
  收不到数据 / 恒返回全零），加 sync 后全转 PASS。
- DDP 的参数一致性校验走 C++ 层
  （`torch._C._distributed_c10d._verify_params_across_processes`），Python
  猴子补丁绕不过——修复必须落在 FlagCX/vllm_fl 自己的 communicator 实现。
- FlagRT fork commit `5d545c9`（作者 seanl）正是打在那个位置：all_reduce 后
  追加 sync + all_gather 覆盖实现（逻辑与基类一致 + sync），另含
  vocab_parallel_embedding 的 bool*int 显式 int64 转换（PrivateUse1 类型提升
  bug，token id 坍缩成 1）。

### 1.2 为什么不直接用 fork、也不放弃修复

- 整体切 fork：fork 与上游 release/0.2 已分叉（非祖先关系），违背"纯公开血统"
  原则，补丁债利息越滚越高。
- 放弃修复：训练腿真实 loss/吞吐数据永远出不来，v3 验证目标无法收口。

### 1.3 落地方式（已完成）

1. `git format-patch -1 5d545c9` 原样导出（内容零修改）→
   `dev/images/ascend-operator-runtime/v3/assets/patches/vllm-plugin-FL/0001-fix-ascend-int64-mask-promote-flagcx-sync.patch`
2. 实测验证：上游 release/0.2 tip `8b059122e` 领先 fork 基点 19 提交，但**均未
   碰 patch 涉及的两个文件**；`git apply --check` 干净套用零冲突（两轮验证）。
3. `Dockerfile.repro` vllm-plugin-FL 层改为：fetch pin commit → `git apply
   --check`（fail-closed）→ `git apply` → pip install。
4. `lock.yaml` 该层 origin `official` → `official+custom-overlay`，记录
   overlay_patches（来源 commit / sha256 / 套用基线 / 保质期）。

### 1.4 保质期与上游回流

- 保质期：上游合入该修复并出现在 release/0.2 后，删除整个覆盖层，Dockerfile.repro
  回退纯上游 pin。
- upstream-first 已启动：PR 文本草稿见附录 A。注意点：修复的原始验证环境是
  torch_fl（flagos）路径，本血统是 torch_npu（Route A）——PR 描述如实写明，
  不夸大适用范围；v3 真机重验（PENDING）同时服务于本侧置信度与 PR 证据。

## 2. 决策②：shmem 缺口（官方开关解堵 + 跨组要出处）

### 2.1 技术事实（round 3 发现）

- 触发链：vllm_fl worker 初始化 → `USE_FLAGGEMS` 为真 → `flag_gems.enable()`
  全量注册 → `torch.cos`（RoPE cos/sin cache 计算）被 FlagGems Triton-Ascend
  算子透明接管 → grid-stride-loop kernel 分支生成代码间接 `import shmem`
  （来自 triton tle/dsa/ascend 的分布式共享内存实验性扩展）→ 模块缺失 →
  CompilationError → engine core 初始化失败。
- `shmem` 不是公开 PyPI 包（镜像源 404），Dockerfile.repro 从未涉及。

### 2.2 为什么选黑名单而不是另两个候选

| 候选 | 判定 | 理由 |
|---|---|---|
| **VLLM_FL_FLAGOS_BLACKLIST=cos**（选用） | ✅ | 插件一级支持的官方开关（vllm_fl/worker/worker.py 读取），零代码改动；只影响 cos 一个算子，拉回 torch_npu 原生；可逆（env 层随时撤）；不遮掩问题——其他算子若同样触发会如实暴露 |
| 装来路不明 shmem wheel | ❌ | 供应链红线：不知来源的包不进结论性验证镜像 |
| 手写空 shmem stub | ❌ | 最差选项：让"FlagGems 在 Ascend 有缺口"的事实消失，后续炸得更隐蔽 |
| USE_FLAGGEMS=false 总开关 | 备选未选 | 影响面过大：FlagGems 全部算子回退原生，等于本轮完全不验证 FlagGems 路径 |

（第三个候选方向"对 embedding 模型完全不激活 FlagGems"由总开关实现，同上备选。）

### 2.3 落地方式（已完成）

- `dev/images/ascend-operator-runtime/v3/docker-compose.flaggems-cos-off.yml`：
  opt-in 叠加层，仅一条 `VLLM_FL_FLAGOS_BLACKLIST=cos`。
- `docker compose config` 实测：与 routeA 层合并后环境变量正确注入。
- 用法：`dev/lib/up.sh <routeA.yml> <flaggems-cos-off.yml>`（up.sh 自动做
  pins 校验；本层无 pins 文件，属"只改一个环境变量的探索层"，符合 ENV-SPEC §2）。

### 2.4 根因归属与跨组需求

根因是**FlagTree（triton）tle/dsa/ascend 扩展的依赖声明缺口**：生成的 kernel
代码 import 了 shmem，但 FlagTree 的发布物（源码/wheel/预构建基座镜像）既不带
该模块、也未在任何文档/依赖清单声明其出处。这是算子编译组的发布形态问题，本组
侧 hack 不出来（康威定律：架构上限受组织边界约束）。跨组需求文本见附录 B。

## 附录 B：跨组需求——shmem 官方出处（转算子编译组）

> 【2026-10-09 升级重写：round 4 真机验证证明这不是"单算子缺依赖"，是
> 结构性缺口，影响所有含 for 循环的 Triton kernel 编译，包括 vLLM 框架
> 自己的 kernel。原按 cos 单算子写的版本已删除，以下为现行版本。】

> 主题：FlagTree triton（ascend 线）的 tle 扩展在模块顶层无条件
> `import shmem`，导致任何含 for 循环的 kernel 编译失败；请求官方修复
> 或给出 shmem 的官方获取渠道

**现象与根因（我们侧，910C 真机实测，npu1-11，2026-10-09）**：

- `triton/experimental/tle/__init__.py` 第 1 行 `from . import backends` →
  `backends.py:13 _build_ascend_impl` 在 ascend 环境**无条件**
  `import shmem`（`language/dsa/ascend/communication.py:6`）。
  实测 `import triton.experimental.tle` 直接 ModuleNotFoundError。
- ascend 后端的编译器前端（`spec/ascend/compiler/code_generator.py:1197`，
  visit_For）对**任何** for 循环都 `import triton.experimental.tle`——
  即任何含 for 循环的 kernel 编译即炸，与用哪个算子无关。
- **影响面超出 FlagGems**：vLLM 框架自己的 kernel
  （`vllm/v1/worker/block_table.py::_compute_slot_mapping_kernel`）同样
  命中。而 vllm-plugin-FL 的黑名单开关（VLLM_FL_FLAGOS_BLACKLIST）只
  作用于 FlagGems 接管的 torch 算子，管不到 vLLM 核心 kernel——下游
  无法用配置完全规避。
- `shmem` 模块（华为 aclshmem 的 Python 绑定）：不在 ascend3.5 预构建
  基座镜像内、`pip show shmem` 未装、公开 PyPI 无此包（镜像源 404）、
  FlagTree wiki ascend 用户手册未提及。镜像内 grep 确认无任何 aclshmem
  python 绑定。
- 后果：vLLM 推理 engine 初始化即失败（CompilationError），且只有真实
  模型前向才触发（静态自检/构建全绿），对下游是隐蔽缺口。
- 我们当前的临时解法（供参考，不建议长期依赖）：注入一个所有函数都
  loud-fail 的 shmem 占位模块（stub）让编译期 import 通过——单卡推理
  全程不会真正调用其中函数（有对照组证明），但任何真正需要分布式
  共享内存的 kernel 会立刻报错，只适用于单卡场景。

**请求（按优先级）**：
1. **修复 import 方式**：把 tle 顶层/backends 的无条件 `import shmem`
   改为惰性加载（真正用到分布式通信功能时才 import）——这是根治，
   下游零改动。
2. 若短期不便改代码：明确 `shmem`（aclshmem python 绑定）的官方出处
   （华为 CANN 配套件？FlagTree 自建？哪个版本线？），给出可写进
   Dockerfile 的获取方式，并补进依赖声明/基座镜像。
3. 若两者都短期无法提供：请在 wiki 标注"哪些代码模式会触发 tle 路径"
   （目前已知：任何 for 循环，含 grid-stride-loop 风格生成的 kernel），
   便于下游评估规避面。

**证据链**：
- 复现与解堵对照日志：~/tmp-reproV3-r4/infer-leg/（round-2.log 含
  vLLM 核心 kernel 命中的完整栈；control-no-blacklist.log 为对照组；
  round-5.log 为解堵后 9/9 PASS）
- 占位模块源码：`dev/images/ascend-operator-runtime/v3/assets/shmem_stub.py`
- 机制分析：`dev/images/ascend-operator-runtime/v3/REBUILD.md`

## 附录 B-2：跨组需求——FlagCX c10d 层异步返回修复（转 FlagCX/通信方向）

> 【2026-10-09 新增，round 4 真机二次实证】

**现象**：flagcx backend 的 `all_gather_into_tensor`（及 DDP 启动检查
用到的路径）异步返回——调用立刻返回但数据未就绪，调用方按同步语义
立即读取时得到全零。PyTorch DDP 的 C++ 启动检查
（`_verify_params_across_processes`）因此失败（"rank0 有 338 个参数、
其他 rank 0 个"），DDP 封装无法使用。

**证据（npu1-11，2×910C，双 rank 一致）**：
- nosync 读取：FAIL（全零）；加 `torch.npu.synchronize()` 后读取：PASS
  （~/tmp-reproV3-r4/train-leg/outputs/flagcx_sync_test.log、probe_agit.log）
- vllm_fl Python communicator 侧的同类修复（补 sync）已在我们的镜像
  补丁层验证有效，但 Python 层补丁覆盖不到 c10d 路径——修复必须落在
  FlagCX 自己的 c10d ProcessGroup 实现。

**请求**：在 FlagCX c10d 层为异步返回的 collective 补同步语义（或按
PyTorch 约定返回可等待句柄），使 DDP 开箱可用。最小复现脚本：
`dev/images/ascend-train-comm/v3/assets/flagcx_sync_test.py`。
