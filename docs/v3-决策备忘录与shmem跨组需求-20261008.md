## 1. 决策①：吸收 sync 修复（声明式覆盖层方式）

### 1.1 技术事实（round 3 已证实）

- 缺 sync 假说真机 2 卡证实：broadcast/all_gather 无 sync 复现错误（目标 rank
  收不到数据 / 恒返回全零），加 sync 后全转 PASS。
- DDP 的参数一致性校验走 C++ 层
  （`torch._C._distributed_c10d._verify_params_across_processes`），Python
  猴子补丁绕不过——修复必须落在 FlagCX/vllm_fl 自己的 communicator 实现。
- FlagRT fork commit `5d545c9`（作者 seanl）正是打在那个位置：all_reduce 后
  追加 sync + all_gather 覆盖实现（逻辑与基类一致 + sync），另含
  vocab_parallel_embedding 的 bool*int 显式 int64 转换（PrivateUse1 类型提升
  bug，token id 坍缩成 1）。

### 1.2 为什么不直接用 fork、也不放弃修复

- 整体切 fork：fork 与上游 release/0.2 已分叉（非祖先关系），违背"纯公开血统"
  原则，补丁债利息越滚越高。
- 放弃修复：训练腿真实 loss/吞吐数据永远出不来，v3 验证目标无法收口。

### 1.3 落地方式（已完成）

1. `git format-patch -1 5d545c9` 原样导出（内容零修改）→
   `dev/images/ascend-operator-runtime/v3/assets/patches/vllm-plugin-FL/0001-fix-ascend-int64-mask-promote-flagcx-sync.patch`
2. 实测验证：上游 release/0.2 tip `8b059122e` 领先 fork 基点 19 提交，但**均未
   碰 patch 涉及的两个文件**；`git apply --check` 干净套用零冲突（两轮验证）。
3. `Dockerfile.repro` vllm-plugin-FL 层改为：fetch pin commit → `git apply
   --check`（fail-closed）→ `git apply` → pip install。
4. `lock.yaml` 该层 origin `official` → `official+custom-overlay`，记录
   overlay_patches（来源 commit / sha256 / 套用基线 / 保质期）。

### 1.4 保质期与上游回流

- 保质期：上游合入该修复并出现在 release/0.2 后，删除整个覆盖层，Dockerfile.repro
  回退纯上游 pin。
- upstream-first 已启动：PR 文本草稿见附录 A。注意点：修复的原始验证环境是
  torch_fl（flagos）路径，本血统是 torch_npu（Route A）——PR 描述如实写明，
  不夸大适用范围；v3 真机重验（PENDING）同时服务于本侧置信度与 PR 证据。

## 2. 决策②：shmem 缺口（官方开关解堵 + 跨组要出处）

### 2.1 技术事实（round 3 发现）

- 触发链：vllm_fl worker 初始化 → `USE_FLAGGEMS` 为真 → `flag_gems.enable()`
  全量注册 → `torch.cos`（RoPE cos/sin cache 计算）被 FlagGems Triton-Ascend
  算子透明接管 → grid-stride-loop kernel 分支生成代码间接 `import shmem`
  （来自 triton tle/dsa/ascend 的分布式共享内存实验性扩展）→ 模块缺失 →
  CompilationError → engine core 初始化失败。
- `shmem` 不是公开 PyPI 包（镜像源 404），Dockerfile.repro 从未涉及。

### 2.2 为什么选黑名单而不是另两个候选

| 候选 | 判定 | 理由 |
|---|---|---|
| **VLLM_FL_FLAGOS_BLACKLIST=cos**（选用） | ✅ | 插件一级支持的官方开关（vllm_fl/worker/worker.py 读取），零代码改动；只影响 cos 一个算子，拉回 torch_npu 原生；可逆（env 层随时撤）；不遮掩问题——其他算子若同样触发会如实暴露 |
| 装来路不明 shmem wheel | ❌ | 供应链红线：不知来源的包不进结论性验证镜像 |
| 手写空 shmem stub | ❌ | 最差选项：让"FlagGems 在 Ascend 有缺口"的事实消失，后续炸得更隐蔽 |
| USE_FLAGGEMS=false 总开关 | 备选未选 | 影响面过大：FlagGems 全部算子回退原生，等于本轮完全不验证 FlagGems 路径 |

（第三个候选方向"对 embedding 模型完全不激活 FlagGems"由总开关实现，同上备选。）

### 2.3 落地方式（已完成）

- `dev/images/ascend-operator-runtime/v3/docker-compose.flaggems-cos-off.yml`：
  opt-in 叠加层，仅一条 `VLLM_FL_FLAGOS_BLACKLIST=cos`。
- `docker compose config` 实测：与 routeA 层合并后环境变量正确注入。
- 用法：`dev/lib/up.sh <routeA.yml> <flaggems-cos-off.yml>`（up.sh 自动做
  pins 校验；本层无 pins 文件，属"只改一个环境变量的探索层"，符合 ENV-SPEC §2）。

### 2.4 根因归属与跨组需求

根因是**FlagTree（triton）tle/dsa/ascend 扩展的依赖声明缺口**：生成的 kernel
代码 import 了 shmem，但 FlagTree 的发布物（源码/wheel/预构建基座镜像）既不带
该模块、也未在任何文档/依赖清单声明其出处。这是算子编译组的发布形态问题，本组
侧 hack 不出来（康威定律：架构上限受组织边界约束）。跨组需求文本见附录 B。

## 附录 A：上游 PR 草稿（flagos-ai/vllm-plugin-FL，release/0.2）

> 标题：`fix(ascend): synchronize flagcx all_reduce/all_gather + explicit int64 mask cast`

**Body 草稿：**

```
Two fixes for the Ascend (torch_npu / Route A) path, both verified on real
910C hardware (2-card container):

1. CommunicatorFL.all_reduce: the flagcx c10d backend returns asynchronously;
   without torch.npu.synchronize() the caller reads stale/zero data.
   Reproduced: broadcast target-rank receives nothing, all_gather returns
   all-zeros; adding sync turns both PASS.
2. CommunicatorFL.all_gather: override base-class implementation (same logic)
   to add the same synchronize after all_gather_into_tensor.
3. AscendVocabParallelEmbedding: explicit .to(torch.int64) on bool masks
   before int multiply. On PrivateUse1 backends the bool*int promotion
   returned bool, collapsing token ids to 1.

Note: originally validated on the torch_fl (flagos) path in an org fork
(FlagRT/vllm-plugin-FL@5d545c9); re-validation on the default torch_npu
path is in progress (results will be linked). Patch applies cleanly on
release/0.2 tip (8b059122e).

Co-authored-by: (原修复作者署名保留)
```

## 附录 B：跨组需求——shmem 官方出处（转算子编译组）

> 主题：FlagTree triton（ascend 线）tle/dsa/ascend 扩展生成的 kernel 依赖
> `shmem` 模块，发布物未声明出处，请求官方获取渠道

**现象**（我们侧，910C 真机，FlagGems @f7ae8e6b + FlagTree triton 3.5.1）：
- `torch.cos` 被 FlagGems Triton-Ascend 算子接管，张量形状命中
  grid-stride-loop 风格 kernel（`ext.num_programs(0)` 分支，
  `ext = flag_gems.utils.triton_lang_extension`）。
- 该分支生成代码间接 `import shmem as ash`（来源
  `triton/experimental/tle/language/dsa/ascend/communication.py`，Ascend
  "分布式共享内存"实验性扩展）。
- `shmem` 模块：不在 ascend3.5 预构建基座镜像内、`pip show shmem` 未装、
  公开 PyPI 无此包（镜像源 404）、FlagTree wiki ascend 用户手册未提及。
- 后果：vLLM 推理 engine 初始化即失败（CompilationError），且只有真实模型
  前向才触发（静态自检/构建全绿），对下游是隐蔽缺口。

**请求**（按优先级）：
1. 明确 `shmem` 的官方出处（华为 CANN 配套件？FlagTree 自建？哪个版本线？），
   给出可写进 Dockerfile 的获取方式。
2. 若属 FlagTree 自身依赖：请在依赖清单/发布物中补齐（wheel 依赖声明或基座
   镜像内置），避免下游逐个踩坑。
3. 若短期无法提供：请在 wiki 标注"哪些算子形状会触发 tle/dsa 路径"，便于
   下游用黑名单规避（我们目前用 VLLM_FL_FLAGOS_BLACKLIST=cos 规避 cos）。

`dev/images/ascend-operator-runtime/v3/REBUILD.md`「ROUND 2/3 真机验证结果」
