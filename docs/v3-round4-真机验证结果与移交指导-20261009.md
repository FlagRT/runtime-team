## 四、训练验证结果

在 2 张 910C 卡上测试,结论三条:

1. **通信缺陷确认**:FlagCX 的多卡数据交换函数(all_gather 系列)返回时
   数据尚未写完,立即读取得到全零;同步后再读取结果正确。双卡、正反对照
   结果一致。
2. **训练跑通**:采用"交换后显式同步再读取"的手动写法规避后,Qwen2.5-1.5B
   训练 24 步,loss 由 2.89 降至 2.55,约 5 秒一步。学习率需设为 1e-5:
   默认的 5e-5 在 bf16 精度下于第 16 步出现数值溢出(NaN),属数值问题,
   与通信无关。
3. **PyTorch 原生 DDP 封装暂不可用**:DDP 初始化时的内置校验(C++ 层)
   触发上述同一通信缺陷,而本组补丁位于 Python 层,无法覆盖该路径。修复
   责任在 FlagCX(见第五节缺陷二)。在修复前训练采用手动写法。

## 五、两个遗留缺陷(均为外部组件问题)

**缺陷一:shmem 软件包缺失,影响面大于原记录。**

FlagGems 加速库和 vLLM 框架均使用 Triton 语言编写 kernel。Triton 工具链的
tle 子模块在加载时会无条件 import shmem 模块,而该模块既不在 FlagTree
工具链发布的镜像中,也无法从公开软件源获取。后果:**任何含 for 循环的
kernel 在编译阶段即失败**,包括 vLLM 框架自身的 kernel。因此,将个别算子
排除出加速库的黑名单只能解决 FlagGems 一侧,vLLM 一侧必须依靠占位模块
(stub)使编译通过。占位模块的所有函数在被实际调用时均直接报错;对照实验
证明单卡推理全程未实际调用这些函数,不影响计算结果。**根治方为算子编译
方向**(改为按需加载,或将 shmem 官方化);该 import 写死在工具链代码中,
无法通过更换 FlagGems/Triton 版本解决。

**缺陷二:FlagCX 通信函数异步返回,阻塞 DDP。**

见第四节第 1、3 条。本组补丁已修复推理侧的 Python 调用路径(真机验证
通过),但 DDP 走 C++ 底层路径,须由 FlagCX 自行修复。**无法通过更换
FlagCX 版本解决**:问题位于其 C++ 实现,且当前所用版本即公开主干。

两个缺陷均不影响"版本选型是否正确"的判断。本轮全部验证表明现有选型
(基座/PyTorch/vLLM/插件/Triton/FlagGems/FlagCX 的精确版本)在真机上
成立,定版无返工风险。
