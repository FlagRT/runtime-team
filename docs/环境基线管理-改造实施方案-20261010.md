> 状态:方案待审。适用范围:`dev/images/` 下全部自建镜像,以及基于这些镜像启动的全部运行环境。
> 关联:设计依据 `docs/运行时基座建设-黄金准则与方案存档.v1.md`(本方案修订其 GR3/GR5 与 §3,

## 1. 目标形态

| 对象 | 是什么 | 基线文件回答的问题 |
|---|---|---|
| **镜像** | 构建完成即不可变的制品,由 image id 寻址 | 这个镜像固化了哪些资产,各自是什么版本 |
| **运行环境目录** | 一个目录 = 一套完备的运行环境:`docker-compose.yml`(启动与装配细节)+ 基线文件(版本事实),基于一个指定镜像创建一个运行实例 | 这个运行实例用的是哪个镜像,另外以可编辑方式挂载了哪些 repo,各自在哪个 commit |

基线文件兼具两种职责:

- **可读**:任何人打开文件即可看到全部资产与版本;每个 commit 附分支名与提交时间,仅供阅读,不参与校验。
- **可配置**:由管理脚本生成(export)、核对(check)、按其切换宿主 repo(load);不手工编写。

基线文件不参与 compose 的创建、启动与运行过程本身,它是全组遵循的环境记录规范。
每个镜像附带一个 demo 运行环境目录,记录该镜像验收时使用的准确运行配置,同时作为该镜像的推荐用法。
镜像的消费方可在任意位置建立自己的运行环境目录,推荐同样包含 `docker-compose.yml` 与导出的基线文件。

## 2. 核心边界:固化资产与挂载资产

一个 repo 属于哪一类,由它的**代码从哪里来**决定,与产出方、变更频率无关(变更频率决定的是"应该放进哪一类",见 §2.3):

| | 固化资产(baked) | 挂载资产(mounted) |
|---|---|---|
| 定义 | 代码在构建期进入镜像文件系统 | 代码来自宿主目录,运行时经 volume 挂载并以可编辑方式生效 |
| 版本归属 | 镜像(由 image id 唯一确定) | 运行实例(由启动时宿主 repo 的 HEAD 确定) |
| 记录位置 | 镜像基线文件 | 运行环境基线文件 |
| check | 不核对宿主 repo(宿主检出与镜像内容无关);只核对本地镜像 id | 核对宿主 repo HEAD 与工作区状态 |
| load | 不处理 | 将宿主 repo 切换到基线中的 commit |

### 2.1 判定规则

- **镜像场景**:解析 `Dockerfile.repro` 中把代码带入镜像的指令,只收录真正固化的 repo,详见 §4.2。
  - 本组构建层不允许以 editable 方式安装:代码固化在镜像中时,editable 没有意义;代码依赖挂载时,镜像又不再自包含。export 遇到时报错。
  - 父镜像继承来的 editable 安装,按"源码是否位于镜像内"判定:位于镜像内即为固化资产,记录并标注 `install: editable-in-image`,同时给出提示,不报错。实例:L1 官方基座中的 vLLM 为 `-e git+…@bc150f50`,源码在 `/vllm-workspace/vllm`。
- **运行环境场景**:只收录 compose 中**显式声明**为可编辑挂载的 repo,声明方式见 §3.2。
  - 仓根整体挂载到 `/workspace` 只使代码"可见",不等于"生效",不自动收录。

### 2.2 同一 repo 既固化又挂载

允许这种情况,用于在镜像基线之上调试某个组件。规则如下:

- 运行环境基线中该 repo 标注 `overrides_baked: true`,并同时显示镜像内的固化版本。
- compose 的生效方式必须确保挂载版本优先,例如 `pip install -e` 覆盖安装或 `PYTHONPATH` 前置。check 会对此给出提示。

### 2.3 资产在两类之间迁移

| 动作 | 触发条件 | 结果 |
|---|---|---|
| 晋升(挂载 → 固化) | 该组件本阶段验证冻结 | 写入新版本镜像 `v<N+1>/` 的构建配方,构建后 export 镜像基线;按 GR7 留痕 |
| 下放(固化 → 挂载) | 需要在现有镜像上快速迭代该组件 | 在运行环境 compose 中声明挂载,形成 §2.2 的覆盖关系;镜像不变 |

"长期固化"与"短期可编辑"之间的边界由这两个显式动作跨越,不存在隐式状态。

## 3. 文件形态

- `info` 块仅供阅读,不参与任何校验。

### 3.2 运行环境目录

```
<任意位置>/<环境名>/
  docker-compose.yml      # 启动与装配;可用 compose 原生 include/extends 引用镜像 demo 作为基线,只写差异
  env.baseline.yaml       # 由 baseline.py export 生成,不手工编辑
  .last-check.json        # up.sh 每次 check 的结果(不追踪)
```

在 `docker-compose.yml` 中用顶层扩展字段声明本环境,工具只读取本目录这个文件中的声明:

```yaml
x-flagrt:
  image_baseline: ../../images/ascend-train-comm/v3/image.baseline.yaml
  mounted_repos:
    vllm-plugin-FL: {activation: pip-editable}      # 或 pythonpath
```

`env.baseline.yaml` 的结构如下:

```yaml
schema: flagrt.baseline/v1
kind: container
generated_by: dev/lib/baseline.py export <env-dir>
generated_at: <export 时间>
compose: docker-compose.yml

image:                       # 抄录自 image.baseline.yaml;check 只核对本地镜像 id
  ref: ...
  id: sha256:...
  baseline: ../../images/ascend-train-comm/v3/image.baseline.yaml

baked_repos: {...}           # 原样抄录自镜像基线,只读;check 与 load 均不处理

mounted_repos:               # check 与 load 的对象
  vllm-plugin-FL:
    host_path: vllm-plugin-FL                # 相对 WORKSPACE_ROOT
    container_path: /workspace/vllm-plugin-FL
    activation: pip-editable
    commit: <40 位 sha>
    dirty: false
    overrides_baked: true                    # 镜像中也固化了该 repo(§2.2)
    info: {branch: release/0.2, committed_at: ...}
```

## 4. 管理脚本:`dev/lib/baseline.py`

### 4.1 动作与场景

| 动作 | 镜像场景(`--image <image-dir>`) | 运行环境场景(`<env-dir>`) |
|---|---|---|
| **export** | 解析 Dockerfile 判定固化资产,读取已构建镜像的标签取得 commit,两者交叉核对后生成 `image.baseline.yaml` | 抄录镜像基线的固化部分;读取 `x-flagrt.mounted_repos` 对应宿主 repo 的 HEAD、工作区状态与提交元数据,生成 `env.baseline.yaml` |
| **check** | 本地镜像 id 与镜像标签是否与基线一致 | 本地镜像 id;每个挂载 repo 的 HEAD 是否等于基线 commit、工作区是否干净 |
| **load** | 不适用(镜像只能重新构建,不能切换) | 将每个挂载 repo 切换到基线 commit;不拉取、不构建镜像 |
| show(只读) | 以表格打印资产、版本、层级与 info | 同左,并标出覆盖关系 |

退出码:0 表示一致或成功;1 表示存在不一致(check)或核对失败(export);2 表示用法或文件格式错误;3 表示 load 被安全规则中止。

### 4.2 镜像场景的 Dockerfile 判定规则

只识别以下模式,其余模式一律报错,不做猜测:

1. `COPY src/<Repo>/ …`,随后对该路径执行非 editable 的 `pip install` → 固化 repo,构建上下文来源。
2. `git remote add origin <url>` + `git fetch … ${<X>_COMMIT|REF}` → 固化 repo,构建期拉取来源。
3. `FROM ${…}` → 父镜像。
   - 若父镜像有自己的 `image.baseline.yaml`,则展开继承;
   - 若是外部基座,则从镜像中读取 `pip list --editable` 与 pip freeze 补全 L1 资产。
4. `curl … ${<X>_URL}` / `COPY assets/<file>` → 固化资源。
5. 本层出现 `pip install -e` → 报错(§2.1)。

commit 的取值以**已构建镜像的 `io.flagrt.*.commit` 标签**为准,Dockerfile 的 ARG 只用于交叉核对,两者不一致即报错。
标签是构建时写入镜像的事实;v3 镜像已具备全部五个 repo 的 commit 标签,已在本机核实。

### 4.3 运行环境场景的行为

- **export**:
  - 挂载 repo 工作区不干净时,记录 `dirty: true` 并给出警告;
  - 加 `--require-clean` 时拒绝导出,用于验收或出结论的环境。
- **check**:
  - 镜像 id 不一致、或挂载 repo commit 不一致,均报告为不一致;
  - 工作区不干净时给出警告;
  - 固化部分不与宿主比对。
- **load**:
  - 任一挂载 repo 工作区不干净 → 整体中止(退出码 3),不做部分切换,并列出不干净的 repo;
  - 本地缺少目标 commit → 先 `git fetch` 再切换;
  - 切换结果为 detached HEAD,同时打印每个 repo 切换前的 commit 与分支,以便回退。
- **up.sh `<env-dir>` [`--strict`]**:
  - 先执行 check。默认只报告不一致、不阻止启动;加 `--strict` 时,不一致即拒绝启动(用于验收与出结论的运行)。
  - 然后执行 `docker compose -f <env-dir>/docker-compose.yml up -d`。
  - check 结果写入 `<env-dir>/.last-check.json`。

## 6. 对现行文档与机制的影响

| 现状 | 改造后 |
|---|---|
| `pins.<tag>.yaml`:人工编写,strict 条目校验的是宿主检出,而 v3 中 strict 的三个 repo 均为固化资产,运行时不读宿主代码 | 镜像侧 `image.baseline.yaml`、运行环境侧 `env.baseline.yaml`,均由工具生成;固化资产只由镜像 id 约束 |
| 黄金准则 GR3:按变更频率分"静态/动态挂载点",与交付方式混在一起 | 交付方式决定校验方式(§2);变更频率只决定资产放在哪一类(§2.3) |

| `.env_provenance.json`:全局单份,只记录期望值 | 每个运行环境目录各自的 `.last-check.json`,记录实测值 |
| 多文件 `-f` 叠加组成一个环境 | 一个目录 = 一个环境;基线复用通过 compose `include`/`extends`(本机 Docker Compose v2.29.7 已支持) |
| `lock.yaml`(人工编写的血统档案) | 保留,继续记录构建过程、已知问题与验证结果;版本事实以 `image.baseline.yaml` 为准,`lock.yaml` 引用它,不再重复填写 commit |

不改动 `dev/stack.lock.910c.*.yaml`。

## 7. 风险与约束

- Dockerfile 解析只覆盖 §4.2 列出的模式。配方写法变化时 export 会报错,需要同步扩展规则,这是有意为之:宁可报错,也不误收录。
- 分支名仅供阅读:同一 commit 可能位于多个分支,工具优先取远端分支,并列出全部包含该 commit 的分支。本机未检出的仓库(如 FlagTree)需要联网获取。
- v1/v2 镜像缺少 commit 标签,不在本次范围内;如需补齐,另行从各自的 `lock.yaml` 回填。
- load 修改宿主 repo 状态,在共享机器上可能影响同机其他人使用同一份检出;运行环境目录宜在个人检出上使用。
