# 运行时层原型验证 — 阶段目标文档（910C）

> 状态：阶段目标定稿（2026-09-09）｜ 范围：昇腾 910C 单芯片 ｜ 验收模型：`Qwen/Qwen3-Embedding-0.6B`
> 本文档面向运行时层全体子方向（device-context / communication / memory / performance / 调度 / 监控），是原型阶段的唯一目标依据，内容自成一体，不依赖其他文档解读。

---

## 1. 阶段目标

**本月内，在 910C 单芯片、两个锁定镜像上（训练腿为组内自构建、已验证可重建的镜像，见 §4），跑通"2 卡分布式微调 + 单卡推理服务"两段式 demo，验证运行时层核心能力（设备执行上下文管理、多卡通信、显存管理、任务调度、监控与故障恢复）真实可用，并产出统一验收报告。**

不追求：跨芯片适配、生产级性能调优、算子层实现。

---

## 2. 现状概述

- **device-context（设备执行上下文）**：进展最扎实，统一运行时 API + Backend 注册表已交付，昇腾（torch_npu）与 flagos（torch_fl）双后端 conformance 全绿；训练腿 2 卡微调、推理腿服务化、错误注入→恢复闭环均已在锁定镜像上拿到真实证据。
- **communication（多卡通信）**：训练腿的通信正确性（all_reduce/all_gather/P2P 对照）已由 device-context 在打通训练腿过程中一并验证；本方向的核心工作是把已定位的通信库昇腾适配问题整理为可提交的干净改动、完成通信接口约定章节定稿，并承接后续的规模化通信验证。
- **memory（显存与缓存管理）**：设备层路线已定（Route A，各芯片厂商官方设备插件）；910C 上华为昇腾官方推理框架（vLLM-Ascend）的原生显存卸载路径当前不可用，基础显存画像需在锁定镜像上重新完成。
- **performance（性能评测）**：验证依赖独立仓库维护；负责两个锁定镜像的发布状态登记与统一验收报告产出。
- **调度、监控**：本月起首次纳入统一目标体系。
- **设备注册路线**：Route A（各芯片厂商官方设备插件，昇腾 = 华为昇腾官方 torch_npu）为全组主线；训练腿因锁定镜像的环境约束，本月使用 flagos（torch_fl）接入，为该镜像下的例外，不代表路线变更（见 `dev/stack.lock.910c.v1.yaml`）。
- **环境现状**：910C 上此前同时存在多套镜像，曾因版本不一致污染实验结论；本文档已将本次原型所需环境收敛为两个锁定镜像（见 §4）。

## 3. 验收 Demo 定义

**模型**：`Qwen/Qwen3-Embedding-0.6B`

| 段 | 内容 | 主责 |
|---|---|---|
| 段一 | 2 卡分布式微调 | device-context + communication（共同承担） |
| 段二 | 单卡推理服务（推理框架锁定版本见 §4） | device-context 主导，memory 提供显存侧支撑，调度提供请求调度支撑，performance 采集性能数据 |

**验收标准**（全部满足 = 原型达成）：

1. 段一：2 卡分布式微调在锁定训练镜像内跑通，loss 正常下降，全程无死锁、无数据错乱，多卡通信正确性（如全量规约、全量收集等集合通信操作）有对照证据。
2. 段二：单卡推理服务在锁定推理镜像内正常启动，产出向量结果正确，有吞吐/时延数据。
3. 两段验证过程中，至少注入一次真实错误，能观察到"统一错误识别 → 分级 → 恢复处理"的完整闭环，监控方向对该闭环出具证据链。
4. memory 方向产出锁定环境下的显存池定义与显存占用峰值画像（KV 缓存相关验证不作为本次硬性指标，理由见 §7）。
5. performance 方向产出一份基于两段 demo 实际证据自动生成的统一验收报告。
6. 全程只使用 §4 锁定的两个镜像（训练腿为组内自构建镜像，功能等价重建已实机验证，见 §7 与 `dev/images/`），不引入第三方临时镜像或容器。

- **memory 方向的验证场景与验收模型不完全匹配**：`Qwen/Qwen3-Embedding-0.6B` 不存在生成式模型那种随生成步数增长的缓存占用，显存分层缓存相关能力本次难以验证——已相应收窄该方向的交付范围（见 §5）。
- **训练腿镜像可复现性**（原"可分发性缺口"）：组内自构建镜像，无 registry 推送要求。2026-09-10 已完成功能等价重建——凭仓内 `dev/images/ascend-train-comm/v1/Dockerfile.repro` + `assets` 可重建，`pip freeze` 与原镜像逐行一致、FlagCX `.so` 逐字节一致（见 `dev/images/ascend-train-comm/v1/REBUILD.md`），repro_status 🟢。逐字节复现（需 owner 私有 FlagCX commit+patch）为可选金标准，见 `dev/images/TODO.md`。
- **FlagTree 版本线（已确认：锁定环境全栈 ascend3.5，环境侧无待决项；仅 FlagTree fork 分支为独立后续项，见末尾）**：锁定环境的 CANN 9.0.0 / Python 3.11 / torch 2.10.0 / triton 3.5.0 / vLLM 0.20.2 逐项对齐 FlagTree ascend 手册的 ascend3.5 线。此前"`triton_ascend 3.2.1` 对应 ascend3.2 线"的说法是对版本号的误读 —— `triton-ascend` 是华为昇腾 Triton 插件，与 `triton` 为两个独立包，其 wheel 取自 `quay.io/ascend/vllm-ascend:v0.20.2rc1-a3`（即 ascend3.5 / vLLM 0.20.2 镜像），import 自报 3.2.0，版本号不随 `triton` 或线号推进，不构成 3.2 线证据，不存在"是否切回 ascend3.5"的问题。构建路径未按 **BAAI·FlagTree 官方**手册（未 checkout FlagTree `triton_v3.5.x` 自编译、未用 FlagTree 3.5 线基座镜像）：推理腿直接用**华为昇腾官方** vllm-ascend，训练腿用 **BAAI 内部** CANN 9.0.0 底座 + pip triton 3.5.0 + **华为昇腾官方** triton-ascend 3.2.1 + FlagOS 组件（Torch-FL / FlagGems / FlagCX）。版本纪元对齐 ascend3.5，构建方式自成一路，详见 `dev/images/image_list.md`。**FlagTree fork 分支（`VERSIONS.md` §1 的 `triton_v3.2.x`）本原型不需变更**——原型镜像不含 FlagTree 构建物；日后若要在 ascend3.5 镜像里引入 FlagTree 构建物，其 fork 须先切到 `triton_v3.5.x`，由编译层 / FlagTree 维护者决定。**BAAI·FlagTree 官方指南**：<https://github.com/flagos-ai/FlagTree/wiki/User-manual-for-ascend>。
