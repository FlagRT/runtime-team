# 运行时基座：使用与维护指南

> 状态：生效（2026-10-11）。本文是入口与流程说明，不重复规范细节；规范以各链接文档为准。

## 0. 三句话

1. **镜像**是不可变的制品：构建时固化进去的代码（固化资产），版本记录在 `image.baseline.yaml`，由 image id 约束。
2. **运行环境目录**是一套完备的运行环境：`docker-compose.yml`（怎么启动）+ `env.baseline.yaml`（用了哪个镜像、另外挂载了哪些 repo、各在哪个 commit）。
3. 两个基线文件都由 `dev/lib/baseline.py` 生成、核对、切换，不手工编辑；统一用 `dev/lib/up.sh <env-dir> [--strict]` 启动。

## 2. 两腿分栈：机制与各自的查法

昇腾 910C 训练与推理为两套镜像、两个容器，使用方按腿选镜像；锁定声明 `dev/stack.lock.910c.*` 分 `lock.train` / `lock.infer` 两段。
一台机器同时只跑一个带卡容器，两腿须串行：跑完一条停掉再起下一条。

**训练腿** = 组内构建镜像（含 FlagCX 多卡通信层）：

- 获取：离线归档包，或按仓内配方（`Dockerfile.repro` + `build.sh`）重建。
- 启动：`dev/lib/up.sh <lock.train 的 base_image_entry>/demo --strict`。
- 约束：受所用版本的已知限制约束（规避配置与根治归属），限制清单见当次 `docs/基座发版说明-<日期>.md` 与该镜像目录 README。

**推理腿** = 芯片厂商官方镜像：

- 获取：公开 registry 按 digest 拉取。
- 起服务前 `unset VLLM_PLUGINS`（vllm-plugin-FL 无 ascend 后端，910C 推理腿不加载）。
- 启动：统一经 [`dev/device-context/prototype/scripts/serve_standard.sh`](../dev/device-context/prototype/scripts/serve_standard.sh) 起服务。

两类镜像的管理方式不同：组内构建镜像走「配方 + 镜像基线（`baseline.py export` 生成）+ `up.sh --strict`」；
厂商官方镜像走「registry digest 锁定 + 登记式基线（手工登记，ADR-0007；`up.sh --strict` 照常核对 image id）」。
**服务启动**在两种形态下都统一经组内启动标准脚本 `serve_standard.sh`（唯一服务入口）；基线 demo 只管容器生命周期，
两层分工、不是双入口。实例：[`ascend-infer-vllm/v1`](../dev/images/ascend-infer-vllm/v1/README.md)。

vllm-plugin-FL 不是 910C 的推理栈，其缺陷已挂起、不跟进、无切换回该插件的计划；记录见现行锁定声明的 `fl_catchup_policy` 段。注意其他芯片上该插件可能是必需项。

**具体 tag / image id / digest / 当前已知限制条目一律不在本文列出**，按下列指针查：

| 要查的事实 | 去哪里 |
|---|---|
| 现行是哪个版本 | [image_list.md「当前生效版本」](../dev/images/image_list.md#当前生效版本) |
| 两腿镜像 tag / image id / digest、`base_image_entry`、使用规则 | 现行 `dev/stack.lock.910c.*` |
| 当前已知限制条目、规避配置、根治归属 | 当次 `docs/基座发版说明-<日期>.md` 与对应镜像目录 README / `lock.yaml` |

## 3. 维护者：发布新镜像版本

以 `dev/images/<name>/v<N+1>/` 为单位，旧版本目录保留不改（[images/README.md §3](../dev/images/README.md)）。

1. **写配方**：`Dockerfile.repro` + `build.sh`，参照现行生效版本目录（见 [image_list「当前生效版本」](../dev/images/image_list.md#当前生效版本)）。三条约束（不满足时 `baseline.py export` 报错）：
   - 每个固化 repo 用 `ARG <X>_COMMIT=<40 位 sha>` 固定版本，并写对应的 commit 标签（名称见 `baseline.py` 的 `COMMIT_LABEL`，如 `io.flagrt.flag_gems.commit`；新 repo 须先在其中登记）；
   - repo 只通过 `COPY src/<Repo>/` 或构建期 `git fetch ${<X>_COMMIT}` 进入镜像，本层不做 `pip install -e`；
   - 下载资源用 `ARG <X>_URL`，补丁放 `assets/patches/` 并带 sha256。
   完整识别规则见 [ENV-SPEC §4.2](../dev/ENV-SPEC.md)。
2. **构建**：`build.sh <构建上下文目录>`。COPY 来源的 repo 由 `build.sh` 按 ARG commit 从本机 checkout `git archive`，只包含已提交内容。
   被 pin 的 commit 须已推送到该 repo 的远端，否则他人无法从零重建。
3. **demo 运行环境**：`v<N+1>/demo/`，写入验收时的全部运行配置（规避项、挂载、环境变量），`mounted_repos: {}`。
4. **生成并核对基线**：
   ```bash
   python3 dev/lib/baseline.py export --image dev/images/<name>/v<N+1> --demo dev/images/<name>/v<N+1>/demo/
   python3 dev/lib/baseline.py check  --image dev/images/<name>/v<N+1>
   python3 dev/lib/baseline.py export dev/images/<name>/v<N+1>/demo
   ```
   有 `baked_packages`（索引发行包）的血统，`export` 会联网取 wheel 的 sha256 记进基线；
   发版前再跑一次 `check --image --online` 核对索引页当前内容（[ENV-SPEC §4.2 模式 6 第四条边](../dev/ENV-SPEC.md)）。
   两者都走 curl 的标准环境变量，需绕过代理的机器先 `export no_proxy='*'`。
   `check` 默认不联网 —— 它在 `up.sh --strict` 的启动路径上。
5. **带卡验证**：`dev/lib/up.sh <demo> --strict` 后运行自判定验证脚本；证据截选放 `assets/evidence/`。
6. **归档与文档**：离线归档并填 `ARCHIVE.md`（**先验证 `docker save` 在本机对该镜像是否可用** ——
   实测 P800 上对巨型厂商派生镜像只出 manifest、`docker load` 不可用且报告成功，
   须改用 `docker export` + `docker import --change`，实例见 `dev/images/kunlun-operator-runtime/v2/ARCHIVE.md`）；
   `lock.yaml` 记构建历史与已知问题；
   按 [CASE-TEMPLATE](../dev/images/CASE-TEMPLATE.md) 写 README；更新 [image_list.md](../dev/images/image_list.md)、`VERSIONS.md`、TODO。

### 接入新芯片

新芯片是新的镜像血统（如 `dev/images/<chip>-operator-runtime/v1/`），流程同上。需要额外处理的点：

- **第一步：先对该芯片的配方跑一遍 `baseline.py export --image`，把报错逐条当成规范缺口清单。**
  规范（[ENV-SPEC §4.2](../dev/ENV-SPEC.md)）只识别列出的模式、其余一律报错，所以报错就是
  「这条血统有一类来源/版本锚还没被机制覆盖」的信号，不是工具坏了。昆仑芯接入时的模式 6
  （pip 索引发行包）与 `baked_packages` 块就是这么发现的。
- L1 基座与设备插件按 [黄金准则 GR4（Route A）](运行时基座建设-黄金准则与方案存档.v1.md) 选厂商官方插件为默认路径。
- **先自己实测该芯片的设备模型，不要照抄别的芯片**：`devices:` 怎么给、要不要 `--privileged`、
  要不要挂宿主驱动目录、多容器能否并存、设备号怎么编。昇腾的「驱动对带卡容器独占」是昇腾专属，
  P800 四条都不同（实测结论与证据的实例写在
  [kunlun-operator-runtime/v2/demo/docker-compose.yml](../dev/images/kunlun-operator-runtime/v2/demo/docker-compose.yml) 文件头）。
  结论写进该镜像 demo 的 compose 文件头与 `REBUILD.md`，不要只留在聊天记录里。
- `baseline.py` 的芯片专属事实都收敛在文件头的几张声明式表里，接新芯片**只加数据、不改控制流**：
  `BASE_PROVIDES_ENV`（L1 版本在环境变量里，如昇腾 CANN）、`BASE_PROVIDES_FILES`（L1 版本在镜像内
  文件里，如昆仑芯的 `torch_xmlir/_versions.txt` 给出 XTDK/XRE/XCCL）、`BASE_PROVIDES_PKGS`（要收录的
  包白名单）、`REPO_DIR`（[ENV-SPEC §3.2](../dev/ENV-SPEC.md) 仓库名表）、`COMMIT_LABEL`（commit 锚标签）、
  `VERSION_LABEL`（版本锚标签）、`PKG_TO_REPO`（pip 发行名 → 仓库名）、`LAYER`、`PACKAGES_PREFER`。
  未登记时的报错会指明该去哪张表登记。扩展时补测试（`dev/lib/tests/`，与规范改动同一个提交）。
- `ARG PYTHON_BIN` 必须是目标解释器的绝对路径；conda 多环境基座不能依赖 `PATH` 上的 `python3`
  （昆仑芯基座 `PATH` 上的是 miniconda base 的 3.13.11，目标 env 是 3.10.18）。

## 4. 使用者：在同一基座上开发

### 4.1 建自己的运行环境

按 [dev/_template/](../dev/_template/README.md) 建目录：`docker-compose.yml` 经 `extends` 复用镜像 demo，只写本方向差异；
`baseline.py export` 生成 `env.baseline.yaml`，两者一起提交到本仓。测试与 demo 脚本放在本方向目录内。

### 4.2 改 repo 的代码：挂载覆盖 + 分支提交

镜像内的 repo 不改；需要修改某个 repo 时，在运行环境中**挂载宿主 checkout 覆盖镜像内版本**，宿主改代码、容器内即生效：

1. 在 compose 的 `x-flagrt.mounted_repos` 声明该 repo（`activation: pip-editable`），按 [ENV-SPEC §5](../dev/ENV-SPEC.md) 写 `command` 与两个环境变量。
2. 在宿主 checkout 上建开发分支（建议 `<方向>/<主题>`），改动以 commit 形式提交。
3. 将分支 push 到该 checkout 已配置的远端（组织 fork 或上游）。未推送的 commit 他人无法复现：`export` 记录 `pushed: false` 并警告，`check` 同样警告。
4. 需要留存或交给他人复现时：`python3 dev/lib/baseline.py export <env-dir> --require-clean`（工作区不干净或 commit 未推送即拒绝），提交 `env.baseline.yaml`。
5. 他人复现：`baseline.py load <env-dir>`（自动 fetch 并切换到记录的 commit）→ `up.sh <env-dir> --strict`。

注意：

- 基线记录的是 commit，分支名只作阅读信息。
- 纯 Python 的 repo（vllm-plugin-FL、FlagGems 的 Python 部分）改完即生效；含 C++ 的 repo（Torch-FL、FlagCX）改动后须重新编译安装（重启容器），挂载前评估是否必要。
- 镜像内的 repo 若带构建期补丁（如 vllm-plugin-FL 的 `0001-…patch`），挂载的 checkout 不含该补丁，`check` 会提示；需要时把补丁提交进开发分支。
- `load` 会切换宿主 checkout，只在自己的仓根 checkout 上使用（`FLAGRT_WORKSPACE_ROOT` 可指定其他仓根）。
- 验收与出结论的运行一律 `up.sh --strict`，且使用已推送的干净 commit。

### 4.3 把改动固化进基座

运行环境中的挂载只影响该环境。改动稳定后：

1. 合入对应 repo 的上游或组织 fork 的稳定分支（不能合入上游的修复，以 `assets/patches/` 声明式补丁形式固化，并附保质期说明）；
2. 由镜像维护者在下一个镜像版本的 `Dockerfile.repro` ARG 中 pin 该 commit，按第 3 节发布；
3. 发布后，运行环境改用新镜像并删除对应挂载声明。

## 5. 常用命令

```bash
python3 dev/lib/baseline.py list                     # 全部镜像的资产与版本
python3 dev/lib/baseline.py show <env-dir>           # 或 show --image <image-dir>
python3 dev/lib/baseline.py export <env-dir> [--require-clean]
python3 dev/lib/baseline.py check  <env-dir>
python3 dev/lib/baseline.py load   <env-dir>
dev/lib/up.sh <env-dir> [--strict]
WORKSPACE_ROOT=$PWD docker compose -f <env-dir>/docker-compose.yml down   # 停止（仓根执行）
```

### 各芯片设备模型对照

| | 昇腾 910C | 昆仑芯 P800 | 平头哥 PPU | 寒武纪 MLU590 |
|---|---|---|---|
| 带卡容器独占 | 是，开工前 `docker ps` 是阻塞条件 | 否，用 `xpu-smi` 挑空闲卡，`docker ps` 只是礼貌 | 否，用 `ppu-smi` 挑空闲卡（同 P800 型） | 否，用 `cnmon` 挑空闲卡（同 P800 型）；机器同时是 k8s 在册节点，集群侧也可能占卡 |
| 选卡变量 | `ASCEND_RT_VISIBLE_DEVICES` | `CUDA_VISIBLE_DEVICES`（按授予顺序密集重编号） | `CUDA_VISIBLE_DEVICES`（同 P800 型，密集重编号） | `MLU_VISIBLE_DEVICES`（密集重编号） |
| 卡号纪律 | 多个检查共用一个容器、用变量分区 | 各起各的无妨，真实约束是显存与算力竞争 | 同 P800；另有两条启动纪律（`extra_hosts` 主机名回环 / `NCCL_SOCKET_IFNAME=bond0`），demo 已内置 | 同 P800；另须授 18 个设备节点并挂 `/usr/bin/cnmon`（宿主无 neuware），demo 已内置 |
| 设备 API 命名空间 | torch_npu | torch（CUDA 命名空间） | torch（**CUDA 命名空间**，`torch.xpu` 为 0） | torch_mlu（**`torch.mlu` 命名空间**，PrivateUse1；进程级单例，不可与 torch_npu / torch_fl 混用） |

两边共同——**绝不**停止/重启/exec 进入任何他人容器，用完把自己的收干净。完整对照与实测证据见 [dev/issues/README.md](../dev/issues/README.md)「共享机器」节。
