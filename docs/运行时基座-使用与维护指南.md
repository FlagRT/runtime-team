# 运行时基座：使用与维护指南

> 状态：生效（2026-10-11）。本文是入口与流程说明，不重复规范细节；规范以各链接文档为准。

## 0. 三句话

1. **镜像**是不可变的制品：构建时固化进去的代码（固化资产），版本记录在 `image.baseline.yaml`，由 image id 约束。
2. **运行环境目录**是一套完备的运行环境：`docker-compose.yml`（怎么启动）+ `env.baseline.yaml`（用了哪个镜像、另外挂载了哪些 repo、各在哪个 commit）。
3. 两个基线文件都由 `dev/lib/baseline.py` 生成、核对、切换，不手工编辑；统一用 `dev/lib/up.sh <env-dir> [--strict]` 启动。

## 3. 维护者：发布新镜像版本

以 `dev/images/<name>/v<N+1>/` 为单位，旧版本目录保留不改（[images/README.md §3](../dev/images/README.md)）。

1. **写配方**：`Dockerfile.repro` + `build.sh`，参照 v3。三条约束（不满足时 `baseline.py export` 报错）：
   - 每个固化 repo 用 `ARG <X>_COMMIT=<40 位 sha>` 固定版本，并写对应的 commit 标签（名称见 `baseline.py` 的 `COMMIT_LABEL`，如 `io.flagrt.flag_gems.commit`；新 repo 须先在其中登记）；
   - repo 只通过 `COPY src/<Repo>/` 或构建期 `git fetch ${<X>_COMMIT}` 进入镜像，本层不做 `pip install -e`；
   - 下载资源用 `ARG <X>_URL`，补丁放 `assets/patches/` 并带 sha256。
   完整识别规则见 [ENV-SPEC §4.2](../dev/ENV-SPEC.md)。
2. **构建**：`build.sh <构建上下文目录>`。COPY 来源的 repo 由 `build.sh` 按 ARG commit 从本机 checkout `git archive`，只包含已提交内容。
   被 pin 的 commit 须已推送到该 repo 的远端，否则他人无法从零重建。
3. **demo 运行环境**：`v<N+1>/demo/`，写入验收时的全部运行配置（规避项、挂载、环境变量），`mounted_repos: {}`。
4. **生成并核对基线**：
   ```bash
   python3 dev/lib/baseline.py export --image dev/images/<name>/v<N+1> --demo dev/images/<name>/v<N+1>/demo/
   python3 dev/lib/baseline.py check  --image dev/images/<name>/v<N+1>
   python3 dev/lib/baseline.py export dev/images/<name>/v<N+1>/demo
   ```
5. **带卡验证**：`dev/lib/up.sh <demo> --strict` 后运行自判定验证脚本；证据截选放 `assets/evidence/`。
6. **归档与文档**：`docker save` 离线归档并填 `ARCHIVE.md`；`lock.yaml` 记构建历史与已知问题；
   按 [CASE-TEMPLATE](../dev/images/CASE-TEMPLATE.md) 写 README；更新 [image_list.md](../dev/images/image_list.md)、`VERSIONS.md`、TODO。

### 接入新芯片

新芯片是新的镜像血统（如 `dev/images/<chip>-operator-runtime/v1/`），流程同上。需要额外处理的点：

- L1 基座与设备插件按 [黄金准则 GR4（Route A）](运行时基座建设-黄金准则与方案存档.v1.md) 选厂商官方插件为默认路径。
- demo 的 `devices:` / 驱动挂载 / 环境变量按该芯片改写。
- `baseline.py` 中与昇腾相关的约定需同步扩展：`base_image.provides` 目前只从 `ASCEND_TOOLKIT_HOME` 识别 CANN 版本；
  新增 repo 须登记到 `REPO_DIR`（[ENV-SPEC §3.2](../dev/ENV-SPEC.md) 仓库名表）与 `COMMIT_LABEL`。扩展时补测试（`dev/lib/tests/`）。

## 4. 使用者：在同一基座上开发

### 4.1 建自己的运行环境

按 [dev/_template/](../dev/_template/README.md) 建目录：`docker-compose.yml` 经 `extends` 复用镜像 demo，只写本方向差异；
`baseline.py export` 生成 `env.baseline.yaml`，两者一起提交到本仓。测试与 demo 脚本放在本方向目录内。

### 4.2 改 repo 的代码：挂载覆盖 + 分支提交

镜像内的 repo 不改；需要修改某个 repo 时，在运行环境中**挂载宿主 checkout 覆盖镜像内版本**，宿主改代码、容器内即生效：

1. 在 compose 的 `x-flagrt.mounted_repos` 声明该 repo（`activation: pip-editable`），按 [ENV-SPEC §5](../dev/ENV-SPEC.md) 写 `command` 与两个环境变量。
2. 在宿主 checkout 上建开发分支（建议 `<方向>/<主题>`），改动以 commit 形式提交。
3. 将分支 push 到该 checkout 已配置的远端（组织 fork 或上游）。未推送的 commit 他人无法复现：`export` 记录 `pushed: false` 并警告，`check` 同样警告。
4. 需要留存或交给他人复现时：`python3 dev/lib/baseline.py export <env-dir> --require-clean`（工作区不干净或 commit 未推送即拒绝），提交 `env.baseline.yaml`。
5. 他人复现：`baseline.py load <env-dir>`（自动 fetch 并切换到记录的 commit）→ `up.sh <env-dir> --strict`。

注意：

- 基线记录的是 commit，分支名只作阅读信息。
- 纯 Python 的 repo（vllm-plugin-FL、FlagGems 的 Python 部分）改完即生效；含 C++ 的 repo（Torch-FL、FlagCX）改动后须重新编译安装（重启容器），挂载前评估是否必要。
- 镜像内的 repo 若带构建期补丁（如 vllm-plugin-FL 的 `0001-…patch`），挂载的 checkout 不含该补丁，`check` 会提示；需要时把补丁提交进开发分支。
- `load` 会切换宿主 checkout，只在自己的仓根 checkout 上使用（`FLAGRT_WORKSPACE_ROOT` 可指定其他仓根）。
- 验收与出结论的运行一律 `up.sh --strict`，且使用已推送的干净 commit。

### 4.3 把改动固化进基座

运行环境中的挂载只影响该环境。改动稳定后：

1. 合入对应 repo 的上游或组织 fork 的稳定分支（不能合入上游的修复，以 `assets/patches/` 声明式补丁形式固化，并附保质期说明）；
2. 由镜像维护者在下一个镜像版本的 `Dockerfile.repro` ARG 中 pin 该 commit，按第 3 节发布；
3. 发布后，运行环境改用新镜像并删除对应挂载声明。

## 5. 常用命令

```bash
python3 dev/lib/baseline.py list                     # 全部镜像的资产与版本
python3 dev/lib/baseline.py show <env-dir>           # 或 show --image <image-dir>
python3 dev/lib/baseline.py export <env-dir> [--require-clean]
python3 dev/lib/baseline.py check  <env-dir>
python3 dev/lib/baseline.py load   <env-dir>
dev/lib/up.sh <env-dir> [--strict]
WORKSPACE_ROOT=$PWD docker compose -f <env-dir>/docker-compose.yml down   # 停止（仓根执行）
```
