# 跨组需求：昆仑芯 P800 GEMM 编译不可用（2026-10-14）

> 提出方：运行时组（runtime-team）。归属方向：算子编译方向（flagtree / triton xpu 后端）——缺陷不在本组代码内。
> 状态：未修复，无可用 workaround（截至 2026-10-12 复核定论）。官方发布栈用 triton 3.0.0 线可绕开，但那是另一条版本线，不在本组锁定 pin 的验证范围内，不作为规避手段推荐。
> 事实来源：case 包 [`../dev/issues/kunlunxin-gemm-triton-compile/README.md`](../dev/issues/kunlunxin-gemm-triton-compile/README.md)。复现、验收、证据以其为准，本文件不复制其脚本正文。

## 一句话请求

请算子编译方向在 flagtree / triton 的 xpu 后端修复 GEMM kernel 编译路径：昆仑芯 P800 上，FlagGems 的 GEMM 类算子（`mm`/`bmm`/`addmm`）在 flagtree `0.6.1+xpu3.6`（triton 3.6.0）下**编译阶段即失败，12 组形状 × dtype 无一可用**。该 pin 是本组已生效锁定的 xpu3.6 线（[`../dev/stack.lock.kunlunxin.v1.yaml`](../dev/stack.lock.kunlunxin.v1.yaml)，2026-10-14 定稿），需要 GEMM 的算子路径目前只能整体绕开 FlagGems 的 GEMM——对本组及全部下游消费方是**硬阻塞**，且无任何可用 workaround。

## 问题定义

**现象**：锁定镜像 `flagrt/kunlun-operator-runtime:2.0.0-xpu3.6-py310-torch2.9-flagtree0.6.1-flaggems73c5aff1-x86_64`（image id `sha256:cac5ddae5f62b356622858dd4f0ea0f82d489cf0cb71e7230f0f97797c25605a`）内，GEMM 类算子经 autotuner → libentry → `flag_gems/runtime/backend/_kunlunxin/ops/mm.py:168` 触发 triton JIT 编译，编译阶段即失败。

**两种失败形态**：

| 失败形态 | 失败阶段 | 代码位置 | 为什么长这样 |
|---|---|---|---|
| 原生 abort（`Fatal Python error: Aborted`） | `llir` | 镜像内 `<site-packages>/triton/backends/xpu/compiler.py:486` 的 `pm.run(mod, 'make_llir')` | 该行没有 try/except，LLVM 原生断言不可捕获，进程被整体 `abort()`。断言原文：`llvm/lib/IR/Instructions.cpp:758 llvm::CallInst::init` 的 `"Calling a function with bad signature!"` |
| `OutOfResources: uni_sram` | `ttxir` | 同文件 `:362-367` 的 `pm.run(mod, 'make_ttxir')` | 该 `except` 把**任何**异常一律包成 `OutOfResources(0, 0, f"uni_sram {e}")`；消息里的 `Required: 0, Hardware limit: 0` 是构造函数里写死的零，并非真实资源读数，`e` 的原文只是 `PassManager::run failed` |

**为什么是同一缺陷**（2026-10-12 复核定论，此前未定论）：

- 形态由 **shape × dtype** 决定，落在同一条编译流水线（`ttir → ttxir → llir → elf → xpubin`）的两个不同阶段：早一步在 `ttxir` 失败的形状走不到 `llir`，得到被包装的异常；过了 `ttxir` 的才撞上 LLVM 断言、进程原生终止。
- 用 FlagGems 自带 `tests/test_blas_ops.py::test_accuracy_mm`（normal 模式 3 形状 × 3 dtype × `b_column_major` 两值 = 18 组）逐组独立进程复跑：**18/18 全部失败，无一组 PASS**；形态按 shape × dtype 二分，`b_column_major` 对形态无影响。
- abort 形态与本组 v1 记录逐帧一致（48 帧栈，File 行差异仅 3 处且均为 FlagGems 路径前缀不同，行号与函数名无一处不同）；本轮另取到 v1 证据中没有的底层断言原文（上述 LLVM 断言）。
- 对称验证排除「镜像」变量：v1 归档镜像（image id `466ee5c61793`）上 64×64 同样得 `OutOfResources: uni_sram`（三种 dtype 皆然）、`(1,1,32)+float32` 同样得原生 abort——两种形态在两个镜像上都能出现。
- 证据：[`../dev/images/kunlun-operator-runtime/v2/assets/evidence/gemm-failure-signature-recheck-20261012.txt`](../dev/images/kunlun-operator-runtime/v2/assets/evidence/gemm-failure-signature-recheck-20261012.txt)。

**与 FlagGems pin 到哪个 commit 无关**：缺陷定位在 triton xpu 后端的编译流水线；memory 子方向此前在旧 dev 容器（同 triton 3.6.0 线）的独立实测与本次栈完全一致——不是环境偏差导致的偶发问题，是该版本线对 GEMM kernel 编译路径的确定性缺陷。

**与是否加载模型无关**：case 包的最小复现不加载模型、不联网，4 形状 × 3 dtype = 12 组直接触发。

|---|---|

| 级别 | 对方要做什么 | 本组能配合什么 |
|---|---|---|
| 最小可行修复 | 修复两处错误处理，使编译失败以真实原因、可捕获的方式暴露：① `compiler.py:362-367` 停止把 ttxir 阶段任意异常包成 `OutOfResources`（删除硬编码的 `Required: 0, Hardware limit: 0` 读数）；② `compiler.py:486` 的 `pm.run(mod, 'make_llir')` 外补错误处理，LLVM 断言不再直接 abort 整个进程。此级不解决 GEMM 本身，但解除「失败即整进程死亡且原因被掩盖」的次生阻塞：下游可以降级、可以把该算子加入黑名单 | 交付 case 包（单入口复现、12 组形态矩阵、48 帧栈证据）；提供镜像重建方式（公开源头，约 15 分钟） |

| 根治 | 对 xpu3.6 编译流水线建立 GEMM 类 kernel 的持续回归（至少覆盖 FlagGems `test_blas_ops` 的形状集合），并保证全流水线异常路径可捕获、报错消息如实——杜绝「同一缺陷两种表象、其中一种还被误标为资源不足」的定位成本 | 贡献本 case 的形状 × dtype 形态矩阵与「每形状起子进程判定」的复现做法；持续同步新发现的同根因算子（如 `index_select`） |

### 单入口命令

仓根执行：

```bash
FLAGRT_MODELS_DIR=<任一实体目录> dev/lib/up.sh dev/images/kunlun-operator-runtime/v2/demo --strict
docker exec flagrt-kunlun-v2-demo-p800 \
  env CUDA_VISIBLE_DEVICES=<xpu-smi 挑中的空闲卡号> \
  /root/miniconda/envs/python310_torch29_cuda/bin/python3 \
  /workspace/dev/issues/kunlunxin-gemm-triton-compile/assets/minirepro_gemm.py
docker compose -f dev/images/kunlun-operator-runtime/v2/demo/docker-compose.yml down
```

脚本覆盖 4 形状 × 3 dtype = 12 组（前三个形状取自 FlagGems 自带 `test_accuracy_mm` 的 `MNK_SHAPES`，第四个 64×64 是镜像验证脚本那组）。两类形状都要跑，否则只会看到一种失败形态。

### 预期结果（问题存在时，退出码 1）

12 组全部失败：2 组 `native-abort@make_llir`（`(1,1,32)` + float16/float32）、10 组 `OutOfResources:uni_sram@make_ttxir`，判定行 `overall: FAIL`。判定为 `overall: ERROR`（退出码 2）说明环境不满足，不是缺陷复现。最近一次实测（2026-10-12，本机卡 7）逐组读数与证据：[`../dev/issues/kunlunxin-gemm-triton-compile/assets/evidence/minirepro-20261012.txt`](../dev/issues/kunlunxin-gemm-triton-compile/assets/evidence/minirepro-20261012.txt)。

向上游报缺陷请用 `(1,1,32)` + float32 这一组做最小复现：它给出原生 abort 加 LLVM 断言原文，信息量最大；64×64 只会给出被误标的 `OutOfResources`，把排查引向「调小 `BLOCK` / `num_stages`」这条无效路径。

## 修复验收判据

case 包判据原文：

> 同一条单入口命令退出码 **0**、判定行 **`overall: PASS`** —— 12 组全部编译通过**且数值在容差内**（fp16 1e-2 / bf16 5e-2 / fp32 1e-3，与 CPU float32 参考比最大绝对偏差）。编译通过但数值错记 `wrong-numerics`，**不算修复**。

补充口径（同 case 包）：仅编译通过而数值错不算修复；只验 64×64 不足以说明 `llir` 阶段的 LLVM 断言已修（pytest 全参数化 18 组全部 PASS 才算）。修复到货后本组动作：case 目录脚本判定转 `overall: PASS`；[`../dev/images/kunlun-operator-runtime/v2/lock.yaml`](../dev/images/kunlun-operator-runtime/v2/lock.yaml) 的 `gemm-same-defect-two-failure-stages` 与 v1 的 `gemm-compile-sigabrt` 一并关闭；`v2/assets/verify_kunlun_runtime.py` 的 GEMM 探测由 `KNOWN` 行改为计入判定。

## 附带问题（需一并答复）

1. **`OutOfResources: uni_sram` 报错文本误导性**（第二个独立问题，可与主缺陷分开处理）：`compiler.py:362-367` 把 ttxir 阶段任意异常一律包成 `OutOfResources`，`Required: 0, Hardware limit: 0` 是构造函数里写死的零，`e` 的原文只是 `PassManager::run failed`——真实失败原因被完全掩盖，按字面「调小 `BLOCK` / `num_stages`」排查无效。验收：该路径报出的异常类型与消息反映真实失败原因。修好它不解决 GEMM，但能让所有后续排查少走弯路。
2. **FlagGems `backends.yaml` 仍声明 `triton==3.0.0+a48aedef`**（xpu3.0 时代遗留，与 xpu3.6 线不符），说明 xpu3.6 线未对 GEMM 路径做回归测试；另 FlagGems 自带 `test_accuracy_mm` 定义上方即有注释 `# TODO: failed at (1, 1, 2)`，上游已知小形状有问题。请一并答复：xpu3.6 线对 FlagGems GEMM 路径的回归状态，以及该版本声明的更新计划。
