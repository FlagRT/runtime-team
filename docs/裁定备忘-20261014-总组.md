## 1. 昆仑芯 P800 镜像入锁

昆仑芯此前没有任何锁定声明（`dev/` 下只有 910c 的两份）。本次为它建立第一份：
`dev/stack.lock.kunlunxin.v1.yaml`，发布物 `flagrt/kunlun-operator-runtime:2.0.0-xpu3.6-py310-torch2.9-flagtree0.6.1-flaggems73c5aff1-x86_64`（image id `sha256:cac5ddae5f62…`，🟢 functional-repro）。

`v1` 已由 v2 取代且**不得用于从零重建**——其归档镜像经查实是 `docker commit` 产物，而非其 `Dockerfile.repro` 的构建产物（四条独立证据见 `dev/images/kunlun-operator-runtime/v1/lock.yaml`）。v1 镜像本身仍可用，其运行时验证结论仍然成立。

P800 的设备模型与昇腾相反，已按实测写入该文件 `device_registration` 与 `rules`：**无带卡容器独占**、用 `xpu-smi` 挑空闲卡、选卡变量 `CUDA_VISIBLE_DEVICES`（按授予顺序密集重编号）。**不要跨芯片照抄。**

## 2. 训练腿镜像分发渠道

**裁定：不推 registry。** 正式确立「离线包 + 仓内配方重建」为分发路径，关闭原有「发布到 registry」诉求。

依据：

- `dev/stack.lock.910c.*.yaml` 原文即写「组内镜像无 registry 要求」。
- 实际可达机器只有 3 台（`npu1-11` / `npu1-27` / `P800`），其余 4 台 910C 节点受 Slurm 限制登不上，registry 的实际收益有限。
- 离线包已实体存在且带校验：`npu1-11` `/mnt/raid/user_cache/xliu969/v3-round4-archive/`，含 `SHA256SUMS.txt`。

分发路径（按优先级）：

1. **首选重建**：按仓内配方构建（先 `dev/images/ascend-operator-runtime/v3`，再 `dev/images/ascend-train-comm/v3`，过程见各目录 `REBUILD.md`）。
2. **备份取包**：从 `npu1-11` 上述路径取 `train-comm-v3-round4-npu11-e13a15d0d02b.tar.gz`，`docker load`。
3. `npu1-27` 虽存有同源 `7028028bb62c`，但该机 docker 存储层校验和损坏、`docker save` 不可用，**不作为分发源**（运行不受影响，已报修）。

## 3. torch 版本差 —— 统一到锁定基座

现状是**两档位并存**，且出结论的一方不在锁定档位上：

| 谁 | torch | 是否在锁定基座内 |
|---|---|---|
| 锁定基座（v3 完整镜像） | **2.10.0** | ✅ 是 |
| device-context 两芯片验收 10/10 | **2.11.0** | ❌ 否（跑在 `venv-infer-a`） |
| communication DeepFM 双卡 | **2.11.0** | ❌ 否（同一 `venv-infer-a`） |
| MLU590 线 | **2.11.0** | —（另一血统） |

**裁定：统一到锁定基座的 torch 2.10.0。** `venv-infer-a` 降为探索层，其结论不得作为验收或发布依据。

关键理由不是「差一个小版本」，而是：**`venv-infer-a` 是共享 venv，其版本不在任何 `image.baseline.yaml` / `env.baseline.yaml` 的版本锚里 —— 基于它得出的结论无法被他人复现**，这直接违反合入把关第①条（镜像与 stack.lock 一致）与第⑤条（未引入新环境分叉）。

## 4. 带卡容器并发上限口径

同一件事在三份材料里有三个数：本规则写 **3**、锚点记录实测 **2**（`-8020 device is used`）、`dev/issues/README.md`「共享机器」节记带卡容器 **独占 1**（第二个带卡容器一律 EBUSY）。

**裁定：这不是"哪个数对"的问题，是两件事被混为一谈。**

- ① **设备级独占**：容器默认挂满 16 张 `davinci` 设备（compose 的 `devices:` 整值给出），设备被占用即起不来 ⇒ **同时只能 1 个带卡容器**。
- ② **驱动 DrvMng 名额**：历史观测 2~3，与①叠加后表现不一致。

当前操作口径 =「**1 个带卡容器 + 容器内用 `ASCEND_RT_VISIBLE_DEVICES` 分区**」。驱动名额的真实上限待专项实测后回填 `stack.lock`。

落地：

- `dev/stack.lock.910c.v3.yaml` `rules` 首条已重写（含历史口径澄清与三个数的来源）。
- 「起容器前自查」条中残留的「并发容器数 ≤3」已同步修正为「本机无其他带卡容器（有则与占用方共用容器或约时间）」。
- 待办：驱动名额上限专项实测，结果回填本节与 `stack.lock`（总组）。
