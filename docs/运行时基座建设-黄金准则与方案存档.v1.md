## 1. 背景：为什么需要这份文档

运行时组的目标是搭建一套**兼容多款国产芯片**的 runtime。这件事天然涉及多个方向，
且各方向节奏、归属、变更频率都不一样：

- **device-context**：负责屏蔽底层设备差异，提供统一运行时接口——是基座最核心的能力来源。
- **总组**：回收 device-context 已验证的能力与现状，制定供全组统一开发的基座；
  负责"基座怎么组装、怎么校验"，具体优化算法由各子方向自己负责。**本文档由总组维护。**
- **memory**：在统一基座之上做显存/缓存管理优化。
- **communication**：在统一基座之上做通信优化。
- **组外算子编译组**：产出 FlagTree（triton）、FlagGems 等代码库——我们是**消费方**，
  跟随其发布节奏。
- **模型组**：做最终的训练/推理调度——是基座的**下游消费方**，基座稳不稳定、
  版本可不可追溯直接决定他们能不能干活。

矛盾点在于：算子编译组的代码库迭代节奏、成熟度与本组维护的推理插件（如
`vllm_plugin_fl`）完全不同，需要对"哪些东西该固定、哪些东西该允许随时切换"
做出明确、可执行的区分，基座才能避免退化成"每次都要重新猜一遍该信哪个版本"的状态——
这正是 `dev/images/image_list.md` 记录的历史教训（910C 上曾同时存在多套镜像，
版本不一致污染过实验结论）。本文档把这套判断标准写死，供全组统一遵循。

## 2. 黄金准则（Golden Rules）

以下七条是设计基座时不可绕过的判断依据。每条准则的"具体怎么落地"见 §3、§4；
"现在做到了哪一条、还差哪一条"见 §5。

| # | 准则 | 一句话理由 |
|---|---|---|
| GR1 | **基座 = 分层组合，每层职责单一、可独立追踪版本**（芯片底座 → 算子编译产物 → runtime 组件 → 挂载/装配），采用可拆解的分层结构 | 只有拆分层次，才能判断"哪一层该固定、哪一层该随时切换"，才能回答"能不能挂载切换 FlagTree 版本"这类问题 |
| GR2 | **优先挂载，其次固化**：变更节奏快、需要"随时切换版本/tag 验证"的层，优先用运行时挂载（volume mount）接入，固化进镜像 tag 作为次选；**现阶段以固化一个固定版本先跑通通路**，是走向"随意切换"的第一步，后续仍需持续迭代至挂载切换的终态 | 固化进镜像意味着每换一个版本就要重新 build、重新验证一整条镜像血统，挂载则可以"改一行 checkout，容器内直接生效" |
| GR3 | **挂载点分两类，区分依据是"变更节奏"而非"归属组内/组外"**：<br>①**静态挂载点**——本阶段验证已冻结、预期短期内不变的组件（不论产出方是组外算子编译组的 FlagTree/FlagGems，还是本组已进入验证阶段的组件如 Torch-FL/FlagCX）：**version + hash 双重校验，必须精确匹配 commit/tag**；<br>②**动态挂载点**——本组正在快速迭代、预期随时切换版本/tag 做验证的组件（当前只有 `vllm_plugin_fl` 这一类由我们自己组内执行变更的推理插件）：**只需分支存在/对齐即可通过校验，顺利启动，无需精确匹配 commit** | 精确 pin 保证"结论性验证的环境可复现，不受底层变化影响而污染结论"；分支级校验保证"自己组内的快速迭代保持高效，不被过度校验拖慢" |
| GR4 | **设备后端遵循 Route A**：各芯片厂商官方设备插件为默认主线（昇腾 = 华为昇腾官方 `torch_npu`）；厂商私有/内部适配方案（如 `torch_fl`/flagos）保留可插拔能力，以显式反向操作激活的 opt-in 方式接入，默认路径始终由官方插件承担 | 官方插件是长期可维护、有厂商背书的路径；私有适配方案锁定的是某个特定环境窗口，应始终保持显式 opt-in 状态 |
| GR5 | **用固定启动脚本代替人工 `docker run`**：`docker compose + bash + yaml config` 的组合固定"怎么启动"——脚本必须显式声明所用 image（版本号 + hash 双重校验），并在启动前检查所有预挂载代码仓是否存在、版本/tag 是否与声明一致；**校验通过方可启动** | 人工 `docker run` 无法保证"这次起的容器和上次起的容器环境一致"；脚本化 + 前置校验把"环境是否对齐"从"事后排查"变成"事前拦截" |
| GR6 | **校验与启动分离，但共用一个入口**：同一套校验逻辑（`pins.yaml` + 校验脚本）既服务总组发版，也服务子方向自行探索，区别只在叠几层配置文件、每层写了什么 | 保证"总组的环境"与"子方向探索的环境"始终共用同一套机制维护，便于日后合并 |
| GR7 | **变更可追溯，留痕管理**：每次基座变更（镜像、版本、路线）必须落一份 changelog；旧版本目录/文件予以保留并标记 `superseded_by`，保证任何历史决策可回溯 | 基座是全组共用的东西，一次未记录的变更可能让某个子方向的历史结论失去复现依据 |

## 3. 具体方案：四层模型

一个镜像血统自上而下拆成四层（对应用户最初设想的"层1/层2/层3/层4"）：

| 层 | 内容示例 | 谁产出 | 变更频率 | 现阶段默认策略 |
|---|---|---|---|---|
| **L1 芯片底座** | CANN / 驱动 / 操作系统 / Python / 厂商官方设备插件（如 `torch_npu`） | 芯片厂商官方 / 算子编译组预构建基座镜像 | 低（跟随厂商发版节奏） | 固化：作为父镜像整体引用，按 digest 锁定 |
| **L2 算子编译** | FlagTree（提供 triton）、FlagGems | 组外算子编译组 | 中（编译组按自己节奏迭代） | **静态挂载点**：现阶段固化进镜像（构建期 pin 一个 commit），远期目标是挂载切换 |
| **L3 Runtime 组件** | Torch-FL、FlagCX（通信）、vLLM、`vllm_plugin_fl` 等推理插件 | 本组 / 本组消费的第三方推理插件 | 高（本组自己维护的部分随时可能改） | 本组已冻结验证的组件（Torch-FL/FlagCX）视为**静态挂载点**；仍在快速迭代的推理插件（`vllm_plugin_fl`）视为**动态挂载点** |
| **L4 挂载/装配** | `docker-compose.<tag>.yml` 的 `volumes:`/`devices:`/`environment:`，工作区代码挂载、设备直通、运行期开关 | 总组（装配规则）+ 各子方向（自己叠加的探索层） | 按需 | 用 compose 原生 `-f` 多文件合并，装配规则本身入库、可审阅 |

四层的边界不是绝对的——判断一个组件属于 L2 还是 L3，看它是"组外算子编译组的产出"还是
"本组维护/消费的 runtime 组件"；L1 与 L2/L3 的边界看它是否随父镜像整体引用。

## 4. 具体方案：机制已落地的部分

GR5/GR6 描述的"固定启动脚本"机制**已经实现**，可直接复用 `dev/ENV-SPEC.md`
定义的一套：

- `docker-compose.<tag>.yml`：这一层用什么镜像、什么挂载、什么环境变量、什么设备（docker
  compose 原生读取）。
- `pins.<tag>.yaml`：这一层期望的镜像 digest 是什么、每个仓库期望的 commit/分支是什么、
  是 `strict`（GR3 的静态挂载点）还是 `loose`（GR3 的动态挂载点）（本规范自己的校验脚本读取）。
- `dev/lib/verify_env.sh` / `up.sh`：校验通过才启动，校验逻辑对总组发版和子方向探索
  完全通用（GR6）；结果落盘 `dev/lib/.env_provenance.json`，供撰写验收报告引用。

Route A（GR4）已经是 `dev/stack.lock.910c.*.yaml` 里 `device_registration.primary`
声明的全组主线，各候选血统在设计时对齐它即可。

**这套机制目前只有 `ascend-operator-runtime/v3`（+ 同源的 `ascend-train-comm/v3`）
在用**——是本文档"具体方案"目前唯一的真实落地实例，见 §5。

## 6. 已知缺口 / 下一步

这里记录的是**本准则视角**的差距，不是 v3 自身的 STOP CONDITION（v3 自己发现的技术阻塞
见 `dev/images/PROCESS.md` 与各 `REBUILD.md`）：

1. **"挂载切换"尚未实现（GR2 远期目标未达成）**：当前所有层仍在构建期固化，
   "挂载 FlagTree/FlagGems 不同版本即测"和"挂载 `vllm_plugin_fl` 不同 tag 即测"都还没有
   对应的 `docker-compose` `volumes:` 配置。建议下一步先在 `vllm_plugin_fl`（已经是
   `loose` 挂载点）上试点：把 `docker-compose.routeA.yml` 加一条把 host 检出的
   `vllm-plugin-FL/` 目录挂进容器、`pip install -e` 装成可编辑模式，验证"改 host
   checkout 的分支 → 容器内直接生效，不需要 rebuild"这条通路是否可行，再推广到
   `FlagGems`。
2. **FlagTree 结构上还做不到"挂载切换"**：`dev/ENV-SPEC.md` 已注明 FlagTree 是构建期
   容器自己 `git fetch` 固定 commit，构建上下文完全来自容器内部，与 host 检出无关——
   这与 GR2 的目标存在结构性冲突：只要 FlagTree 停留在"构建期 fetch"，就只能支持固定
   版本，支持"随时切换版本验证"需要算子编译组配合调整其发布形态（例如提供可直接挂载的
   源码目录，而非只提供预构建 wheel/镜像）——需要跨组协调，记为跨组协调事项。
3. **"静态/动态挂载点"目前只覆盖了 5 个仓库**（`FlagTree`/`FlagGems`/`Torch-FL`/
   `FlagCX`/`vllm-plugin-FL`，见 `dev/ENV-SPEC.md` 仓库名注册表）——新增组件（如
   模型组自己的推理框架分支）接入基座时，第一步就是判断它属于哪一类挂载点，
   写进对应 `pins.<tag>.yaml`，而不是先斩后奏直接固化进镜像。
