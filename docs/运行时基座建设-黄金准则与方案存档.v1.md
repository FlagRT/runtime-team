## 1. 背景：为什么需要这份文档

运行时组的目标是搭建一套**兼容多款国产芯片**的 runtime。这件事天然涉及多个方向，
且各方向节奏、归属、变更频率都不一样：

- **device-context**：负责屏蔽底层设备差异，提供统一运行时接口——是基座最核心的能力来源。
- **总组**：回收 device-context 已验证的能力与现状，制定供全组统一开发的基座；
  负责"基座怎么组装、怎么校验"，具体优化算法由各子方向自己负责。**本文档由总组维护。**
- **memory**：在统一基座之上做显存/缓存管理优化。
- **communication**：在统一基座之上做通信优化。
- **组外算子编译组**：产出 FlagTree（triton）、FlagGems 等代码库——我们是**消费方**，
  跟随其发布节奏。
- **模型组**：做最终的训练/推理调度——是基座的**下游消费方**，基座稳不稳定、
  版本可不可追溯直接决定他们能不能干活。

矛盾点在于：算子编译组的代码库迭代节奏、成熟度与本组维护的推理插件（如
`vllm_plugin_fl`）完全不同，需要对"哪些东西该固定、哪些东西该允许随时切换"
做出明确、可执行的区分，基座才能避免退化成"每次都要重新猜一遍该信哪个版本"的状态——
这正是 `dev/images/image_list.md` 记录的历史教训（910C 上曾同时存在多套镜像，
版本不一致污染过实验结论）。本文档把这套判断标准写死，供全组统一遵循。

## 2. 黄金准则（Golden Rules）

以下七条是设计基座时不可绕过的判断依据。每条准则的"具体怎么落地"见 §3、§4；
"现在做到了哪一条、还差哪一条"见 §5。

| # | 准则 | 一句话理由 |
|---|---|---|
| GR1 | **基座 = 分层组合，每层职责单一、可独立追踪版本**（芯片底座 → 算子编译产物 → runtime 组件 → 挂载/装配），采用可拆解的分层结构 | 只有拆分层次，才能判断"哪一层该固定、哪一层该随时切换"，才能回答"能不能挂载切换 FlagTree 版本"这类问题 |
| GR2 | **优先挂载，其次固化**：变更节奏快、需要"随时切换版本/tag 验证"的层，优先用运行时挂载（volume mount）接入，固化进镜像 tag 作为次选；**现阶段以固化一个固定版本先跑通通路**，是走向"随意切换"的第一步，后续仍需持续迭代至挂载切换的终态 | 固化进镜像意味着每换一个版本就要重新 build、重新验证一整条镜像血统，挂载则可以"改一行 checkout，容器内直接生效" |
| GR3 | **资产按交付方式分两类，变更节奏决定放进哪一类**：<br>①**固化资产**——代码在构建期进入镜像，版本由 image id 唯一确定，只核对镜像 id，不核对宿主检出；<br>②**挂载资产**——代码来自宿主目录、运行时挂载并以可编辑方式生效，版本按运行实例确定（启动时宿主 repo 的 HEAD），核对宿主 commit 与工作区状态。<br>本阶段验证冻结、预期短期不变的组件（不论产出方在组内还是组外）放入固化资产；正在快速迭代、需要随时切换版本验证的组件放入挂载资产。两类之间只通过显式动作迁移：**晋升**（挂载 → 固化，写入新版本镜像配方）与**下放**（固化 → 挂载，在运行环境中声明挂载覆盖镜像内版本），不存在隐式状态 | 交付方式决定"版本归谁、怎么核对"：固化资产的版本属于镜像，与宿主检出无关；挂载资产的版本属于运行实例。按变更节奏选择放置位置，兼顾结论性验证的可复现与组内迭代效率 |
| GR4 | **设备后端遵循 Route A**：各芯片厂商官方设备插件为默认主线（昇腾 = 华为昇腾官方 `torch_npu`）；厂商私有/内部适配方案（如 `torch_fl`/flagos）保留可插拔能力，以显式反向操作激活的 opt-in 方式接入，默认路径始终由官方插件承担 | 官方插件是长期可维护、有厂商背书的路径；私有适配方案锁定的是某个特定环境窗口，应始终保持显式 opt-in 状态 |
| GR5 | **用固定启动脚本代替人工 `docker run`**：`docker compose + bash + yaml` 的组合固定"怎么启动"——运行环境显式声明所用镜像（以 image id 核对）与以可编辑方式挂载的代码仓（以 commit 核对），启动前自动核对。**默认只报告不一致、不阻止启动；验收与出结论的运行使用 `--strict`，不一致即拒绝启动** | 人工 `docker run` 无法保证"这次起的容器和上次起的容器环境一致"；脚本化 + 前置核对把"环境是否对齐"从"事后排查"变成"事前可见"，结论性运行再加强制拦截 |
| GR6 | **核对与启动分离，但共用一个入口**：同一套基线文件与管理脚本（`dev/lib/baseline.py` + `dev/lib/up.sh`）既服务总组发版，也服务子方向自行探索，区别只在运行环境目录里声明了什么 | 保证"总组的环境"与"子方向探索的环境"始终共用同一套机制维护，便于日后合并 |
| GR7 | **变更可追溯，留痕管理**：每次基座变更（镜像、版本、路线）必须落一份 changelog；旧镜像版本目录予以保留并标记 `superseded_by`；被取代的运行配置文件可删除，取代关系记入对应 `lock.yaml` changelog，内容由 git 历史保留 | 基座是全组共用的东西，一次未记录的变更可能让某个子方向的历史结论失去复现依据 |

## 3. 具体方案：四层模型

一个镜像血统自上而下拆成四层（对应用户最初设想的"层1/层2/层3/层4"）：

| 层 | 内容示例 | 谁产出 | 变更频率 | 现阶段默认策略 |
|---|---|---|---|---|
| **L1 芯片底座** | CANN / 驱动 / 操作系统 / Python / 厂商官方设备插件（如 `torch_npu`） | 芯片厂商官方 / 算子编译组预构建基座镜像 | 低（跟随厂商发版节奏） | 固化：作为父镜像整体引用，按 digest 锁定 |
| **L2 算子编译** | FlagTree（提供 triton）、FlagGems | 组外算子编译组 | 中（编译组按自己节奏迭代） | 固化资产：构建期 pin 一个 commit；远期目标是可挂载切换 |
| **L3 Runtime 组件** | Torch-FL、FlagCX（通信）、vLLM、`vllm_plugin_fl` 等推理插件 | 本组 / 本组消费的第三方推理插件 | 高（本组自己维护的部分随时可能改） | 默认固化；需要快速迭代的组件（如 `vllm_plugin_fl`）在运行环境中下放为挂载资产 |
| **L4 挂载/装配** | 运行环境目录的 `docker-compose.yml`：`volumes:`/`devices:`/`environment:`，工作区代码挂载、设备直通、运行期开关 | 总组（镜像 demo）+ 各子方向（自己的运行环境目录） | 按需 | 一个目录 = 一个运行环境；经 compose `extends` 复用镜像 demo，装配规则本身入库、可审阅 |

四层的边界不是绝对的——判断一个组件属于 L2 还是 L3，看它是"组外算子编译组的产出"还是
"本组维护/消费的 runtime 组件"；L1 与 L2/L3 的边界看它是否随父镜像整体引用。

层级（L1–L4）与交付方式（固化 / 挂载，GR3）正交：层级描述资产的职责，交付方式描述代码从哪里来；
同一层的资产既可固化也可挂载。基线文件对每项资产同时记录两者。

## 4. 具体方案：环境基线机制

GR3/GR5/GR6 由环境基线机制落地，规范见 [`dev/ENV-SPEC.md`](../dev/ENV-SPEC.md)：

- **镜像基线** `dev/images/<name>/v<N>/image.baseline.yaml`：镜像固化的全部资产与版本，由 image id 约束。
- **运行环境目录**：`docker-compose.yml`（含 `x-flagrt` 声明）+ `env.baseline.yaml`（挂载资产的 commit）。
  每个镜像附带一个 demo 运行环境目录，记录验收时的运行配置。
- **`dev/lib/baseline.py`**（export / check / load / show / list）与 **`dev/lib/up.sh <env-dir> [--strict]`**：
  对总组发版和子方向探索完全通用（GR6）；每次核对结果写入该运行环境目录的 `.last-check.json`。

Route A（GR4）已经是 `dev/stack.lock.910c.*.yaml` 里 `device_registration.primary`
声明的全组主线，各候选血统在设计时对齐它即可。

目前接入本机制的是 `ascend-operator-runtime/v3` 与 `ascend-train-comm/v3`，见 §5。

## 6. 已知缺口 / 下一步

这里记录的是**本准则视角**的差距，不是 v3 自身的 STOP CONDITION（v3 自己发现的技术阻塞
见 `dev/images/PROCESS.md` 与各 `REBUILD.md`）：

1. **挂载切换已在 `vllm_plugin_fl` 上验证可行，尚未推广**：试点以可编辑方式挂载宿主
   `vllm-plugin-FL/` 覆盖镜像内固化版本，宿主改动在容器内直接生效，export / check / load 闭环
   跑通（生效方式与注意事项见 `dev/ENV-SPEC.md` §5、§6）。下一步按需推广到 `FlagGems`；
   挂载副本不含镜像内固化补丁时，check 会给出警告。
2. **FlagTree 结构上仍做不到"挂载切换"**：FlagTree 在构建期由容器自行 `git fetch` 固定 commit
   并编译，运行时可替换的只是编译产物，与宿主源码检出无关——只要停留在"构建期 fetch + 编译"，
   就只能以固化资产交付。支持"随时切换版本验证"需要算子编译组配合调整其发布形态（例如提供
   可直接挂载的源码目录或可替换的构建产物），记为跨组协调事项。
3. **新增组件接入**：新组件（如模型组自己的推理框架分支）接入基座时，第一步是按 GR3 判断
   它作为固化资产还是挂载资产交付，并写入对应镜像配方或运行环境声明，而不是直接固化进镜像。

  规范相应新增 §4.2 模式 6 与 `baked_packages` 块、§2.3「不可下放的固化资产」、
  `commit: unavailable` 一档（取不到 commit 是已知不可得，不是错误），并把 `baseline.py` 里
  昇腾专属的取数硬编码收敛为声明式探针表（接第三款芯片只加数据、不改控制流）。
  GR1–GR7 的条文本身未改。规范见 `dev/ENV-SPEC.md` §2.3/§3.1/§4.1/§4.2/§5。
- 2026-10-10：以环境基线机制取代 `pins.<tag>.yaml` + `verify_env` + 多文件 compose 叠加。
  GR3 由"按变更节奏分静态/动态挂载点"改为"按交付方式分固化/挂载资产，变更节奏决定放置位置，
  晋升/下放为显式动作"；GR5 改为默认只报告、`--strict` 时强制；GR6/GR7 措辞随之调整；
